| 단계 | 작업 | 검증 및 인계 |
|------|------|-------------|
| 1. 호환성 | 고정 태그의 core API, 조판 전 HFT 공급과 native bridge의 호출 시점, Studio의 메뉴·호스트 공급 API 및 matcher generator 입력을 대조한다. | core 읽기 전용 호환성 검사와 실제 소스 대조. 필요한 호스트 변경과 원인을 구현 범위에 특정한다. |
| 2. 공식 후보 생성 | RustBridge pin·Cargo.lock·core lock, Swift build-info와 render tree golden을 생성한다. 같은 태그의 WASM을 빌드하고 앱 소유 어댑터로 Studio를 생성한다. native matcher와 receipt, README 배지를 갱신한다. | universal bridge·portable ABI, 실제 producer와 Swift decode, Studio strict 검증, matcher 재생성 검증, HostApp 빌드. #594에 checkout·Studio Resources·Frameworks 실제 위치와 manifest·주요 파일 해시를 전달한다. |
| 3. 글꼴·소비자 수용 | #598 fixture와 실제 설치 글꼴 대조, sample10 HWP3/HFT HWPX, 고운바탕 저장 후 새 프로세스 재열기를 재실행한다. Studio·native 본문, PDF·인쇄, Quick Look·Thumbnail을 원본과 독립 출력으로 대조한다. | 공급 bytes, 실제 선택 face, 배치, 출력 증거를 각 입력별로 기록한다. 합성 시험·실제 대상·실제 OS 변경을 구분하고 재현되지 않은 항목은 원인과 함께 남긴다. |

## 작업 범위와 판정

- 체크아웃과 인덱스를 #594와 분리한다. T7에 빌드·비공개 검증 자료를 두고 Cargo target은 공용 지정 경로를 사용한다.
- 생성 코드는 writer와 verifier로 갱신한다. 기존 웹폰트 무응답 보완 실험 어댑터를 복사하지 않는다. v0.9.0의 AbortController·기한 처리와 앱의 글꼴 메뉴 어댑터가 각각 유지되는지 확인한다.
- 기존 공급 fixture 기준은 67 PASS·0 FAIL·30 NOT_RUN, 고운바탕 기능 검사는 40 PASS 및 저장 재열기 6개 항목이다. 실제 파일 SHA와 상태를 대조하고 변경된 결과에는 이유를 기록한다.
- 실제 딸기 서체 및 독립 한컴 PDF의 확보 여부, 설치 권한, 실제 Intel·최소 OS 가용성을 기록한다. 실물 없이 해결 문구를 확정하지 않는다. 독립 PDF와 공급 증거가 확보돼도 소비자별 최종 출력에 대한 관찰이 필요하다.
- native 공급 수명·ABI, Studio API·생성기, golden decode 실패는 실제 원인을 조사한 뒤 필요한 앱 소유 변경을 제시한다. 코드 변경 전 관련 매뉴얼을 확인하고 단계 승인을 받는다.

수행계획 승인 후 구현계획에 명령·산출물·검증 순서를 구체화한다. [작업 절차](../manual/task_workflow_guide.md), [core 운영](../manual/core_dependency_operation_guide.md), [빌드·검증](../manual/build_run_guide.md), [릴리스 운영](../manual/release_distribution_guide.md)을 따른다.
