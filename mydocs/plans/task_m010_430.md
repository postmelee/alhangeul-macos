# Issue #430 수행 계획서

## 목적

GitHub Pages 홈 하단에 프로젝트의 문서 접근 철학을 명시적으로 보여주고, 링크 공유 시 사용하는 Open Graph 설명을 간결하게 정리한다. 승인된 HTML/CSS 변경을 기존 docs-only Pages 배포 경로로 공개하고, 기존 public Sparkle appcast가 보존되는지 확인한다.

## 배경

- GitHub Issue: [#430](https://github.com/postmelee/alhangeul-macos/issues/430)
- Milestone: v0.1
- 문서 prefix: `task_m010_430`
- 통합 브랜치: `devel`
- 작업 브랜치: `local/task430`

기존 Pages 홈은 footer에서 제품을 짧게 설명하지만, 프로젝트가 지향하는 문서 접근 철학을 본문에서 독립된 메시지로 보여주지 않는다. 이전 #178에서는 두 번째 앱 소개 섹션의 화면 밀도 문제로 철학 문구가 제거됐고, #212에서는 footer 문구가 제품 설명으로 통일됐다.

이번 작업 전 로컬 시안 검토를 통해 철학 문구의 최종 위치, 문장, 강조 범위와 여백을 확정했다. 승인된 시안은 Task #430 시작 전에 이름 있는 Git stash로 보존했으며, 수행계획 승인 전에는 `docs/`에 다시 적용하지 않는다.

## 범위

포함:

- `docs/index.html`의 Open Graph 설명을 `Mac에서 HWP/HWPX를 미리보고 편집하고 공유하는 오픈소스 앱입니다.`로 변경
- FAQ 다음, footer 직전 본문 최하단에 독립 철학 섹션 추가
- 철학 제목 `문서 접근은 특정 프로그램 구매 여부에 묶이면 안 됩니다.`와 보조 설명 반영
- 제목 중 `문서 접근`은 파란색과 600 굵기, `특정 프로그램 구매 여부`는 본문색과 600 굵기, 나머지는 400 굵기로 표시
- 제목 크기를 기존 섹션 헤더와 같은 데스크톱 40px, 태블릿 38px, 모바일 32px로 적용
- 철학 섹션의 위아래 여백을 데스크톱 `clamp(88px, 10vh, 120px)`, 모바일 68px로 대칭 적용
- 로컬 정적 서버 시각 검증, Pages artifact 사전 검증, PR CI 확인
- 승인된 `main` 반영 후 `Docs-only Pages Deploy` workflow와 공개 Pages 확인
- docs-only 배포 전후 public appcast 보존 여부 확인

제외:

- footer 문구 변경
- HostApp, Quick Look, Thumbnail, Swift/Rust 코드 변경
- `.github/workflows/pages-docs-deploy.yml`과 Pages 저장소 설정 변경
- 새 앱 버전, release tag, GitHub Release, DMG 생성
- Sparkle appcast 신규 항목 생성 또는 교체
- Homebrew Cask 변경
- 업데이트·릴리즈 노트 페이지 구조 변경

## 설계 방향

철학 섹션은 FAQ와 footer 사이에 독립된 `<section>`으로 둔다. 기존 흰색 배경, near-black 본문, 파란색 accent, muted 설명색을 재사용하며 새 이미지나 장식 요소는 추가하지 않는다.

긴 제목 전체를 같은 굵기로 표시하지 않고 의미상 핵심인 `문서 접근`과 `특정 프로그램 구매 여부`만 다른 섹션 헤더와 같은 600 굵기로 올린다. `문서 접근`에만 기존 accent 색상을 적용하고 나머지 핵심 구절은 본문색을 유지한다. 보조 설명은 muted 색상과 좁은 최대 폭으로 제목 아래에 배치한다.

섹션 위아래 padding은 같은 값으로 맞춰 footer 직전에서 시각 중심이 한쪽으로 치우치지 않게 한다. footer 문구는 기존 제품 설명을 유지해 철학 본문과 footer 역할을 분리한다.

배포는 기존 `Docs-only Pages Deploy` workflow를 사용한다. 이 workflow는 `main`의 `docs/**` 변경에서 실행되고 현재 public appcast를 내려받아 검증한 뒤 Pages artifact에 보존한다. Task #430 통합 대상은 정책상 `devel`이므로, `main` 승격 단계에서는 `origin/main...origin/devel` 포함 범위를 다시 확인하고 Task #430 외 변경의 동반 반영 여부를 별도 승인받는다.

## 잠정 단계

1. Stage 1: 현재 Pages 구조, 승인 시안, docs-only 배포 경계를 대조하고 구현계획서 작성
2. Stage 2: 승인 시안을 `local/task430`에 복원해 HTML/CSS 구현, 문구·반응형·footer 무손실 검증
3. Stage 3: 로컬 브라우저 시각 검증과 Pages artifact/appcast 보존 사전 검증, 단계 결과 기록
4. Stage 4: 최종 결과보고서 작성, `publish/task430` 게시와 `devel` 대상 PR 생성
5. Stage 5: PR merge 이후 승인된 `main` 승격 경로 적용, Docs-only Pages workflow와 공개 Pages/appcast 검증, 배포 결과 기록 보정

각 단계 완료 후 단계별 보고서 또는 해당 절차의 승인 요청을 제시하고, 작업지시자 승인 없이 다음 단계로 넘어가지 않는다. `main` 반영과 Pages 공개 배포는 별도 승인 gate로 다룬다.

## 리스크

- 긴 한국어 제목이 중간 폭과 모바일에서 과도하게 줄바꿈될 수 있다.
- FAQ와 footer 사이에 새 섹션을 추가하면 페이지 최하단 길이와 스크롤 리듬이 달라진다.
- 제목 일부에 accent와 굵기를 함께 적용하면 강조 범위가 과해 보일 수 있다.
- 브라우저가 이전 CSS query를 캐시하면 시각 검증에서 새 스타일이 즉시 보이지 않을 수 있다.
- docs-only 배포가 public appcast 다운로드·XML 검증 또는 release asset gate에서 중단될 수 있다.
- `devel`과 `main`에 Task #430 외 차이가 있으므로 `main` 승격 범위를 확인하지 않으면 관련 없는 변경이 함께 공개될 수 있다.
- Pages 배포 성공 뒤 CDN 반영 지연으로 공개 페이지 확인 시점에 잠시 이전 내용이 보일 수 있다.

## 승인 요청 사항

이 수행계획서 기준으로 Stage 1의 현재 구조·배포 경계 조사와 구현계획서(`mydocs/plans/task_m010_430_impl.md`) 작성을 진행할지 승인 요청한다.

승인 전에는 보존한 시안을 `docs/`에 복원하거나 새 구현 변경을 진행하지 않는다. `main` 승격과 public Pages 배포는 구현·검증·PR merge 이후 별도 승인받는다.
