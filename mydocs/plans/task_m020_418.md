# Task M020 #418 수행계획서

## 목적

upstream `edwardkim/rhwp v0.7.18`을 최신 `devel` 기준으로 다시 full sync하고, native core와 bundled `rhwp-studio`를 동일한 release tag와 resolved commit으로 정렬한다.

기존 자동 PR #415가 만들어진 뒤 merge된 #391, #408, #406을 보존하면서 #408의 external image context C ABI 15개와 새 core artifact provenance가 `v0.7.18`에서 유효한지 검증한다. 이 결과를 다음 public release 작업의 확정 입력으로 넘긴다.

## 배경

현재 `devel`의 `rhwp-core.lock`, `RustBridge/Cargo.toml`, bundled `rhwp-studio/manifest.json`은 `v0.7.17` / `03351190ec35436e58cbfee0aa9278a8fdc04a59`를 가리킨다. upstream 최신 stable release는 `v0.7.18` / `93862a4e16df59834ebce46d91e948cd739208e9`이며 upstream `main`도 같은 commit에 있다.

자동 full sync PR #415는 `devel`이 `477447f`였을 때 생성됐다. 현재 `devel`은 그 뒤 #408과 #406을 포함해 17커밋 전진했고, GitHub은 #415를 `mergeable=false`, `mergeable_state=dirty`로 판정한다. 로컬 `git merge-tree`에서도 `rhwp-core.lock` 충돌이 확인됐다.

#415의 성공 CI는 #408의 `HwpDocument` 전환과 external image setter/query/injection ABI가 merge되기 전에 실행됐다. `v0.7.18` source에 해당 upstream API가 유지되는 것은 확인했지만, 현재 RustBridge source와 새 tag 조합의 build, test, generated header, symbol lock, app target compile/link는 다시 검증해야 한다.

## 범위

포함:

- PR #415의 stale 상태와 재생성 조건을 확인하고 superseded 처리 또는 동등한 최신화 방식을 확정한다.
- 최신 `origin/devel`에서 `v0.7.18` full sync 후보를 생성한다.
- `RustBridge/Cargo.toml`, `RustBridge/Cargo.lock`, `rhwp-core.lock`을 `v0.7.18` 기준으로 갱신한다.
- bundled `rhwp-studio`와 WASM assets를 target commit에서 다시 빌드·동기화한다.
- manifest의 tag, commit, `source_cargo_lock_sha256`, entrypoint hash를 검증한다.
- #408의 15개 expected/generated FFI symbol, generated header, static library/XCFramework provenance를 보존한다.
- RustBridge test, embedded image regression, HostApp/Quick Look/Thumbnail build를 실행한다.
- current visual regression harness와 대표 HWP/HWPX sample로 renderer 회귀를 측정한다.
- upstream release note를 앱 사용자-facing, 개발자-facing, bundled editor 영향으로 분류한다.
- 다음 public release task에 넘길 검증 결과와 잔여 위험을 정리한다.

제외:

- public release version/build 확정과 버전 파일 갱신
- signing, notarization, GitHub Release, Sparkle, Pages, Homebrew 배포
- #409 Swift external image resolver와 #410~#413 후속 기능
- Skia release default 전환
- upstream `edwardkim/rhwp` source 수정
- unreleased commit 또는 floating branch pin

## 설계 방향

1. Stable dependency 기준은 `v0.7.18` release tag와 resolved commit `93862a4e16df59834ebce46d91e948cd739208e9`의 쌍으로 고정한다.
2. 충돌 난 #415의 `rhwp-core.lock`을 한쪽 버전으로 수동 선택하지 않는다. 최신 `devel`의 #408 ABI를 입력으로 core build와 lock generation을 다시 실행해 artifact metadata를 재계산한다.
3. native core와 bundled `rhwp-studio`는 같은 upstream tag/commit으로 한 PR에서 동기화한다. viewer/WASM reference가 다른 tag에 남는 구성을 허용하지 않는다.
4. `rhwp-ffi-symbols.txt`의 15개 symbol을 ABI 기준으로 유지한다. upstream update로 symbol이나 header가 바뀌면 임의 수용하지 않고 원인을 분류한다.
5. static archive byte hash 차이는 source/ABI 실패와 구분하되, 최종 `rhwp-core.lock`에는 이번 기준 환경에서 생성한 reference metadata를 기록한다.
6. #415의 원격 close, branch cleanup, workflow 재실행 같은 GitHub mutation은 Stage 1 조사 결과와 작업지시자 승인 뒤 수행한다.
7. public release 준비는 이 타스크에서 실행하지 않는다. 최종 보고서 승인과 sync PR merge 뒤 별도 Release Operations 이슈로 시작한다.

## 리스크

- `v0.7.18`은 `v0.7.17` 이후 렌더링, 페이지네이션, 대형 표 성능, tolerant parsing, bundled editor를 크게 변경했다. compile 성공만으로 사용자-visible 회귀가 없다고 판단할 수 없다.
- #415의 기존 녹색 CI는 현재 #408 source를 검증하지 않았으므로 재사용할 수 없다.
- Rust dependency graph에 TIFF 등 신규 dependency가 추가돼 static archive 크기, universal build 시간, WASM 크기가 증가할 수 있다.
- generated static archive의 byte hash는 toolchain과 build path에 민감하다. strict mismatch가 생기면 #394의 portable verification 기준과 source/ABI 결과를 분리해 기록해야 한다.
- bundled studio rebuild는 upstream Docker/npm 환경과 asset hash에 의존한다. 자동 workflow 재생성이 실패하면 기존 #415 asset을 무검증 복사하지 않고 실패 지점을 보고한다.
- visual harness는 macOS sandbox readiness 또는 설치/등록 상태 영향을 받을 수 있다. 환경 실패와 renderer regression을 구분한다.
- public release 직전에 기능 범위를 확장하면 회귀 판단이 어려워진다. #409 이후 external image 제품 기능은 이번 타스크와 다음 release의 기본 범위에서 제외한다.

## 승인 요청 사항

1. #418을 `v0.7.18` full sync와 current `devel` 통합 검증의 추적 이슈로 사용한다.
2. 기준 브랜치는 `devel`, 분리 worktree의 작업 브랜치는 `local/task418`로 진행한다.
3. #415의 충돌을 수동 lock 선택으로 해결하지 않고 최신 `devel`에서 core/studio sync를 재생성한다.
4. #408의 15개 C ABI symbol 보존과 core/studio 동일 provenance를 필수 gate로 둔다.
5. 위 5개 잠정 단계와 public release 분리 원칙을 승인한다.

수행계획서 승인 전에는 구현계획서 작성, core/studio 파일 변경, PR #415 상태 변경, workflow 재실행을 진행하지 않는다.
