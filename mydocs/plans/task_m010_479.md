# Task M010 #479 수행계획서

## 목적

Debug·개발 빌드가 production 익명 앱 실행 이벤트 endpoint로 요청을 보내지 않도록 빌드 구성 경계를 분리한다. Signed/notarized 배포에 사용하는 Release 구성에는 공개 production endpoint를 유지하되, endpoint가 없거나 잘못된 개발 산출물에서도 앱 실행·문서 기능·Sparkle 업데이트가 비차단으로 정상 동작하는 계약을 검증한다.

개발 빌드와 공개 배포 빌드를 payload에 새 식별자를 추가해 사후 구분하지 않고, 개발 빌드의 production 전송 자체를 차단한다. 기존 운영 집계는 삭제·보정하지 않으며 공개 릴리즈 이전 version 행이 개발 실행에서 유입됐을 수 있다는 관측 한계를 문서화한다.

## 배경

Issue #453은 영구 사용자·기기·설치 식별자 없이 최초 실행·기존 설치 기준선·업데이트 이벤트를 보내는 비차단 분석 경로를 추가했다. `AppExecutionAnalyticsEndpoint.resolve()`는 `Info.plist`의 `AlhangeulAppExecutionEndpoint`가 credential·query·fragment 없는 HTTPS URL일 때만 endpoint를 반환하고, 값이 없거나 잘못되면 `nil`을 반환한다.

현재 `Sources/HostApp/Info.plist`에는 production Worker URL이 고정 문자열로 들어 있다. HostApp의 Debug와 Release가 같은 plist를 사용하므로 기능 병합 뒤 실행한 Debug·개발 앱도 production endpoint를 해석할 수 있다. 공개 v0.1.9에는 수집 코드가 없었지만 운영 집계에 v0.1.9 `existing_baseline` 행이 존재하며, 현재 payload만으로 공개 Release 실행과 개발 빌드를 사후 구분할 수 없다.

`project.yml`이 Xcode project의 진실 원천이고 HostApp 설정은 아직 Debug/Release별 analytics endpoint를 구분하지 않는다. 따라서 plist key를 build setting placeholder로 바꾸고 `project.yml`에서 Release에만 production 값을 주입하는 방향을 우선 검토한다. 생성된 `Alhangeul.xcodeproj`는 직접 수정하지 않고 `xcodegen generate` 결과만 반영한다.

## 범위(포함·제외)

포함:

- HostApp production analytics endpoint의 Debug/Release build configuration별 주입 경계 확정
- Debug와 endpoint 미지정 개발 구성에서 `AlhangeulAppExecutionEndpoint`가 유효한 production URL로 해석되지 않도록 차단
- Release 구성에서 기존 production HTTPS endpoint가 정확히 포함되는지 정적·built bundle 기준 검증
- endpoint 없음·빈 값·잘못된 값에서 분석 runtime이 outbox flush를 시작하지 않고 앱 기능을 방해하지 않는 기존 fail-closed 계약 확인
- 기존 opt-out, outbox 보존·폐기, Sparkle pending/update 분류와 payload allowlist 회귀 검증
- `project.yml` 변경 뒤 XcodeGen 재생성과 생성 project drift 확인
- 공개 릴리즈 이전 version 운영 행의 발생 가능성과 기존 데이터 미보정 원칙 문서화
- 필요 시 PR CI 또는 isolated helper에 configuration drift 검증 추가

제외:

- 기존 production 집계 행의 삭제·수정·재분류
- production Worker, analytics 저장소 또는 `postmelee/alhangeul-analytics` 배포 변경
- 영구 사용자·기기·설치 식별자나 상세 build identifier를 payload에 추가하는 작업
- Debug 이벤트를 production endpoint로 합성 전송하는 smoke
- 별도 staging endpoint 생성·배포 또는 secret 등록
- 분석 기능 전체 제거, 기본 opt-out 전환이나 개인정보 UI 재설계
- public release, 서명, 공증, GitHub Release, appcast와 Homebrew 배포 실행

## 설계 방향

1. 공통 `Info.plist`에는 production URL 자체가 아니라 전용 build setting placeholder만 둔다. HostApp `project.yml` 설정에서 Debug는 빈 값 또는 미정의 값으로 두고 Release에만 기존 공개 HTTPS endpoint를 주입한다.
2. endpoint 부재를 정상적인 비활성 상태로 취급한다. Debug 전용 분기를 분석 runtime에 추가하기보다 기존 `AppExecutionAnalyticsEndpoint.resolve() -> nil`과 비차단 startup 경로를 재사용해 configuration이 잘못돼도 네트워크 전송 없이 앱이 계속 동작하게 한다.
3. configuration 이름을 payload dimension으로 추가하지 않는다. 개발/배포 구분은 빌드 산출물 생성 시점에 끝내고 공개 payload 여섯 key 및 개인정보 경계를 유지한다.
4. 설정 검증은 source 문자열만 확인하지 않고 Debug와 Release의 resolved build setting 또는 built app `Contents/Info.plist`를 확인한다. Debug에서는 key가 없거나 빈 값이라 resolver가 `nil`이어야 하고, Release에서는 exact production URL이 credential·query·fragment 없는 HTTPS URL이어야 한다.
5. Release endpoint를 command line 임시 override나 개발자 로컬 환경 변수에 의존시키지 않는다. 저장소의 `project.yml`이 배포 구성의 재현 가능한 진실 원천을 유지하도록 한다.
6. 실제 production 요청을 보내지 않고도 설정 경계를 검증할 수 있게 한다. unit test, `xcodebuild -showBuildSettings`, built plist 검사와 stub transport를 우선하고 production endpoint network smoke는 수행하지 않는다.
7. CI 자동화 추가 여부는 Stage 1에서 기존 `pr-ci.yml`의 Debug build와 release helper gate를 조사해 결정한다. 작은 configuration verifier로 충분하면 별도 Release 전체 build를 매 PR마다 추가하지 않는다.

## 잠정 단계(3단계)

1. 현재 설정·실행 경계 조사와 configuration 계약 확정
   - `Info.plist`, `project.yml`, generated project, Debug/Release resolved build setting과 분석 startup 경로를 추적한다.
   - Debug가 production endpoint를 포함하는 현재 상태를 built plist 또는 동등한 재현으로 고정한다.
   - endpoint 없음에서 outbox와 앱 실행이 비차단으로 유지되는 기존 test seam, CI와 release package 검증 지점을 확정한다.
2. Release-only endpoint 주입과 자동 회귀 구현
   - plist placeholder와 `project.yml` configuration 설정을 적용하고 Xcode project를 재생성한다.
   - Debug 비활성, Release exact endpoint, missing/invalid endpoint fail-closed와 기존 analytics runtime 계약을 테스트한다.
   - 필요하면 configuration drift를 잡는 isolated helper와 PR CI gate를 추가한다.
3. Debug·Release 산출물 검증과 운영 한계 문서화
   - HostAppTests, Debug build와 서명·배포를 수행하지 않는 Release build를 검증한다.
   - 두 built app의 `Contents/Info.plist`와 endpoint 해석 결과를 비교하고 production 네트워크 요청이 없는 방식으로 완료 기준을 확인한다.
   - 기존 운영 데이터의 발생 가능성, 미보정 원칙과 향후 개발 smoke 경계를 analytics 계약·최종 보고에 기록한다.

## 검증 계획

기본 정적·생성 검증:

```bash
xcodegen generate
git diff --check
./scripts/check-no-appkit.sh
```

자동 테스트와 Debug build:

```bash
xcodebuild -project Alhangeul.xcodeproj \
  -scheme HostAppTests \
  -configuration Debug \
  -derivedDataPath build.noindex/task479-tests \
  CODE_SIGNING_ALLOWED=NO \
  test
xcodebuild -project Alhangeul.xcodeproj \
  -scheme HostApp \
  -configuration Debug \
  -derivedDataPath build.noindex/task479-debug \
  CODE_SIGNING_ALLOWED=NO \
  build
```

Release configuration 검증은 public package·서명·공증 없이 별도 `build.noindex/` 산출물로 수행한다.

```bash
xcodebuild -project Alhangeul.xcodeproj \
  -scheme HostApp \
  -configuration Release \
  -derivedDataPath build.noindex/task479-release \
  CODE_SIGNING_ALLOWED=NO \
  build
```

산출물·계약 검증 항목:

- Debug built app의 `AlhangeulAppExecutionEndpoint`가 없거나 빈 값이며 `AppExecutionAnalyticsEndpoint.resolve()` 결과가 `nil`
- Release built app에는 기존 exact production HTTPS endpoint가 포함되고 credential·query·fragment가 없음
- endpoint `nil`, 빈 문자열과 잘못된 값에서 transport 요청이 시작되지 않고 startup/outbox 관찰이 앱 실행을 차단하지 않음
- 기존 opt-out, outbox, Sparkle update와 여섯 key payload allowlist 테스트 통과
- Debug/Release configuration을 바꿔도 문서 열기와 Sparkle 설정에 필요한 다른 plist key가 유지됨
- `xcodegen generate` 재실행 뒤 예상 밖 project diff 없음
- production Worker로 실제 합성 이벤트를 보내지 않음

## 리스크

- plist placeholder가 미정의일 때 문자열 `$(SETTING_NAME)` 자체가 산출물에 남으면 resolver가 의도치 않은 값을 처리하거나 검증이 환경별로 달라질 수 있다. Debug built plist의 실제 결과를 기준으로 빈 값·key 제거 중 한 정책을 확정한다.
- Release endpoint 설정을 공통 base에서 제거한 뒤 Release configuration에 잘못 배치하면 public 배포의 분석이 조용히 비활성화될 수 있다. Release built plist exact-value 검증을 blocking gate로 둔다.
- Debug/Release 이름에만 의존한 임시 shell 분기는 Archive나 release workflow의 configuration override와 어긋날 수 있다. `project.yml`과 실제 release scripts의 `Release` 사용을 함께 확인한다.
- unit test는 test bundle의 generated plist를 사용하므로 HostApp built plist configuration을 직접 보장하지 못한다. source unit test와 제품 bundle 검증의 책임을 분리한다.
- 매 PR마다 Release 전체 build를 추가하면 CI 시간이 불필요하게 늘 수 있다. configuration verifier로 충분한지 먼저 판단하고 최소 gate를 선택한다.
- 기존 production 집계에서 개발 실행과 실제 공개 실행을 사후 구분할 수 없다. 근거 없이 행을 삭제하거나 수치를 보정하지 않고 관측 한계만 기록한다.
- 별도 staging endpoint가 없으므로 개발 중 실제 전송 E2E를 production에 시도하면 동일 문제가 재발한다. staging은 별도 이슈와 승인 전까지 사용하지 않는다.

## 승인 요청 사항

1. production endpoint를 공통 plist 고정값에서 제거하고 `project.yml`의 Release configuration에만 주입하는 방향 승인
2. Debug·endpoint 미지정 구성은 runtime 분기 추가 없이 기존 resolver의 `nil` fail-closed 경로로 비활성화하는 방향 승인
3. payload에 build identifier를 추가하거나 기존 운영 행을 보정하지 않고 전송 차단과 관측 한계 문서화에 한정하는 범위 승인
4. production 네트워크 합성 요청 없이 unit test, resolved build setting과 Debug/Release built plist로 검증하는 방향 승인
5. 위 범위와 3단계 진행 구조 승인 후 구현계획서 `mydocs/plans/task_m010_479_impl.md` 작성 단계 진행 승인
