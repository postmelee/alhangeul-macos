# Task M010 #484 수행계획서

## 목적

v0.1.10 HostApp의 page SVG 기반 PDF 내보내기에서 한글 문항 본문 글꼴의 `ToUnicode` CMap이 누락돼 PDF 뷰어에 따라 텍스트 선택·검색·복사가 실패하거나 불안정해지는 회귀를 수정한다.

페이지를 bitmap으로 되돌리거나 수식을 이미지로 치환하지 않고, 현재 editor 상태와 page geometry, 한글·수식 시각 결과, 격리된 PDF renderer의 보안 경계를 유지하면서 Unicode text mapping을 검증 가능한 출력 계약으로 고정한다.

## 배경

Issue #455 작업은 사용자 PDF 내보내기를 HWP bytes와 native bitmap renderer 조합에서 현재 editor의 `pageCount`/`getPageSvg`와 `WKWebView.createPDF` 조합으로 전환했다. 이 경로는 v0.1.10에 포함됐고, 일반 인쇄와 PDF 저장이 `RhwpStudioPagePDFRenderer`를 공유한다. 기존 자동 검증은 영문 합성 SVG의 `PDFPage.string`과 page geometry를 확인하며, 실제 한글 글꼴 resource의 `ToUnicode` 존재 여부는 확인하지 않는다.

`rhwp` 공개 sample인 `3-11월_실전_통합_2022.hwp`를 v0.1.10으로 내보낸 PDF를 조사한 결과는 다음과 같다.

- source HWP SHA-256: `bc8bccbb954c337d813d1af96f4e3047242124c2f2939163e282634eb721accd`
- app PDF SHA-256: `0b5d64c4611555578a70f9b78540775f43f81a2886bda4e91d12db54154acdaf`
- app PDF: 21 page, `794 × 1123 pt`, 7,570,926 bytes, Quartz PDFContext 1.4
- app PDF font subset: 184개 중 `ToUnicode` 있음 79개, 없음 105개
- 한글 문항 본문의 `AppleSDGothicNeo` 계열 CID font subset: `uni=no`
- 비교용 Hancom PDF: 1,345,036 bytes, font 9개, 모두 `uni=yes`

app PDF의 21개 page에는 모두 text object가 있고 PDFKit의 page string과 rectangle selection도 생성된다. 1 page의 `문1` 영역은 한글 본문과 분수·근호 수식을 포함한 selection을 반환한다. 따라서 이 증상은 수식이어서 text layer가 없는 문제가 아니라, WebKit/Quartz가 생성한 일부 font subset의 Unicode mapping을 PDFKit이나 Poppler가 추론할 수 있어도 다른 viewer가 안정적으로 복원하지 못하는 상호운용성 결함이다.

현재 PDF HTML wrapper는 외부 resource 실행을 차단하기 위해 CSP에 `font-src 'none'`을 사용한다. 실제 page SVG의 원본 font를 격리 renderer가 읽지 못하면 시스템 fallback font로 해석될 수 있으며, 조사 PDF에서는 `AppleSDGothicNeo`가 사용됐다. 다만 CSP와 fallback이 `ToUnicode` 누락의 직접 원인인지는 font source·font format·WebKit PDF 출력 조합을 분리 측정한 뒤 확정해야 한다.

## 범위

포함:

- exact `devel`과 v0.1.10 기준으로 실제 한글·수식 page SVG, resolved font와 PDF font resource의 관계를 재현한다.
- `PDFPage.string` 성공과 `ToUnicode` 존재를 구분하는 text-layer 검증 계약을 정의한다.
- system fallback, bundled Unicode-capable font, font format과 `document.fonts.ready` 대기 여부를 격리된 WebKit PDF 변환에서 비교한다.
- 외부 network resource를 허용하지 않는 범위에서 PDF renderer가 필요한 bundled font만 결정적으로 로드하는 방식을 검토·구현한다.
- 한글 문항 본문, 수식, 문항 번호와 선택지를 선택·검색·복사할 수 있는지 PDFKit과 독립 PDF 도구로 검증한다.
- page count, media box, portrait/landscape, 현재 편집 상태, 일반 인쇄와 PDF 저장 공용 경로를 회귀 검증한다.
- font subset 개수, `ToUnicode` 비율, 출력 크기와 page별 중복을 전후 측정한다.
- 실제 공개 sample을 smoke fixture로 사용하고, CI에는 라이선스·크기를 고려한 최소 한글·수식 회귀 fixture 또는 합성 SVG를 추가한다.
- searchable/selectable PDF의 보장 범위와 잔여 viewer 차이를 architecture·사용자 문서에 사실대로 반영한다.

제외:

- Quick Look/Thumbnail bitmap renderer 변경
- 이미지·스캔 문서 OCR 또는 OCR text layer 생성
- HWP/HWPX serializer와 저장 기능 변경
- HostApp viewer/editor 화면의 기본 renderer 전환
- 전체 native PDF renderer 또는 전면적인 PDF post-processor 신규 구현
- 라이선스가 불명확한 원본 문서 글꼴 bundling
- bundled `rhwp-studio` minified asset 직접 수정
- 새 upstream ref sync, release, 서명, 공증 또는 배포 실행

## 설계 방향

1. `PDFPage.string`이나 `pdftotext`가 값을 반환한다는 사실만으로 searchable/selectable 계약을 통과시키지 않는다. 대표 한글을 그리는 PDF font resource의 `ToUnicode` CMap과 영역 selection 결과를 함께 확인한다.
2. page SVG가 가진 Unicode 문자열을 진실 원천으로 유지한다. 수식을 raster image로 바꾸거나 PDF 전체에 OCR을 덧씌우는 방식은 사용하지 않는다.
3. 첫 후보는 격리 renderer 안에서 승인된 bundled font만 결정적으로 준비한 뒤 `document.fonts.ready`를 기다리고 `createPDF`를 호출하는 방식이다. `font-src data:` 또는 bundle 전용 custom scheme 등 후보별 보안·메모리·캐시 비용을 Stage 1에서 비교한다.
4. 외부 `http`, `https`, `file`, 임의 `blob` font와 navigation은 계속 차단한다. font 허용 범위가 바뀌면 기존 CSP·navigation·loopback request 차단 테스트를 같은 단계에서 보강한다.
5. fallback font를 바꾸면 글자 폭, baseline, 줄바꿈과 수식 정렬이 달라질 수 있다. text mapping 개선은 대표 page raster diff와 page geometry가 허용 범위 안일 때만 채택한다.
6. 페이지별 `createPDF`와 PDFKit merge가 21 page에서 font subset 184개를 만드는 현상은 원인과 성능 영향을 측정한다. subset deduplication 자체는 text mapping 수정에 필요할 때만 구현 범위에 포함한다.
7. WebKit/Quartz만으로 유효한 `ToUnicode`를 안정적으로 만들 수 없으면 불완전한 우회 구현을 병합하지 않는다. Unicode text-run overlay나 제한된 PDF post-processing 후보와 별도 범위를 보고하고 작업지시자 승인 후 계획을 보정한다.
8. production code에 외부 CLI 의존을 추가하지 않는다. `pdffonts`, `pdftotext`, `pdfinfo`, `pdftoppm`은 통합 검증 도구로 사용하고, 자동 단위 검증은 PDFKit/CGPDF 기반 test helper를 우선한다.

## 잠정 단계

1. Stage 1: exact `devel`과 대표 HWP/PDF에서 page SVG font, WebKit resolved font, PDF font resource와 `ToUnicode` 누락 조건을 재현하고, bundled font·font readiness·CSP 후보별 최소 실험으로 원인과 수정 계약을 확정한다.
2. Stage 2: 승인된 격리 font-loading·PDF 생성 보정을 구현하고, 한글·수식 selection과 `ToUnicode`, CSP·navigation 차단을 검증하는 HostAppTests 회귀를 추가한다.
3. Stage 3: `3-11월_실전_통합_2022.hwp`와 대표 HWPX를 Debug app에서 내보내 page count·geometry·raster·텍스트·font resource·파일 크기·인쇄 회귀와 원본 hash 불변을 통합 검증한다.
4. Stage 4: PDF text mapping ownership, 검증 기준과 잔여 viewer 제한을 architecture·사용자 문서에 반영하고 전체 tests, build, asset·dependency boundary를 최종 검증한다.

각 단계의 산출물·검증·커밋 경계는 수행계획 승인 뒤 구현계획서에서 확정한다. Stage 1에서 WebKit/Quartz 경로만으로 완료 조건을 충족할 수 없다고 판정하면 Stage 2 구현을 시작하지 않고 대안 범위와 계획 보정 승인을 요청한다.

## 리스크

- `ToUnicode` 존재는 Unicode 복사·검색의 필요조건이지만 reading order, grapheme 결합과 선택 UX 전체를 자동 보장하지 않는다. 영역 selection과 실제 viewer smoke를 함께 유지해야 한다.
- system fallback을 bundled font로 바꾸면 문서 원본 font와 다른 metric으로 인해 줄바꿈, 표 높이, 수식 baseline과 page overflow가 달라질 수 있다.
- 현재 `font-src 'none'`은 Issue #455 작업에서 외부 resource를 차단한 보안 경계다. font source 허용을 넓히면 network·file 접근이나 embedded font payload 공격 표면이 생기지 않도록 scheme과 MIME, size를 제한해야 한다.
- WOFF2, TrueType, CFF와 system font는 WebKit/Quartz에서 서로 다른 PDF font dictionary를 만들 수 있다. 한 환경의 `uni=yes`만 보고 모든 macOS와 viewer를 보장하지 않는다.
- 페이지별 WebKit PDF를 PDFKit으로 합치는 구조는 font subset 중복과 큰 파일을 만든다. single-document 변환은 subset을 줄일 수 있지만 혼합 page size와 기존 page-by-page 오류 격리 계약을 깨뜨릴 수 있다.
- 실제 sample은 5 MB 이상이고 외부 `rhwp` repository가 소유하므로 그대로 test asset에 복제하면 저장소 크기와 라이선스 문제가 생길 수 있다. 최소 fixture와 수동 smoke 역할을 분리해야 한다.
- 일부 그래프·스캔·embedded image 안의 글자는 PDF text object가 아니므로 본 타스크 완료 후에도 선택되지 않는다. 이를 한글 본문 mapping 실패와 구분해 안내해야 한다.
- WebKit/Quartz가 필요한 CMap을 제어할 API를 제공하지 않으면 production-safe 수정이 제한될 수 있다. 이 경우 투명 text overlay나 PDF post-processing은 별도 정확도·보안 범위 승인이 필요하다.

## 승인 요청 사항

- 위 포함·제외 범위와 4단계 잠정 진행 순서를 수행계획으로 승인받는다.
- Stage 1에서는 source나 production asset을 바꾸기 전에 대표 SVG와 synthetic Korean/math SVG로 font source·format·readiness·CSP 조합을 분리 측정한다.
- 수정 우선순위는 `결정적 bundled font 준비와 WebKit PDF 유지`로 두되, visual fidelity와 보안 경계를 통과하지 못하면 구현을 강행하지 않고 대안 승인을 요청한다.
- 실제 `3-11월_실전_통합_2022.hwp`는 사용자 파일이 아니라 공개 sample의 읽기 전용 복사본으로 smoke하고, repository 포함 여부는 Stage 1에서 라이선스·크기 검토 후 결정한다.
- 수행계획 승인 후에만 구현계획서 `mydocs/plans/task_m010_484_impl.md`를 작성하고, 구현계획 승인 전에는 제품 source·test·manual을 변경하지 않는다.
