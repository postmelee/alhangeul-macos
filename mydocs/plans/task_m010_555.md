## 1. 목적

알한글 제품 페이지 방문자가 개발 소식과 사용 사례를 한곳에서 볼 수 있도록, `@postmelee`의 Threads 게시물 중 실제 `알한글` 주제 태그가 붙은 글을 수집해 소식 카드와 전체 목록으로 제공한다. 이후 X를 추가할 수 있도록 저장 데이터에 플랫폼 구분을 둔다.

## 2. 배경

- 작업지시자는 Threads 수집과 소식 카드 화면부터 시작하고 X는 후속 연동으로 두는 방향을 승인했다. 예시 원문은 [Threads 공유 링크](https://www.threads.com/share/GUInSJlPj/)다.
- 제품 사이트는 `docs/index.html`, `docs/styles.css`, `docs/script.js`를 사용하는 정적 GitHub Pages이며 업데이트와 문의 페이지가 별도로 있다.
- 최신 통합 브랜치에는 #523 업데이트 화면 보강이 반영되어 있다. 공통 스타일을 수정할 때 해당 화면의 회귀를 확인해야 한다.
- `.github/workflows/pages-docs-deploy.yml`은 `main`의 `docs/**` 변경과 수동 실행으로 배포하며, 현재 공개 appcast를 내려받아 검증·보존한다. 릴리스 배포와 `pages-deploy` 동시 실행 제어를 공유한다.
- 기존 랜딩페이지 #135 및 제품 페이지 보강 #430과 같은 `v0.1` 분류로 이슈를 등록했다.
- 본인 API의 태그 선별과 공개 oEmbed·로컬 렌더링을 확인했다. [Stage 1 조사 기록](../tech/task_m010_555.md)에 근거를 정리했다. 자동 URL 선별과 공개 표시를 조합한 전체 사용 사례에 대한 Meta의 별도 확인은 공개 활성화 전에 남은 조건이다.

## 3. 범위

### 포함

- 본인 계정 인증, 필요한 최소 조회 권한, 토큰 보관·갱신·재인증 절차 확인.
- 작성자와 실제 주제 태그를 기준으로 하는 Threads 게시물 수집, 초기 과거 글 조회와 정기 동기화.
- 플랫폼·원문 링크와 목록 갱신·표시 만료 시각의 공통 저장 형식. 본문·미디어 사본은 공개 JSON에 넣지 않는다.

- 홈의 최신 소식 카드 기본 3개와 `docs/news/index.html`의 최신순 전체 소식 목록, 사이트 내비게이션 연결.
- 공식 임베드의 본문·날짜·미디어 표시와 원문 링크, 빈 목록·만료·데이터/임베드 로딩 실패 상태.
- 수집·데이터 검증 스크립트, 필요한 workflow 연결, 운영 안내와 로컬 화면 검증.

## 4. 설계 방향

### 수집과 화면의 분리

인증된 실행 환경의 태그 선별 → 인증 없는 공개 oEmbed 검사 → 링크 전용 JSON → 공식 임베드 순서로 구성한다. 방문자 브라우저는 사용자 토큰 없이 Threads의 공식 script/iframe을 읽는다. 공통 키는 플랫폼과 정규 원문 참조이며 스키마 버전을 포함한다.

### 실제 태그와 작성자 확인

본문 문자열 포함 여부를 주제 태그 판정으로 대체하지 않는다. 연결 계정의 ID와 사용자명을 확인하고, 실제 응답의 태그·작성자·재게시물 구분 및 페이지네이션 동작을 검증한다. 필요한 필드를 얻지 못하면 추정해 수집하지 않고 판별 불가로 기록한다. 예시 글을 실데이터 수용 검증에 포함한다.

### 동기화와 저장

- 초기에는 API가 제공하는 범위의 과거 글을 수집하고 범위·누락 가능성을 명시한다. 정기 실행 간격은 수 시간 단위를 후보로 삼되 호출 제한과 계정 규모에 따라 구현계획에서 정한다.
- 새 데이터 전체를 검증한 후 교체한다. 일부 페이지 실패나 인증 실패로 기존 목록이 빈 배열로 덮이지 않게 한다.
- 완전한 현재 목록에서 미관찰되거나 태그가 제거된 글은 새 표시 목록에 포함하지 않는다. 이를 원문의 영구 삭제로 단정하지 않는다. 일부 페이지 실패 때는 새 목록 전체를 게시하지 않는다.
- 표시용 데이터와 인증·운영 상태를 분리한다. 공개 JSON에는 허용한 필드만 기록하고 API 원본 응답이나 오류 전문을 그대로 저장하지 않는다.
- 미디어 URL의 만료, 갱신, 표시 실패와 데이터 보관 조건을 확인한다. 다운로드·영구 복제를 전제로 하지 않는다.

### 정기 실행과 Pages 연결

GitHub Actions 6시간 정기 실행을 사용한다. 매 배포에서 Threads 원본을 다시 조회하여 실행별 snapshot을 생성한다. 별도 Git 데이터 브랜치나 장기 캐시를 만들지 않는다. 48시간 표시 기한, Pages artifact 1일 보존과 명시 제거 절차를 보정안에 포함한다. 토큰은 운영자가 갱신하고 secret을 교체한다.

기존 Pages는 release 및 docs-only 배포 때 전체 사이트를 조립하므로, 어느 경로에서 재배포해도 소식이 이전 버전으로 되돌아가지 않는 데이터 원천이 필요하다. 공개 반영은 기존 appcast 보존, 배포 직렬화 및 `main` 기준을 지키는 방향으로 설계한다. 정기 수집 구현과 자동 공개 반영 활성화의 승인 범위는 구분한다.

### 화면

기존 사이트의 색상·서체·여백을 재사용하고 소식 전용 스타일 범위를 둔다. 홈은 최신 3개, 전체 목록은 12개씩 표시한다. 게시물 내부 디자인은 공식 임베드가 담당하며 본문을 추출·재구성하지 않는다. 데이터가 없으면 실제 글을 꾸며 넣지 않고 빈 상태를 표시한다. 만료·임베드 차단 때는 안내와 원문 링크를 제공한다.

## 7. 검증 계획

- API: 실제 계정 ID/작성자, 예시 글, 주제 태그, 페이지네이션과 과거 글 범위, 미디어 및 재게시물 구분을 확인한다. 토큰과 인증 응답을 보고서에 남기지 않는다.
- 데이터: 대상 태그·비대상 태그·본문 키워드만 있는 글·다른 작성자·재게시·중복·수정·태그 제거·확정된 삭제·조회 실패를 구분하는 fixture로 검증한다.
- 실패 복구: 부분 페이지 오류, 속도 제한, 인증 만료, 잘못된 스키마와 URL에서 기존 정상 데이터가 보존되는지 확인한다. 최근 목록 부재가 삭제로 처리되지 않는지도 검증한다.
- 화면: 데스크톱 1440px, 모바일 390px, 좁은 화면 320px에서 넘침·줄바꿈·긴 본문·이미지 실패를 확인한다. 키보드 포커스와 링크 이름, 로딩/빈 상태/오류 안내를 점검한다.
- 보안 경계: API 입력의 HTML 실행 방지, URL 검증, 공개 JSON·로그·브라우저 요청의 토큰 비노출을 확인한다.
- Pages: 프로젝트 하위 경로의 상대 링크, 홈·업데이트·문의·다운로드 및 기존 복사 버튼 동작, 콘솔 오류를 확인한다. `scripts/ci/update-release-version-notices.sh --updates-dir docs/updates --check`를 수행한다.
- 조립: `scripts/ci/prepare-pages-artifact.sh`로 `build.noindex/task555/` 아래 조립하고 입력/출력 appcast의 bytes를 비교한다. release 및 docs-only 재조립에서 소식 데이터 보존을 확인한다.
- 문서와 변경 검증: `git diff --check`, JSON 및 스크립트 검사, 변경 유형에 따른 기존 CI 검사를 수행한다.
- 실제 API 검증, fixture 검증, 로컬 화면 검증, 공개 운영 검증을 보고서에서 구분한다. 계정 연결 전에는 실데이터 수집 완료로 기록하지 않는다.

## 9. 승인 요청 사항
