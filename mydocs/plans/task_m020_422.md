# Task M020 #422 수행계획서

## 목적

upstream `edwardkim/rhwp v0.7.19`를 current `devel`에 full sync하고, native core와 bundled `rhwp-studio`를 stable release tag와 resolved commit `f137b4c9468eaff5bb43e25108e9c9d39a2ed15b`로 정렬한다.

자동 sync PR #421 후보를 current RustBridge source와 앱 세 target 기준으로 다시 검증해 기존 15개 C ABI, production CoreGraphics 기본 경로, Skia internal opt-in 진단 경로를 보존한다. 검증된 provenance와 사용자 영향 경계를 다음 `v0.1.8 (14)` public release 작업의 확정 입력으로 넘긴다.

## 배경

Task #418 작업과 PR #420 반영으로 현재 `devel`의 native core와 bundled studio는 `v0.7.18` / `93862a4e16df59834ebce46d91e948cd739208e9`에 고정돼 있다. upstream은 2026년 7월 17일 stable `v0.7.19`를 공개했으며 target commit은 `f137b4c9468eaff5bb43e25108e9c9d39a2ed15b`다.

`v0.7.19`는 `v0.7.18` 이후 55개 PR과 578개 커밋을 포함한다. 저장 지오메트리, 표 페이지네이션, BinData 지연 로딩, export 결정성, HML parser/serializer, bundled studio, 글꼴 자산과 CanvasKit 경로가 변경됐으며 upstream impact detector는 viewer/WASM/core 영향 경로 208개를 보고했다.

자동 full sync PR #421 후보는 current `devel` merge commit `9ca9c488937bdda00fb045eb82b1ab2ecb31aa83`에서 생성됐다. head는 `ddcc0329ae1b6bef7c6dacb51ee8375de3b6d42c`이고 GitHub의 merge 상태는 `CLEAN`, PR CI의 macOS validation을 포함한 네 check는 모두 성공했다. 따라서 Task #418 당시 stale automation 후보와 달리 재실행 필요성은 현재 확인되지 않지만, 자동 후보의 녹색 CI만으로 public release 입력을 확정하지 않고 local artifact, ABI, 앱 runtime과 visual 회귀를 별도로 검증한다.

## 설계 방향

1. Stable dependency는 release tag `v0.7.19`와 resolved commit `f137b4c9468eaff5bb43e25108e9c9d39a2ed15b`의 쌍으로 고정하며 floating ref를 허용하지 않는다.
2. PR #421 후보는 생성 증거와 동기화 diff로 사용한다. Stage 1에서 current base와 동일함을 다시 확인한 뒤 exact automation commit을 Task branch에 통합하고, PR #421 자체는 Task PR merge 후 superseded 처리한다.
3. automation이 생성한 artifact metadata를 그대로 신뢰하지 않는다. current RustBridge source에서 native artifact와 lock을 재생성하고 generated header 및 `rhwp-ffi-symbols.txt`의 15개 symbol과 대조한다.
4. native core와 bundled studio는 같은 tag/commit을 사용한다. manifest의 `source_cargo_lock_sha256`와 hashed entrypoint를 함께 검증한다.
5. production renderer 기본값은 CoreGraphics로 유지한다. Skia는 DEBUG/internal opt-in 진단 경로로만 측정하며 `KTX.hwp`의 known delta와 신규 회귀를 분리한다.
6. upstream HML 지원은 이번 동기화에 포함되더라도 macOS document type/open handoff가 없으므로 public app 기능으로 표현하지 않는다.
7. Issue #409 작업 전에는 external linked image 제품 지원 완료를 주장하지 않는다. signed HOP exact UTI 검증은 다음 public release의 blocking manual gate로 유지한다.
8. public release 변경은 이 타스크에서 수행하지 않는다. 최종 보고서 승인과 Task PR merge 뒤 별도 Release Operations 이슈로 시작한다.

## 리스크

- `v0.7.19`는 patch release지만 core/studio 영향 경로가 넓다. compile 성공만으로 저장 지오메트리, 표 분할, 글꼴과 후반 페이지 회귀가 없다고 판단할 수 없다.
- BinData 지연 로딩은 메모리를 개선하지만 external/embedded image lifetime과 native bridge 사용 방식에 영향을 줄 수 있어 대표 이미지 문서를 다시 확인해야 한다.
- bundled studio의 font root와 NotoSansKR asset이 변경됐다. WKWebView 로딩 성공과 실제 글꼴 표시를 분리해 확인해야 한다.
- static archive hash와 size는 toolchain 및 build path에 민감하다. strict metadata 차이가 생기면 source/ABI 실패와 환경 차이를 분리해 기록한다.
- automation PR #421 후보는 현재 clean이지만 Stage 1 전에 `devel`이 전진하면 freshness와 충돌 여부를 다시 판정해야 한다.
- visual harness는 macOS sandbox readiness와 설치·등록 상태 영향을 받을 수 있다. 환경 실패와 renderer regression을 구분한다.
- upstream HML과 MessageChannel 기능을 알한글의 공개 지원 기능으로 과장하면 실제 macOS integration surface와 불일치한다.
- public release 직전 범위를 넓히면 회귀 원인과 release blocker 판정이 어려워진다. 신규 제품 기능은 별도 이슈로 유지한다.

1. Issue #422 작업을 `v0.7.19` full sync와 public release 전 회귀 검증의 추적 이슈로 사용한다.
2. 기준 브랜치는 `devel`, 분리 worktree `/Users/melee/Documents/projects/rhwp-mac-task422`의 작업 브랜치는 `local/task422`로 진행한다.
3. current base가 유지되면 PR #421 exact automation candidate를 통합 입력으로 사용하고, native artifact와 lock은 current RustBridge에서 재생성한다.
4. 15개 C ABI, core/studio 동일 provenance, 앱 세 target과 representative visual result를 필수 gate로 둔다.
5. 위 5개 잠정 단계와 public release 분리 원칙을 승인한다.

수행계획서 승인 전에는 구현계획서 작성, core/studio 파일 변경, PR #421 상태 변경과 public release 작업을 진행하지 않는다.
