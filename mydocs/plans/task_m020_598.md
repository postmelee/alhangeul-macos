## 목적

공식 upstream 릴리스 전에는 기존 core와 Studio를 유지하면서 앱의 설치 글꼴 공급을 진단하고 회귀 검증 도구와 인계 자료를 준비한다. 이후 작업지시자가 공식 릴리스 반영 및 알한글 새 릴리스를 요청하면 동일 입력·명령·판정 기준으로 검증을 이어갈 수 있게 한다.

## 배경

사용자의 `~/Library/Fonts` 포함 요청은 후속 설명과 [upstream #8371](https://github.com/edwardkim/rhwp/issues/8371)을 통해 HFT 원본 글꼴에 대응하는 설치 OTF/TTF 선택 문제로 구체화됐다. [PR #8397](https://github.com/edwardkim/rhwp/pull/8397)은 2026-10-31 devel에 병합됐다. 원본 대응 OTF/TTF 우선 공급, 측정·출력 일치, 감지 후 재조판 연결을 다루지만 실제 알한글의 macOS 설치 글꼴 공급 검증을 대신하지 않는다.

앱은 사용자 글꼴 폴더를 이미 탐색하고 CoreText의 활성 글꼴을 열거한다. 설치 글꼴의 별칭은 family/full/PostScript 이름에서 생성하지만 관리 글꼴은 파일 name table의 여러 이름을 사용한다. 설치 스타일은 알려진 문자열만 변환하므로 `Book` 또는 빈 스타일은 제외된다. OTF/CFF 검사와 변경 알림 전달은 이미 있다. 이 항목들은 조사 후보이며 제보의 확정 원인으로 표시하지 않는다.

사전 조사에서 provider/bootstrap Node 테스트 22개가 통과했다. 이는 공급 계약의 일부 검증이고 HFT 원본 선택·재조판·최종 제품 수용 성공은 아니다. 실제 재현 글꼴·문서 확보 여부는 Stage 1에서 확인한다.

포함:

제외:

- 공식 릴리스 전 core pin, Rust dependency, Studio/WASM bundle, 생성 matcher 갱신 또는 upstream 패치 선반영.
- 앱에 별도 HFT 치환표·OTF 우선 resolver 구현, HFT 파일 해석·변환, TTC/가변 지원 확대.

## 설계 방향

### 공급 진단과 실패 분리

문서 요청 이름 → CoreText metadata → adapter 후보 → 검증 bytes → 소비자 선택의 각 경계를 별도로 기록한다. 이름, 스타일, opaque ID, 검증 hash, 실패 코드, 공급 세대와 소비자 종류를 근거로 사용한다. 원본 경로·bookmark·상용 bytes를 공개 결과에 기록하지 않는다. UI에 이름이 보이거나 fallback이 그려졌다는 이유만으로 성공 처리하지 않는다.

설치 글꼴 metadata는 지연 bytes 읽기 정책을 유지한다. 진단 편의를 위해 전체 설치 글꼴 파일을 선읽거나 이름 유사성만으로 무조건 alias를 추가하지 않는다. OTF/CFF와 TTF는 실제 signature로 구분하고 메타데이터 일치·스타일·글리프 공급을 각각 판정한다.

### 기존 구조 재사용

`InstalledFontSystem`, `StudioFontSupply`, `StudioFontProviderScript`, `StudioFontSession`과 기존 Node/Swift/실제 Mac probe를 재사용한다. Stage 1에서 가장 작은 확장 지점을 정한다. 관리 보관함 우선순위와 동명 충돌 거부를 임의 해제하지 않는다. 변경 알림 전달 성공과 upstream 문서 재조판 성공을 분리한다.

Native는 layer tree 생성 이후 요청을 수집하는 현재 bridge와 조판 전 글꼴 공급을 요구하는 upstream 계약의 차이를 문서화한다. 해당 구조 변경 및 실제 연결은 공식 릴리스 이후 항목으로 남긴다.

### 후속 작업 재개 계약

[공식 릴리스 재개 인계](../tech/task_m020_598_release_handoff.md)를 후속 진입점으로 작성했다. 기준 SHA/lock, 입력 provenance·필요 자산, 실행 명령, 결과 위치, 현재 실패와 미검증, 공식 릴리스 후 통과 조건을 포함한다. 최종 보고·게시 승인 후 최종 보고서와 이슈·PR에도 이 진입점을 연결한다.

후속 순서는 공식 release tag에 #8397 수정 포함 확인 → core/Studio/WASM/matcher 동기화 → 이 타스크 회귀 재실행 → 실제 앱 본문·PDF·인쇄·Quick Look·Thumbnail 검증 → 별도 릴리스 운영 타스크의 서명·공증·설치·업데이트·공개 gate다. 다음 릴리스에 수정이 반드시 포함된다고 가정하지 않는다. 필요한 자산 또는 API가 없으면 미검증/후속 필요로 유지한다.

- 별칭: 한글 요청·영문 family·다국어 name table, installed/managed 비교 및 오매칭 거부.

## 리스크

- 실제 문제 글꼴을 확보하지 못하면 제보 자체 재현은 확정할 수 없다. 합성 데이터로 공급 계약만 검증한다.
- 한글 별칭·스타일 보완은 잘못된 매칭, 읽기 비용 증가 또는 기존 충돌 정책 변경을 일으킬 수 있어 재현 근거 없이 제품 로직을 확대하지 않는다.
- upstream 새 릴리스의 API/ABI·bridge 계약 변화로 후속 추가 작업이 생길 수 있다. 이번 준비를 연결 완료로 보고하지 않는다.
- #594 작업과 HostApp 공통 파일이 겹칠 가능성이 있다. 최신 origin/devel의 별도 worktree에서 작업하며 다른 타스크의 미통합 변경은 복사하지 않는다. 최종 PR 전 충돌을 재확인한다.
- 판정에 필요한 큰 PDF·상용 글꼴은 저장소에 무조건 추가하지 않는다. 라이선스와 provenance를 확인하고 필요한 입력과 재생성 명령을 기록한다.
