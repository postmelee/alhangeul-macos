# Task #516 수행계획서

## 목적

파일 없이 실행한 알한글에서 새 문서에 입력한 내용을 HWP/HWPX로 저장할 수 있게 한다. 편집기의 새 문서와 HostApp의 문서 상태를 동기화하여 첫 저장, 후속 저장, PDF 내보내기, 창 닫기·앱 종료 시 저장 확인을 정상화한다. 별도 원인인 Word(.doc)·HTML 내보내기 연결 누락도 같은 이슈에서 단계별로 수정한다.

- GitHub Issue: [#516](https://github.com/postmelee/alhangeul-macos/issues/516)
- 제목: 새 문서 저장 실패와 Word·HTML 내보내기 연결 누락 수정
- 마일스톤: `v0.1` / 문서 코드 `m010`
- 라벨: `bug`, `area:viewer-app` — 기존 HostApp 문서 처리 기능 결함
- 작업 브랜치: `local/task516`
- 대상 통합 브랜치: `devel`
- 시작 기준: `origin/devel`의 `56fe1ca6afda3baba1975a3cc5fda53fcf58f944`
- 작업 위치: `build.noindex/worktrees/task516` 분리 worktree. 메인 worktree의 `local/task513` 변경과 미병합 커밋을 유지한다.
- 분석 기준 공개판: `v0.1.11`, bundled `rhwp-studio` / core `v0.8.6`

사용자가 Apple M1 MacBook / macOS Tahoe 26.3에서 저장 실패와 Word 내보내기 실패를 제보했다. 작업지시자는 파일 없이 앱 실행 → `ㅇㅇ` 입력 → 저장에서 “저장할 문서가 없습니다.”를 재현했다. 특정 하드웨어나 IME에 국한되는지 입증된 상태는 아니며, 현재 코드에서는 새 문서 상태 불일치로 설명된다.

HostApp은 파일 없이 시작하면 문서 payload가 nil인 상태로 WebView를 연다. 편집기는 자체적으로 빈 문서를 만들지만 HostApp에 등록되지 않는다. Coordinator의 저장·다른 이름 저장·PDF 내보내기 검사와 편집 알림 처리에서는 문서가 없는 것으로 판단한다. Word(.doc) 내보내기는 HTML 기반 Blob 다운로드를 사용하며, HostApp의 native command 또는 다운로드 저장 처리와 연결되어 있지 않다. Word·HTML의 구체적인 실행 증상은 Stage 1에서 확인한다.

관련 선행 작업은 #142, #144, #243, #455, #456 이며, 원본 보호 정책의 회귀 확인 대상은 #480, #482, #497 이다.

## 범위

포함:

- 자동 생성된 빈 문서와 메뉴에서 생성·교체한 새 문서의 준비 완료, 문서 식별자, 파일명, source URL, dirty state 동기화
- 새 문서 첫 HWP/HWPX 저장, 다른 이름 저장, 후속 Command+S, 저장 완료 통지와 최근 문서 갱신
- 저장 취소·실패 및 저장 도중 문서 교체에 대한 상태 보존
- 새 문서의 PDF 내보내기, native 도구 버튼 활성화, 창 닫기·앱 종료 시 저장 확인
- Word(.doc)·HTML 내보내기의 native 파일 저장 연결, 취소·오류 처리 및 편집 내용 보존 검증
- 기존 문서와 암호 문서·HWP3 저장 보호 회귀 검증, 관련 문서 갱신

제외:

- 실제 DOC 바이너리·DOCX exporter 신규 구현
- upstream core 기능 변경, core 버전 갱신, bundled asset 직접 패치
- native viewer/editor 전환 및 autosave/recovery 전면 개편
- 서명·공증·public release 실행

## 설계 방향

1. 파일의 원본 bytes 유무와 현재 편집 문서의 존재를 구분한다. nil 검사를 제거하는 우회 대신, HostApp이 새 문서의 준비 완료와 교체를 명시적으로 인식하도록 한다. 현재 고정된 editor API와 이벤트가 제공하는 계약을 조사한 뒤 상태 모델과 연결 방식을 구현계획에서 구체화한다.
2. 새 문서를 앱에 등록할 때 편집기를 재로드하여 이미 입력한 내용을 잃지 않아야 한다. 문서 세대와 native load identity를 정리하고, 이전 문서의 지연 응답이 새 세션의 저장·dirty 상태를 변경하지 못하게 한다.
3. 기존 파일에서 새 문서로 전환하면 이전 source URL과 보호 상태를 이어받지 않는다. 새 문서임이 확인된 상태와 암호 문서·형식 미확정 상태를 구분하며, 알 수 없는 상태를 임의로 평문으로 분류하지 않는다.
4. 첫 저장은 native 저장 패널과 기존 HWP/HWPX exporter·payload 검증·atomic write 계약을 사용한다. 저장 성공 뒤 파일명, source URL, 저장 형식, payload 또는 세션 metadata, native/editor dirty 상태를 함께 갱신한다. 취소·실패 시에는 편집 내용을 유지한다.
5. PDF 및 도구 버튼의 문서 존재 판정을 같은 상태 계약으로 맞춘다. 종료 확인은 native 문서의 dirty state와 editor 저장 완료 통지를 일관되게 반영한다.
6. Word·HTML은 upstream이 제공하는 HTML 기반 출력 의미를 유지한다. 고정된 API의 출력 접근 가능성과 WKDownload 지원을 비교하여 native bridge 또는 전용 다운로드 처리 중 검증 가능한 경로를 선택한다. 출력 형식과 파일 확장자·저장 패널이 일치해야 하며, 내보내기 성공이 HWP/HWPX 원본 저장 완료로 취급되어서는 안 된다.

## 검증 계획

현재 문서 준비 단계에서는 `git diff --check`, 본문 참조 형식, 이슈 번호·마일스톤·9개 표준 섹션·오늘할일 행을 확인한다. 제품 코드 변경과 앱 실행 검증은 아직 수행하지 않는다.

구현 단계에서는 변경 전 Swift/macOS 및 빌드 매뉴얼을 확인하고, 분리 worktree의 `Rhwp.xcframework` 등 생성 의존성을 준비한다. 의존성 준비 실패와 코드 회귀를 구분한다.

기본 검증 명령은 다음과 같다. target 설정을 바꾸면 먼저 `xcodegen generate`를 수행한다.

```bash
./scripts/check-no-appkit.sh
scripts/verify-rhwp-studio-assets.sh
xcodebuild -project Alhangeul.xcodeproj -scheme HostAppTests \
  -configuration Debug -derivedDataPath build.noindex/task516/DerivedDataTests \
  CODE_SIGNING_ALLOWED=NO test
xcodebuild -project Alhangeul.xcodeproj -scheme HostApp \
  -configuration Debug -derivedDataPath build.noindex/task516/DerivedData \
  CODE_SIGNING_ALLOWED=NO build
```

주요 동작 검증:

- 파일 없이 실행 → `ㅇㅇ` 입력 → HWP/HWPX 첫 저장 → 재열기에서 입력 보존
- 각 형식으로 첫 저장한 뒤 재편집·Command+S가 같은 경로·형식을 유지하는지 확인
- 저장 패널 취소·쓰기 실패·저장 중 문서 교체에서 내용, dirty state, 원본 보존 확인
- 문서 교체 통지가 늦게 도착하거나 SwiftUI가 갱신되어도 새 문서가 재로드되지 않는지 확인
- 편집 문서 창 닫기와 앱 종료에서 저장·취소·버리기 및 저장 실패 후 창 유지 확인
- 새 문서 PDF 생성 후 한글 내용과 페이지 수 확인, 상단 도구 버튼 상태 확인
- 기존 파일 → 새 문서 전환 후 이전 원본의 bytes/hash가 바뀌지 않는지 확인
- 새 문서·기존 문서의 Word(.doc)/HTML 출력에서 현재 텍스트와 대표 서식 확인; Word 등 사용 가능한 호환 앱에서 열기 결과와 실행 환경 기록
- Word/HTML 내보내기 후 원본 URL·형식과 dirty 상태 유지 확인
- 기존 HWP/HWPX, 암호 문서 평문 복사본, HWP3 변환 복사본 정책 및 Sandbox 저장 경로 회귀 확인

HostApp smoke 산출물은 `build.noindex/`에 둔다. Quick Look/Thumbnail 등록이 필요해지는 경우에는 표준 smoke 절차와 종료 시 등록 해제를 따른다.

## 리스크

- 새 문서 등록을 기존 파일 로드로 처리하면 WebView 재로드로 입력 내용이 사라질 수 있다.
- 기존 원본 URL·보호 상태가 새 문서에 남으면 첫 저장이 이전 파일을 덮어쓸 수 있다.
- editor와 HostApp의 문서 세대가 다르면 지연된 저장 응답이 다른 문서의 dirty state를 해제할 수 있다.
- 내보내기를 원본 저장 완료로 오인하면 변경 내용이 저장되지 않았는데 종료 확인이 사라질 수 있다.
- Word(.doc)는 HTML 기반 호환 형식이므로 DOCX 또는 binary DOC의 표현 능력을 약속하지 않는다. 호환 앱이 없으면 파일 구조 확인과 실제 Word 열기 검증의 차이를 기록한다.
- 분리 worktree에는 원격 devel에 아직 없는 Task #513 후속 커밋을 포함하지 않는다. 이후 통합 시 같은 날짜의 오늘할일 문서가 충돌하면 양쪽 작업 기록을 보존하여 합친다.
