## 배경

최신 공개 앱 릴리즈는 `v0.1.6`이며, GitHub Release는 `Alhangeul v0.1.6 (rhwp v0.7.16)`로 공개되어 있다. upstream `rhwp` 최신 공개 릴리즈는 `v0.7.17`이고, PR #369가 `devel`에 merge되면서 `rhwp-core.lock`과 bundled `rhwp-studio` manifest가 모두 `v0.7.17` / `03351190ec35436e58cbfee0aa9278a8fdc04a59` 기준으로 맞춰졌다.

또한 PR #377에서 `rhwp Upstream Sync PR` workflow가 `devel` 기준 current 판정과 merge 완료 automation branch cleanup 후보 구분을 하도록 보강되었다. 이 작업 이후에는 release execution issue에서 source metadata, release communication, workflow default, 검증 기록을 `0.1.7 (13)`과 `rhwp v0.7.17` 기준으로 정렬하면 된다.

현재 source plist version/build는 HostApp, Quick Look, Thumbnail 모두 `0.1.6 (12)`이고, release rehearsal/publish workflow default도 `0.1.6`, `v0.1.5`, `v0.7.16` 기준에 머물러 있다. Cask source는 `0.1.4` 기준이므로 public DMG SHA256 확정 후 별도 gate에서 갱신 여부를 확인한다.

## 범위

포함:

- HostApp, Quick Look, Thumbnail extension plist version을 `0.1.7 (13)`로 갱신
- `Release Rehearsal DMG`, `Release Publish DMG` workflow 기본 입력을 `0.1.7`, `v0.1.6`, `v0.7.17` 기준으로 갱신
- `mydocs/release/v0.1.7.md` release record 초안 작성
- `docs/updates/v0.1.7.html`, `docs/updates/index.html`, README 최신 공개 릴리즈 요약 정렬
- `v0.1.6..candidate` 범위의 포함 PR 분석과 release delta checklist 작성
- source preflight, rehearsal, pre-public signed/notarized draft DMG smoke, official stable publish, Pages/Sparkle, Homebrew gate 결과 기록

제외:

- upstream `rhwp` 수정
- unreleased `rhwp` commit pin 적용
- Developer ID credential, notary credential, Sparkle private key, GitHub token 값 기록
- public publish, GitHub Release 게시, Pages/Sparkle 갱신, Homebrew tap 반영을 승인 gate 없이 실행
- 제품 기능 구현 또는 renderer parity 개선 자체

## 설계 방향

릴리즈 실행 순서는 `mydocs/manual/public_release_runbook.md`를 우선한다. #378은 제품 기능 구현 이슈가 아니라 release execution 이슈이므로, source identity, release communication, 배포 gate를 분리해 기록한다.

1. release candidate source를 `0.1.7 (13)`과 `rhwp v0.7.17` provenance 기준으로 정렬한다.
2. `v0.1.6` 이후 포함 PR을 사용자-facing, upstream sync, 운영/배포, 문서-only로 분류하고 공개 release note에는 사용자-facing 변화만 주요 요약으로 반영한다.
3. source-level 검증과 release helper dry-run으로 publish 전 결함을 먼저 제거한다.
4. rehearsal DMG는 public artifact로 사용하지 않고 layout, checksum, delta checklist 확인에만 쓴다.
5. public publish는 `main` 반영과 `v0.1.7` tag 확정 후 release owner 승인으로만 실행한다.
6. `draft=true`, `prerelease=false` 실행은 pre-public signed/notarized DMG smoke gate로 보고 stable appcast와 Pages deployment 성공 조건에 포함하지 않는다.
7. `draft=false`, `prerelease=false` official stable release에서만 Sparkle stable appcast와 Pages deployment를 성공 조건에 포함한다.
8. Homebrew는 public DMG URL과 SHA256이 확정된 뒤 별도 승인 gate로 진행한다.

## 잠정 단계

1. Stage 1: release context와 source metadata 정렬
   - 최신 공개 앱 release, latest upstream `rhwp`, current lock/manifest, `origin/main`과 `origin/devel` 차이를 대조한다.
   - `0.1.7 (13)`, `previous_release_ref=v0.1.6`, `expected_rhwp_tag=v0.7.17` 기준으로 source metadata와 workflow default를 갱신한다.
2. Stage 2: release communication 작성
   - `mydocs/release/v0.1.7.md`, Pages release note, updates index, README 최신 요약을 정리한다.
   - 포함 PR 분석 표를 작성하고 `rhwp v0.7.17` 사용자-facing 변화, 알한글 앱 변화, known limitations를 구분한다.
3. Stage 3: source preflight와 rehearsal
   - lock/provenance, bundled asset, no-AppKit, Debug build, render smoke, release helper dry-run을 수행한다.
   - 승인 후 local rehearsal DMG 또는 `Release Rehearsal DMG` workflow를 실행하고 delta checklist 초안을 보정한다.
4. Stage 4: main/tag/pre-public smoke와 official publish gate
   - `devel` release candidate를 `main`에 반영할 PR 준비 자료를 완성한다.
   - `v0.1.7` tag 생성 후 별도 승인으로 `Release Publish DMG`를 `draft=true`, `prerelease=false`로 실행해 signed/notarized DMG 설치 smoke를 수행한다.
   - draft smoke 통과 후 별도 승인으로 `Release Publish DMG`를 `draft=false`, `prerelease=false` official stable 기준으로 실행한다.
5. Stage 5: post-publish 확인과 Homebrew gate
   - GitHub Release asset, official stable public DMG SHA256, Pages 다운로드 링크, stable appcast, public 설치본 smoke, Sparkle update smoke를 기록한다.
   - Homebrew 반영은 public DMG SHA256 확정 후 별도 승인으로 처리한다.
6. Stage 6: 최종 보고와 cleanup handoff
   - 최종 release report를 작성하고, PR/merge 후 남은 branch, issue, release record 정리 항목을 확인한다.

## 리스크

- release workflow 기본 입력이 stale한 상태에서 workflow_dispatch를 실행하면 lock guard에서 실패하거나 잘못된 delta checklist가 생성될 수 있다.
- `devel`과 `main` 사이에 포함된 변경 범위를 release note에서 사용자-facing 변화와 운영 자동화 변화로 정확히 분리하지 않으면 릴리즈 커뮤니케이션이 흐려질 수 있다.
- `rhwp v0.7.17`에는 차트 렌더 정합과 표 편집 회귀 보정이 포함되므로 HostApp WebView bridge, bundled `rhwp-studio`, Finder/Quick Look native path가 어떤 변화를 실제로 노출하는지 구분해야 한다.
- public publish는 GitHub Actions release environment secret과 Pages environment 설정에 의존하므로, secret 값은 기록하지 않고 존재와 검증 결과만 남겨야 한다.
- rehearsal DMG, 개발용 zip, pre-public draft DMG, official stable public DMG의 산출물 계층을 섞으면 Homebrew SHA나 Sparkle enclosure가 잘못될 수 있다.
- Intel Mac 실기기 smoke, GUI Quick Look preview, Sparkle update smoke를 실행하지 못하면 성공으로 기록하지 않고 미실행 사유를 남겨야 한다.
