## 배경

2026-07-28 live 조회 기준 최신 공개 앱 릴리즈는 `v0.1.8 (14)`이며, Git tag는 `542a35f2179e5499996b2ab7d2b1a94774b544a2`를 가리킨다. 최신 upstream 공개 릴리즈는 `rhwp v0.8.2`이고 resolved commit은 `9b16aa9e23f476e2b335d7c029fc9f24a199d63c`이다.

PR #436과 PR #440 merge로 현재 `devel`에는 다음 결과가 반영됐다.

- `rhwp-core.lock`, RustBridge dependency와 bundled `rhwp-studio`를 `v0.8.2`의 같은 resolved commit으로 정렬
- `RhwpCoreBuildInfo` provenance 보정
- external image Swift resolver를 포함한 최신 `devel` 결합 검증
- Rust/Swift ABI, ExternalImageTests, 세 app target, representative renderer, Quick Look과 Thumbnail policy 검증
- actual Finder thumbnail과 local Release package smoke
- `project.yml`을 진실 원천으로 한 generated Xcode project 정합화

현재 HostApp, Quick Look과 Thumbnail extension source version/build는 모두 `0.1.8 (14)`다. Release Rehearsal/Publish workflow 기본 입력도 `version=0.1.8`, `previous_release_ref=v0.1.7`, `expected_rhwp_tag=v0.7.18`에 머물러 있어 새 release identity와 정렬해야 한다.

Task #438에서 `v0.8.2` 결합 후보는 portable source/header/FFI와 앱·Finder gate를 통과했다. 다만 local toolchain에서 strict `librhwp.a` byte hash/size는 reference와 달랐고, 실제 registered Quick Look의 external sibling 접근은 sandbox `permissionDenied` 뒤 main document fallback을 유지했다. Finder GUI Preview, bundled editor 인쇄/PDF와 장문서 repaint, signed/notarized DMG, Sparkle update와 Intel Mac 실기기 확인은 public release의 수동 차단 gate로 남아 있다.

`v0.1.8..candidate`에는 직전 릴리즈의 종료 정리·back-merge와 이후 제품 변경이 함께 보인다. 포함 PR 분석에서는 이미 `v0.1.8`에 공개된 항목을 다시 해결된 Issue나 주요 변화로 노출하지 않고, 실제 신규 사용자-facing 변화·upstream sync·운영 변경을 분리해야 한다.

## 설계 방향

1. `mydocs/manual/public_release_runbook.md`의 Gate 0~10과 rollback 기준을 실행 순서의 진실 원천으로 삼는다.
2. release identity는 `v0.1.9 (15)`, previous ref `v0.1.8`, core/studio `rhwp v0.8.2`로 제안한다. Stage 1에서 앱·upstream 최신 release, candidate commit과 tag 미사용 상태를 다시 조회한 뒤 확정한다.
3. `rhwp-core.lock`, RustBridge lock, `RhwpCoreBuildInfo`와 bundled studio manifest의 tag/commit을 source와 artifact 단계 모두에서 대조한다.
4. strict `librhwp.a` byte 검증과 portable source/header/FFI 검증을 하나의 성공으로 합치지 않는다. strict mismatch가 재현되면 toolchain·archive 차이와 portable 결과를 보고하고, rehearsal 진입 전 release owner가 허용 경계를 별도로 승인하도록 중단한다.
5. `v0.1.8..candidate`의 first-parent merge, PR body, 연결 Issue와 최종 보고서를 근거로 포함 PR 분석 표를 만든다. 직전 릴리즈 종료 정리와 back-merge는 신규 사용자-facing 변화에서 제외한다.
6. 공개 문구는 사용자가 실제로 보는 앱, 문서 호환, Finder preview/thumbnail, 편집기 변화만 주요 변경으로 설명한다. provenance, workflow default, generated project와 단순 version bump는 운영·기술 세부로 분리한다.
7. rehearsal artifact, pre-public draft DMG와 official public DMG를 서로 다른 계층으로 관리한다. draft/rehearsal URL이나 SHA256을 Sparkle, Pages 또는 Homebrew 입력으로 사용하지 않는다.
8. signed/notarized draft DMG 설치 smoke를 official publish 전 차단 gate로 둔다. 실제 Preview, Finder provider 경로, external sibling fallback, 장문서와 인쇄/PDF 결과를 실행 여부까지 구분해 기록한다.
9. `require_latest_rhwp=true`, `include_rhwp_in_title=true`를 제안한다. 실행 직전 upstream latest가 바뀌면 publish를 중단하고 새 sync 또는 명시적 예외 승인 여부를 확인한다.
10. official publish, Pages/Sparkle와 Homebrew는 각각 별도 승인 후 수행한다. publish 후 문구·record 보정은 runbook 원칙에 따라 하나의 릴리즈 종료 정리 단계로 모은다.

## 잠정 단계

1. Stage 1: release context와 source identity 확정
   - 최신 앱/upstream release, `main`, `devel`, candidate commit, tag와 `v0.1.8..candidate` 범위를 live 조회한다.
   - app/extension version, workflow default, core/studio provenance와 Cask current 상태를 inventory한다.
   - 승인된 identity에 따라 source version/build와 workflow 기본 입력을 정렬한다.
2. Stage 2: 포함 PR 분석과 release communication 작성
   - merge PR, PR body, 연결 Issue와 최종 보고서를 분류해 포함 PR 분석 표를 작성한다.
   - release record, README, Pages 업데이트 문서와 release note 초안을 작성·검증한다.
   - 사용자-facing 변화, 기술 세부, 알려진 한계와 미실행 수동 gate를 구분한다.
3. Stage 3: source preflight와 rehearsal
   - core/studio provenance, strict/portable artifact, ABI/tests, app target, renderer와 universal Release package를 검증한다.
   - 별도 승인 후 Rehearsal workflow 또는 동등한 local rehearsal을 실행한다.
   - rehearsal checksum, DMG layout, delta checklist와 artifact 계층을 확인한다.
4. Stage 4: release PR/tag와 pre-public signed candidate
   - 별도 승인 후 `devel -> main` release PR을 생성·검증·merge하고 final candidate를 고정한다.
   - 별도 승인 후 정확한 final candidate에 annotated `v0.1.9` tag를 생성한다.
   - 별도 승인 후 draft Publish를 실행하고 signed/notarized DMG 설치 smoke와 수동 차단 gate를 수행한다.
5. Stage 5: official stable publish와 public surface
   - draft smoke 통과 후 별도 승인으로 official stable Publish를 실행한다.
   - GitHub Release, public DMG, Pages, stable appcast, Sparkle update와 설치본 Finder smoke를 확인한다.
   - public DMG SHA256 확정 뒤 별도 승인으로 Homebrew tap을 반영하고 검증한다.
6. Stage 6: release record, 최종 보고와 종료 정리
   - 실제 tag/commit, workflow run, DMG URL/SHA256, public surface, 수동 smoke와 미실행 항목을 release record와 최종 보고서에 확정한다.
   - publish 이후 문구/record 보정은 하나의 종료 정리 단계와 PR로 묶는다.
   - Task #441 PR·Issue close와 branch/worktree cleanup 조건을 확정한다.

각 Stage 종료 시 `task-stage-report` 절차로 변경과 단계 보고서를 검증·커밋하고 다음 Stage 승인을 요청한다. Stage 안에서도 rehearsal, `main` merge, tag, draft Publish, official Publish와 Homebrew는 위에 명시한 별도 실행 승인을 받아야 한다.

## 리스크

- Stage 1 전후로 `devel`에 다른 PR이 merge되면 candidate commit과 포함 PR 분석 범위가 달라진다. candidate 이동을 조용히 흡수하지 않고 release owner에게 재확정받는다.
- local toolchain의 strict `librhwp.a` byte hash/size가 reference와 다르다. portable source/header/FFI 통과만으로 strict 통과라고 기록하지 않으며, rehearsal 전에 release artifact 허용 근거를 별도 승인받는다.
- upstream latest가 `v0.8.2` 이후로 이동하면 `require_latest_rhwp=true`가 publish를 차단한다. guard를 임의로 해제하지 않고 새 sync 또는 명시적 예외 판단으로 분리한다.
- source build와 headless policy test는 실제 Finder Space/Preview, PlugInKit provider 선택, LaunchServices cache와 signed 설치본 동작을 대체하지 못한다.
- registered Quick Look은 external sibling image sandbox 접근이 거부될 수 있다. main document fallback을 유지하더라도 release note에서 지원 완료로 과장하지 않는다.
- bundled editor의 장문서 repaint, 인쇄/PDF와 WebView interaction은 자동 renderer test만으로 충분하지 않다. draft 설치본 수동 결과를 별도로 기록한다.
- rehearsal, draft와 official DMG를 혼동하면 Pages, Sparkle enclosure 또는 Homebrew SHA256이 잘못될 수 있다.
- signing/notarization, Sparkle appcast와 Pages는 GitHub Actions environment와 secret에 의존한다. secret 값은 읽거나 기록하지 않고 존재 여부와 workflow 결과만 확인한다.
- 기존 설치본과 Quick Look provider cache가 smoke false positive를 만들 수 있다. registration hygiene와 실제 provider path를 함께 기록한다.
- Intel Mac 실기기 smoke를 수행하지 못하면 universal binary 검증과 별개로 미실행 사유와 잔여 위험을 남긴다.
- official publish 이후 사용자-facing 문구 수정이 필요하면 public surface와 release record가 일시적으로 어긋날 수 있다. 하나의 종료 정리 단계로 모아 최종 상태를 다시 검증한다.
