# Task M019 #348 수행계획서

## 목적

`rhwp Upstream Sync PR` workflow를 `rhwp-studio` bundled asset만 갱신하는 자동화에서, upstream `rhwp` 최신 stable release를 앱 저장소에 완전 적용하는 full upstream sync 후보 PR 생성 자동화로 확장한다.

이번 작업의 full sync 기준은 같은 upstream release tag를 기준으로 다음 provenance가 정합되는 상태다.

- `Sources/HostApp/Resources/rhwp-studio/manifest.json`
- bundled `rhwp-studio` asset과 WASM 산출물
- `RustBridge/Cargo.toml`
- `RustBridge/Cargo.lock`
- `rhwp-core.lock`
- 필요 시 `rhwp-ffi-symbols.txt`와 `rhwp-core.lock`에 기록되는 generated header/staticlib reference metadata

public release, signed/notarized DMG, GitHub Release, Sparkle appcast, Homebrew Cask 배포는 이번 작업의 자동 실행 범위가 아니다. full sync PR은 release 후보 입력을 만드는 단계이며, 실제 release 여부와 version은 별도 release approval gate에서 결정한다.

## 배경

#347에서 `rhwp Upstream Sync PR` workflow의 upstream WASM build 권한 문제와 자동 PR 생성 권한 문제를 수정했다. 검증 과정에서 자동 생성된 #346은 `rhwp-studio` bundled asset만 `v0.7.14`로 갱신했고, native RustBridge 기준인 `rhwp-core.lock`은 `v0.7.13`으로 남겼다.

이 상태는 release provenance와 release note에서 `rhwp-studio`/WASM과 native core 기준을 분리해 설명해야 하므로, “upstream rhwp 최신 릴리즈를 우리 앱에 완전히 적용한다”는 운영 목표와 맞지 않는다.

또한 GitHub Actions의 기본 `GITHUB_TOKEN`으로 생성한 PR은 후속 `pull_request` workflow를 자동으로 트리거하지 않아, 자동 생성 PR에 PR CI가 붙지 않는 문제가 있다. 따라서 자동 PR 생성 token 또는 검증 트리거 구조도 함께 정리해야 한다.

Stage 1 시작 시점인 2026-06-07에는 upstream latest release가 `v0.7.15`로 바뀌었으므로, 이번 작업의 실제 full sync 검증 대상은 `v0.7.15`로 보정한다.

현재 확인 기준:

- upstream `edwardkim/rhwp` 최신 release: `v0.7.15`
- release URL: `https://github.com/edwardkim/rhwp/releases/tag/v0.7.15`
- publishedAt: `2026-06-06T14:59:20Z`
- resolved commit: `aa925a5954f0fd26dfcef2166cbce7877c481f44`
- 현재 `devel`의 `rhwp-core.lock`: `v0.7.13`
- #346: `rhwp-studio` only PR로 superseded close됨
- #347: #345 workflow 권한 수정 PR merge 완료

## 범위

- macOS runner에서 core update와 provenance 검증을 수행하는 단계 추가 또는 job 분리
- 자동 생성 PR이 PR CI를 정상 트리거하도록 token/dispatch 구조 설계
- PR body에 studio/core provenance와 검증 결과를 분리해 표시
- `mydocs/manual/ci_workflow_guide.md`, `mydocs/manual/core_dependency_operation_guide.md` 등 운영 문서 보강
- 실제 `v0.7.15` 대상 dry-run/full-run 검증과 자동 PR 생성 확인

제외:

- upstream `edwardkim/rhwp` 자체 수정
- public release version 확정
- signed/notarized DMG 생성과 게시
- GitHub Release, Sparkle stable appcast, Homebrew Cask 배포

## 설계 방향

1. 현재 workflow의 `rhwp-studio` only staging 구조를 분석한다.
2. full sync 산출물 경계를 정한다.
   - `scripts/update-rhwp-core.sh --channel stable --tag <tag>`
   - `scripts/build-rust-macos.sh --update-lock`
   - `scripts/build-rust-macos.sh --verify-lock`
   - `scripts/check-no-appkit.sh`
   - `scripts/sync-rhwp-studio.sh`
   - `scripts/verify-rhwp-studio-assets.sh`
3. Ubuntu job과 macOS job의 역할 분리를 검토한다.
   - upstream WASM/studio build는 기존 Ubuntu Docker 경로 유지 가능
   - native RustBridge artifact/provenance update는 macOS runner 필요 가능성이 높음
   - 산출물을 하나의 automation branch로 모으는 artifact handoff 또는 단일 macOS job 전환을 비교한다.
4. PR CI 트리거 방식을 정한다.
   - GitHub App token을 우선 검토한다.
   - fine-grained PAT는 운영 부담과 secret 범위를 비교한다.
   - `repository_dispatch`/`workflow_dispatch` 보조 검증은 fallback으로 검토한다.
5. 자동 PR body는 release owner가 판단할 수 있게 다음을 분리한다.
   - previous/current `rhwp-core.lock`
   - previous/current `rhwp-studio` manifest
   - upstream release URL과 resolved commit
   - repository changed paths
   - core/studio 검증 결과
   - release boundary

## Stage 2 설계 결정

Stage 2에서 full sync 구현 방향을 다음으로 고정한다.

- workflow는 Ubuntu와 macOS job split 구조를 사용한다.
  - Ubuntu job은 upstream checkout, viewer impact 분석, Docker 기반 WASM build, `rhwp-studio` Vite build, build artifact upload를 담당한다.
  - macOS job은 base branch checkout, upstream checkout 복원, studio build artifact download, `scripts/update-rhwp-core.sh --channel stable --tag <target>`, `scripts/build-rust-macos.sh --update-lock`, `scripts/check-no-appkit.sh`, `scripts/sync-rhwp-studio.sh`, `scripts/verify-rhwp-studio-assets.sh`, 자동 branch commit/push/PR 생성을 담당한다.
- current 판정은 `rhwp-core.lock`과 `rhwp-studio/manifest.json`을 모두 사용한다. 둘 다 target tag/resolved commit과 일치할 때만 current로 보고, 한쪽만 뒤처진 경우에도 full sync PR을 생성한다.
- viewer impact 분석은 PR body의 판단 자료로 유지하되, full sync 생성 여부의 유일한 gate로 사용하지 않는다.
- 자동 branch는 `automation/rhwp-<tag>-full-sync`, PR 제목은 `Sync rhwp upstream <tag>` 형식을 사용한다.
- 자동 PR 생성 token은 GitHub App installation token을 기본값으로 사용한다. `GITHUB_TOKEN` fallback으로 실제 PR을 만들지 않는다.
- repository에는 `vars.ALHANGEUL_AUTOMATION_APP_ID`, `secrets.ALHANGEUL_AUTOMATION_APP_PRIVATE_KEY`를 준비해야 한다. GitHub App 권한은 이 저장소의 Contents write, Pull requests write, Issues write, Metadata read로 제한한다.
- `Frameworks/` 산출물은 기존 정책대로 git에 commit하지 않는다. `scripts/build-rust-macos.sh --update-lock`로 생성 산출물의 hash/size를 `rhwp-core.lock`에 반영하고, tracked 변경은 `rhwp-core.lock`, `RustBridge/*`, `rhwp-ffi-symbols.txt`, bundled studio asset 중심으로 제한한다.
- PR body helper는 full sync 기준으로 확장하거나 신규 helper로 분리해 core/studio provenance, upstream impact, repository changed paths, verification, release boundary를 명시한다.

## 잠정 단계

### Stage 1. 현재 workflow와 core update 경계 분석

- 현재 `rhwp Upstream Sync PR`의 `rhwp-studio` only staging 구조를 정리한다.
- `scripts/update-rhwp-core.sh`, `scripts/build-rust-macos.sh`, PR CI classification을 확인한다.
- `v0.7.15` 기준 current/proposed provenance 차이를 보고서에 고정한다.
- full sync에 macOS runner가 필요한지 확정한다.

### Stage 2. full sync 설계와 PR CI 트리거 설계 확정

- 단일 job, Ubuntu+macOS job split, artifact handoff 선택지를 비교한다.
- GitHub App token, fine-grained PAT, dispatch 기반 검증 대안을 비교한다.
- 운영 secret/permission 요구사항과 fallback 절차를 문서화한다.
- 구현계획서에 최종 선택지를 고정한다.

### Stage 3. workflow/helper 구현

- workflow source와 필요한 helper를 수정한다.
- core/studio 산출물 staging 범위를 확장한다.
- PR body 생성 내용을 full sync 기준으로 보강한다.
- YAML/shell syntax와 helper interface를 검증한다.

### Stage 4. 로컬/CI dry-run 검증

- `target_tag=v0.7.15`, `dry_run=true` 또는 check-only 경로로 target resolve, impact detection, full sync decision을 확인한다.
- macOS/core update 단계가 실제 write 전 검증 가능한 구조인지 확인한다.
- PR CI trigger 설계가 secret 없이 검증 가능한 범위와 실제 secret 필요 범위를 분리한다.

### Stage 5. 실제 full sync 자동 PR 생성 검증

- 승인된 token/secret 또는 선택한 trigger 구조로 `dry_run=false` 실행한다.
- full sync automation branch/PR이 생성되는지 확인한다.
- 생성 PR에서 `rhwp-core.lock`과 `rhwp-studio` manifest가 같은 target release 기준으로 정합되는지 확인한다.
- PR CI가 자동 생성 PR에 정상 표시되는지 확인한다.
- 생성된 full sync PR은 검토 후보로만 남기고, 이번 #348 작업 안에서 merge하지 않는다.

### Stage 6. 최종 보고와 #348 수정 PR 게시

- 최종 보고서를 작성한다.
- 검증 결과와 잔여 운영 secret/permission 위험을 정리한다.
- `publish/task348` PR을 `devel` 대상으로 게시한다.

## 리스크

- full sync는 `rhwp-studio` only sync보다 실행 시간이 길고 macOS runner 의존성이 커질 수 있다.
- `build-rust-macos.sh --update-lock`가 만드는 staticlib metadata는 runner/toolchain 차이 영향을 받을 수 있으므로, 기존 hash skip 정책과 충돌하지 않게 설계해야 한다.
- GitHub App token 또는 fine-grained PAT 도입은 secret 관리와 권한 범위 결정이 필요하다.
- 자동 PR이 workflow 파일을 변경할 가능성이 생기면 token scope와 PR CI 트리거 정책이 더 엄격해질 수 있다.
- `v0.7.15` core update 과정에서 RustBridge ABI 또는 Swift bridge 호환 이슈가 발견될 수 있다. 이 경우 full sync workflow 구현과 core 적응 작업을 분리해야 할 수 있다.
- 자동 생성 full sync PR은 release 후보 입력이지 public release가 아니므로, release owner의 별도 분석과 release approval이 계속 필요하다.

## 승인 요청 사항
