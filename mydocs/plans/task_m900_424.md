## 배경

최신 공개 앱 릴리즈는 `v0.1.7 (13)`이다. 이후 `devel`에는 HOP이 등록한 HWP/HWPX UTI 호환 지원과 upstream `rhwp v0.7.18` core 및 bundled editor 동기화가 반영됐다. Task #422와 PR #423은 `rhwp v0.7.19`에서 bundled studio Host RPC 회귀를 확인하고, 이번 릴리스 입력을 stable `v0.7.18` / `93862a4e16df59834ebce46d91e948cd739208e9`로 확정했다.

현재 HostApp, Quick Look, Thumbnail extension의 source version/build는 모두 `0.1.7 (13)`이다. Release Rehearsal/Publish workflow 기본 입력도 `version=0.1.7`, `previous_release_ref=v0.1.6`, `expected_rhwp_tag=v0.7.17`에 머물러 있어 릴리스 후보와 정렬해야 한다.

upstream 최신 공개 태그는 `v0.7.19`이므로 Publish workflow의 `require_latest_rhwp=true`를 그대로 사용하면 이번 후보는 의도대로 차단된다. 전역 기본 안전장치는 유지하고, upstream Issue `edwardkim/rhwp#2396`과 Task #422의 회귀 판정에 근거해 이번 draft/official 실행에서만 `require_latest_rhwp=false` 예외를 별도 승인받아 사용한다. `v0.7.19` 문제를 해결한 새 stable tag는 다음 core sync와 후속 릴리스에서 검토한다.

## 설계 방향

1. `mydocs/manual/public_release_runbook.md`를 실행 기준으로 삼고 source identity, release communication, artifact 검증과 공개 배포 gate를 분리한다.
2. release candidate는 `0.1.8 (14)`와 `rhwp v0.7.18` tag/commit 쌍으로 고정한다. native core와 bundled studio provenance가 같은지 모든 source 및 artifact 단계에서 확인한다.
3. `v0.7.19`가 upstream latest라는 사실을 숨기거나 latest 검사를 전역에서 비활성화하지 않는다. Publish workflow 실행 시 `require_latest_rhwp=false`를 명시하고, Task #422와 upstream #2396을 예외 근거로 release record와 workflow 결과에 남긴다.
4. `v0.1.7..candidate` 변경을 사용자-facing, core/studio sync, 운영·배포, 문서 변경으로 분류한다. 공개 문구에는 실제 앱에서 확인된 사용자 변화만 포함한다.
5. HOP 호환은 Finder 후보 경로 보강으로 설명한다. macOS 기본 앱 자동 변경이나 모든 환경에서의 후보 노출을 보장한다고 표현하지 않는다.
6. rehearsal artifact, pre-public draft artifact와 official stable artifact를 구분한다. SHA256, appcast enclosure와 Homebrew Cask는 official public DMG를 기준으로만 확정한다.
7. signed/notarized draft DMG에서 HOP exact UTI 및 custom scheme Host RPC를 차단 gate로 검증한 뒤 official publish 승인을 요청한다.
8. official stable publish와 Homebrew 반영은 각각 작업지시자의 별도 명시 승인 후 실행한다.

## 잠정 단계

1. Stage 1: release context와 source metadata 정렬
   - public release, upstream/core provenance, `main..devel` 변경과 workflow guard를 재확인한다.
   - 앱 세 target과 workflow 기본 입력을 `0.1.8 (14)`, `v0.1.7`, `v0.7.18`로 정렬한다.
2. Stage 2: release communication 작성
   - release record, 포함 PR 분석, README와 Pages 업데이트 문서를 작성한다.
   - 사용자-facing 변화, known limitations와 `v0.7.19` 제외 근거를 구분한다.
3. Stage 3: source preflight와 rehearsal
   - lock/studio provenance, ABI, 앱 build, renderer, release helper와 universal package를 검증한다.
   - 별도 승인 후 rehearsal DMG를 생성하고 layout, checksum과 delta checklist를 확인한다.
4. Stage 4: main/tag와 pre-public signed candidate 검증
   - 별도 승인으로 `devel -> main` release PR과 `v0.1.8` tag를 진행한다.
   - 별도 승인으로 draft publish를 `require_latest_rhwp=false` 예외와 함께 실행하고 signed/notarized DMG에서 일반 설치 smoke, HOP exact UTI와 Host RPC 차단 gate를 검증한다.
5. Stage 5: official publish와 post-publish surface 확인
   - draft smoke 통과 후 별도 승인으로 official stable publish를 실행한다.
   - GitHub Release, public DMG, Pages, stable appcast, Sparkle 업데이트와 설치본 smoke를 확인하고, 별도 승인 후 Homebrew를 반영한다.
6. Stage 6: 최종 보고와 cleanup handoff
   - 전체 승인·검증 결과, 미실행 항목, 잔여 위험과 후속 이슈를 최종 보고서에 정리하고 PR 및 merge 후 cleanup 조건을 확정한다.

각 Stage 종료 시 `task-stage-report` 절차로 단계 변경과 보고서를 검증·커밋하고 다음 Stage 승인을 요청한다.

## 리스크

- upstream latest가 `v0.7.19`이므로 `require_latest_rhwp=false` 예외 없이 Publish workflow는 실패한다. 반대로 예외 근거를 불명확하게 남기면 release provenance 안전장치가 약화될 수 있다.
- source build와 일반 문서 열기만으로는 `v0.7.19`에서 발견한 Host RPC 계열 회귀를 배제할 수 없다. readiness, page count, SVG/PDF export, 저장·공유·인쇄 시작까지 signed candidate에서 확인해야 한다.
- HOP exact UTI routing은 LaunchServices cache, 기존 한컴 앱과 설치 순서에 영향을 받을 수 있다. UTI tree, handler와 Finder 후보를 함께 기록해 앱 결함과 환경 상태를 분리한다.
- release note에서 HOP 호환을 기본 앱 자동 설정으로 과장하거나 외부 연결 이미지, Skia default, `v0.7.19` 기능까지 포함하면 실제 지원 범위와 불일치한다.
- rehearsal, draft와 official DMG를 혼동하면 Sparkle enclosure, Homebrew SHA256 또는 Pages 다운로드 링크가 잘못될 수 있다.
- public publish는 GitHub Actions environment와 signing/notary/Sparkle secret에 의존한다. 값은 기록하지 않고 존재 여부와 결과만 기록한다.
- Intel Mac 실기기, Finder GUI, Sparkle update 등 수동 smoke를 수행하지 못하면 성공으로 간주하지 않고 미실행 사유와 잔여 위험을 남긴다.

## 승인 요청 사항

1. release identity를 `v0.1.8 (14)`, previous release `v0.1.7`, expected core `rhwp v0.7.18` / `93862a4e...`로 고정한다.
2. 기준 브랜치는 `devel`, 작업 브랜치는 `local/task424`, 분리 worktree는 `/Users/melee/Documents/projects/rhwp-mac-task424`를 사용한다.
3. 위 6개 잠정 단계와 각 단계 종료 승인 gate를 사용한다.
4. upstream latest guard 기본값은 유지하되, draft와 official publish에서 `require_latest_rhwp=false`를 사용하려면 Task #422와 upstream #2396 근거로 별도 승인을 받는다.
5. signed candidate의 HOP exact UTI와 custom scheme Host RPC 검증을 official publish 전 필수 차단 gate로 둔다.
6. public publish, Pages/Sparkle와 Homebrew 반영은 각 실행 시점에 별도 승인을 받는다.
