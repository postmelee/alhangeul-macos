## 1. 실행 목표와 경계

Mac에 설치된 글꼴을 독립 보관한 뒤 한컴 한글이 없는 환경에서도 화면·PDF에 적용할 수 있는지 입증하고, 후속 제품 구현의 계약을 확정한다. Windows 폴더·ZIP도 같은 관리 계층으로 수용할 수 있는지 설계한다.

이 이슈의 결과물은 설계 문서와 재현 가능한 최소 실험이다. 가져오기 UI, 정식 저장소, 모든 renderer 연결을 완성하는 이슈로 확대하지 않는다. 구현계획 작성 단계에서는 계획 문서만 변경했으며, Stage 1은 조사 문서와 읽기 전용 메타데이터 확인을 수행했다.

제품 소스·entitlement·project.yml·core pin·bundled Studio를 직접 변경하지 않는 독립 실험을 우선한다. 제품 경로 변경 없이는 입증할 수 없는 항목은 한계와 필요한 변경을 후속 이슈에 남긴다. 독립 실험 성공을 실제 sandbox 설치본의 전체 지원 성공으로 일반화하지 않는다.

## 2. 공통 조사·증거 규칙

- 기준: 현재 lock의 `rhwp v0.8.6` / `f1f9c6ae58344ee9368996d3543f76b9345cf227`. 로컬 upstream checkout을 사용할 때는 commit 일치를 먼저 확인한다.
- 공식 자료, 로컬 코드, 실제 실행 결과, 설계 제안을 구분한다. 공식 자료에는 URL·확인일·대상 버전을 기록한다.
- 실제 설치본 확인은 한컴 앱 후보와 글꼴 디렉터리 등 과업 관련 위치에 한정한다. 사용자 문서와 무관한 디렉터리를 일괄 탐색하지 않는다.
- 각 글꼴은 출처, 형식, 파일 해시, face index, family/full/PostScript 이름, 스타일·버전, 사용 조건 및 시스템 설치 여부를 기록한다.
- 상용 글꼴 bytes와 사용자 절대 경로는 저장소·보고서에 공개하지 않는다. 공식 설치 위치 예시와 비식별 메타데이터만 남긴다.
- 검증에 필요한 한컴 설치본·Windows 환경·형식별 자산이 없으면 미검증으로 기록한다. 확보 가능한 공개 글꼴로 독립 공급 원리를 검증하되 실제 한컴 호환성 판정을 대신하지 않는다.
- 원본 부재는 실험용 복사본의 경로 분리·접근 차단으로 재현한다. 사용자 한컴 앱과 시스템 글꼴은 삭제·변경하지 않는다.

## 3. Stage 1 — 위치·형식·접근·사용 조건 조사

### 작업

1. macOS 버전, 앱 배포 버전, 한컴 설치본 유무·버전 및 글꼴 후보 위치를 확인한다.
2. Mac 한글 번들 내부 글꼴, 사용자 설치 글꼴, 공용 설치 글꼴을 구분한다. CoreText 목록에서 볼 수 있는 것과 실제 파일을 읽을 수 있는 것을 구분한다.
3. 한컴 공식 자료로 Windows의 OS 설치 글꼴과 한글 전용 폴더 위치를 버전별로 정리한다. 경로 하나로 모든 설치본을 설명하지 않는다.
4. TTF·OTF·TTC, 가변 글꼴 및 HFT의 판별·공급 가능성을 정리하고, 테스트 가능한 자산을 선정한다.
5. 사용자 선택 접근, 지속 접근, 앱 관리 저장소, 확장 간 공유에 필요한 macOS 계약을 공식 문서와 현재 entitlement에 대조한다.
6. 사용·복사·PDF 임베딩 조건을 구분한다. 권리 정보가 불분명하면 허용으로 단정하지 않는다.

### 산출물·통과 기준

- `mydocs/tech/font_migration_design.md`에 환경·출처별 지원 표, 후보 위치, 사용 조건 및 미확인 항목을 작성한다.

## 4. Stage 2 — 독립 보관·이름 매칭·렌더 공급 설계

### 작업

1. 가져오기 흐름을 후보 발견 → 파일 읽기·검증 → 중복·충돌 판단 → 앱 관리 영역 게시 → 목록 갱신 → renderer 적용으로 정의한다.
2. 원본 참조와 독립 복사를 비교하고 한컴 삭제 이후 수명을 기준으로 선택한다. 관리 파일과 manifest의 원자적 게시, 취소·중단 복구, 제거·재등록 정책을 정한다.
3. 파일 hash와 face 식별자를 분리하고 한글·영문 이름, 스타일·굵기, 같은 이름의 다른 버전, TTC face, 가변 축을 표현하는 메타데이터 계약을 작성한다.
4. 자동 일치 / 복수 후보 충돌 / 미일치 처리를 정의한다. 가져온 글꼴을 사용할 수 없을 때 fallback 정책과 사용자 결과 표시를 명시한다.
5. HostApp에서 글꼴을 등록하는 것만으로 별도 WebContent·확장 프로세스까지 공급되는지 단정하지 않고, bytes 전달 또는 제한된 resource route를 비교한다.
6. PDF 전용 글꼴 허용 정책, 로드 완료 대기, ToUnicode 유지와 CoreGraphics/Skia의 공급 지점을 정리한다.
7. Windows ZIP 입력에는 경로 이탈, symlink, 해제 용량·개수 제한, 중첩 폴더와 한글 이름 처리를 요구한다. 해제 도구 구현은 #566 범위다.

### 산출물·통과 기준

- 설계 문서에 저장 수명, 메타데이터 예시, 결과 상태, 이름 충돌 정책과 renderer별 연결 표를 작성한다.
- 한컴 삭제·원본 이동·알한글 재시작 후 참조가 끊기는 지점이 없도록 설계하거나 해결해야 할 조건을 명시한다.
- 앱 저장소와 upstream의 변경 소유 경계, 확장 공유 구성 및 실제 sandbox 검증 잔여 항목이 정리된다.
- Stage 3 실험 입력·대조군·예상 판정이 구체화된다. 가설은 검증 완료로 표시하지 않는다.

## 5. Stage 3 — 최소 적용·재시작·원본 부재 실험

### 실험 구현 범위

- 신규 진입점 `scripts/probe-font-migration.sh`, 독립 Swift 실험 코드 `scripts/font_migration_probe.swift`를 필요 범위에서 작성한다.
- 진입점은 `--help`, 명시적 글꼴 입력·출력 디렉터리를 제공한다. 출력은 기본적으로 `build.noindex/task563-font-migration/` 아래에 둔다.
- 실험 코드·재현 방법만 버전 관리하고 글꼴 bytes, PDF, 이미지, 임시 앱은 실험 출력 디렉터리에 둔다.
- 기존 `RhwpStudioPagePDFRendererTests.swift`와 `CGPDFFontResourceInspector.swift`를 읽어 PDF 검사 방식을 참고한다. 변경 없는 기존 테스트를 통과한 것으로 새 기능을 입증하지 않는다.

### 실험 순서

1. 시스템에 같은 face가 존재하는지 확인하고, 미설치 자산 또는 허용된 별도 이름의 테스트 자산으로 대조군을 구성한다. 단순한 파일명 변경은 글꼴 이름 분리로 취급하지 않는다.
2. 실험용 원본 디렉터리에서 관리 디렉터리로 복사하고 hash·face 메타데이터를 기록한다.
3. WKWebView에 관리 디렉터리의 font bytes를 공급하여 한글 regular/bold 표본을 표시하고 PDF를 만든다. 외부 네트워크 글꼴에 의존하지 않는다.
4. 프로세스와 WebView를 종료하고 실험 원본을 읽을 수 없도록 분리한 뒤, 새 프로세스가 관리 디렉터리만으로 동일 표본을 렌더링한다.
5. 관리 글꼴도 없는 음성 대조군과 비교해 캐시·시스템 fallback이 성공처럼 보이지 않는지 확인한다.
6. 동일 이름 충돌, TTC face·가변 글꼴, 손상·미지원 파일은 확보된 자산별로 성공·실패·미검증을 기록한다.
7. 현재 bundled Studio의 후보 매칭·실제 렌더 경로에 설계한 공급 방식을 넣기 위해 필요한 변경을 추적한다. 독립 HTML 표본만 성공하면 이를 Studio 통합 성공으로 보고하지 않는다.

### 검증·통과 기준

- 재실행 전후 관리 글꼴 hash, 선택 face 및 공급 resource 증거가 일치한다.
- 화면 글리프·측정 비교와 PDF font resource/한글 텍스트 추출로 적용을 확인한다. `document.fonts.check` 또는 글꼴 목록 표시만으로 판정하지 않는다.
- PDF 검사 도구가 있으면 `pdffonts`, `pdftotext`를 교차 사용하고, 없으면 가용 PDFKit/CGPDF 검사와 검증 한계를 기록한다.
- 지원하지 않는 샘플이 성공으로 오인되지 않으며, 원본과 시스템 글꼴이 보존된다.
- 최소 실험 실패 시 실패 원인·대안을 동일 단계에서 검토한다. 입증하지 못한 핵심 목표를 성공 처리하지 않고 범위 조정이 필요하면 보고한다.
- 실제 sandbox HostApp·확장 smoke, 전체 문서 편집·저장, 실인쇄는 후속 제품 구현의 수용 조건으로 남긴다. 이번 실험에서는 Quick Look 등록을 수행하지 않는다.
