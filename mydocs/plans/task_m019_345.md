# Task M019 #345 수행계획서

## 목적

`rhwp Upstream Sync PR` workflow가 upstream WASM build 중 container 내부에서 `/app/Cargo.lock`을 쓰지 못해 실패하는 문제를 수정한다.

완료 후에는 `devel` ref에서 `target_tag=v0.7.14`, `dry_run=false`로 workflow를 실행했을 때 권한 오류 없이 build/sync 경로가 진행되고, 성공 시 자동 업데이트 후보 PR이 생성되어야 한다.

## 배경

2026-06-05에 `rhwp Upstream Sync PR` run `27004087710`을 다음 조건으로 실행했다.

- ref: `devel`
- target tag: `v0.7.14`
- force PR: `false`
- dry run: `false`

#336 작업으로 추가한 `.env.docker` 준비 로직은 검증됐다. 기존의 `.env.docker` 누락 오류는 재발하지 않았고, Docker image build와 `wasm-pack` 설치까지 진행했다.

하지만 build 단계 후반에서 container 내부 `cargo metadata`가 `/app/Cargo.lock`을 쓰려고 하면서 권한 오류가 발생했다.

```text
error: failed to write /app/Cargo.lock
Caused by:
  failed to open: /app/Cargo.lock
Caused by:
  Permission denied (os error 13)
```

현재 workflow는 upstream `.env.docker.example`을 `.env.docker`로 복사한다. upstream example의 기본값은 `UID=1000`, `GID=1000`이다. GitHub-hosted runner workspace의 실제 file owner UID/GID와 container user UID/GID가 맞지 않아 bind-mounted `/app` write가 실패한 것으로 판단한다.

## 범위(포함·제외)

포함:

- `.github/workflows/rhwp-upstream-sync-pr.yml`의 upstream `.env.docker` 생성 로직 보강
- CI에서 runner workspace의 실제 `id -u`, `id -g` 값을 사용해 `.env.docker` 생성
- `.env.docker.example` 존재 여부와 무관하게 CI 실행에 필요한 최소 `UID`, `GID` env file을 안정적으로 준비하는 방식 검토
- workflow YAML parse와 shell helper syntax 검증
- `devel` ref에서 `target_tag=v0.7.14`, `dry_run=false`로 실제 workflow 실행 검증
- 성공 시 생성된 `automation/rhwp-v0.7.14-studio-sync` PR 확인

제외:

- bundled `rhwp-studio` asset 수동 갱신
- `rhwp-core.lock` 직접 갱신
- RustBridge dependency 직접 갱신
- upstream `edwardkim/rhwp` 수정
- public release, signing, notarization, Homebrew 배포
- 자동 sync PR merge

## 설계 방향

이번 실패는 upstream source 자체가 아니라 GitHub-hosted runner의 bind mount 권한 문제다. 따라서 workflow가 CI용 `.env.docker`를 만들 때 upstream example의 고정 `UID=1000`, `GID=1000`을 그대로 사용하지 않고, 현재 runner user의 실제 UID/GID를 사용한다.

우선 설계 후보는 다음이다.

```bash
{
  echo "UID=$(id -u)"
  echo "GID=$(id -g)"
} > .env.docker
```

기존 `.env.docker`가 이미 있는 경우의 처리 방식은 Stage 1에서 확정한다. CI workflow의 upstream checkout은 재생성 가능한 임시 directory이므로, GitHub Actions에서는 `.env.docker`를 workflow가 명시적으로 생성해도 된다. 다만 upstream이 향후 `.env.docker.example`에 필수 변수를 추가할 가능성을 고려해 example을 기반으로 덮어쓰는 방식과 최소 env file 생성 방식의 장단점을 비교한다.

## 리스크

- UID/GID 권한 문제가 해결돼도 upstream Docker build, `wasm-pack`, npm dependency, TypeScript, Vite build에서 다른 실패가 이어질 수 있다.
- workflow가 성공하면 별도 automation PR이 생성된다. 이 PR은 bundled asset 업데이트 후보이며, maintainer 검토와 PR CI를 거쳐야 한다.
- `rhwp-core.lock` 갱신은 이번 작업 범위가 아니다. 자동 sync PR과 core lock 업데이트의 경계는 기존 운영 정책을 따른다.
- GitHub-hosted runner에서만 완전 검증되는 항목이 있으므로 로컬 syntax 검증만으로 완료 처리하지 않는다.
