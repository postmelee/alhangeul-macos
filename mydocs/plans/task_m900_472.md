PR #471 merge로 현재 `devel`의 native core, RustBridge dependency와 bundled `rhwp-studio`는 같은 `v0.8.4` commit으로 정렬됐다. 이 후보는 PR CI 네 항목, v0.8.4 universal Rust bridge와 HostApp Debug build, bundled asset 검증, 대표 HWP/HWPX viewer smoke를 통과했다.

`v0.1.9` 이후 `devel`에는 다음 변화가 포함된다.

현재 HostApp, Quick Look과 Thumbnail extension source version/build는 모두 `0.1.9 (15)`다. Release Rehearsal/Publish workflow 기본 입력도 `version=0.1.9`, `previous_release_ref=v0.1.8`, `expected_rhwp_tag=v0.8.2`에 머물러 있어 새 release identity와 정렬해야 한다.

현재 `origin/main`은 `26f3104469135c5e80b3a19dddb9d0baebfbfb0a`, `origin/devel`은 `4abdc30746edcd25be3d11fa3d5c1e09f600c6c3`이며 `origin/main...origin/devel` 좌우 차이는 `3 68`이다. Stage 1에서 main 전용 3개 커밋의 성격과 이미 devel에 반영됐는지를 확인하고, release PR 전에 필요한 back-merge를 별도 승인·PR로 분리해야 한다.

로컬 v0.8.4 strict `librhwp.a` byte hash는 workflow가 기록한 reference와 달랐지만 source tag/commit, Cargo resolution, generated header와 FFI symbol 검증은 portable 정책으로 통과했다. strict mismatch를 lock 갱신으로 숨기지 않고 release source preflight에서 strict와 portable 결과를 분리해 기록해야 한다.

이전 viewer smoke 뒤 LaunchServices dump에는 과거 개발 경로의 stale record가 남았지만 활성 Quick Look과 Thumbnail provider는 `/Applications/Alhangeul.app` 하나였다. release Finder smoke 전에는 표준 helper와 실제 provider path를 다시 확인하되 stale record만을 이유로 전역 LaunchServices database reset을 수행하지 않는다.

## 설계 방향

1. `mydocs/manual/public_release_runbook.md`의 Gate 0~10과 rollback 기준을 실행 순서의 진실 원천으로 삼는다.
2. release identity는 `v0.1.10 (16)`, previous ref `v0.1.9`, core/studio `rhwp v0.8.4`로 제안한다. Stage 1에서 앱·upstream latest, candidate commit과 tag 미사용 상태를 다시 조회한 뒤 확정한다.
3. `rhwp-core.lock`, RustBridge lock, `RhwpCoreBuildInfo.swift`와 bundled studio manifest의 tag/commit을 source와 artifact 단계 모두에서 대조한다. sync writer만 identity를 생성하고 release 경로는 verifier로만 차단하는 원칙을 유지한다.
4. bundled studio manifest의 `source_cargo_lock_sha256`을 target upstream checkout의 root `Cargo.lock`과 비교한 sync 근거를 release record에 연결한다. 일반 release workflow가 writer나 sync를 재실행해 후보를 조용히 바꾸지 않게 한다.
5. strict `librhwp.a` byte 검증과 portable source/header/FFI 검증을 하나의 성공으로 합치지 않는다. strict mismatch가 재현되면 toolchain·archive 차이와 portable 결과를 보고하고 rehearsal 진입 전 release owner가 허용 경계를 판정한다.
6. `origin/main` 전용 3개 commit을 first-parent, patch와 이전 release record로 분석한다. 필요한 back-merge는 release source 변경과 섞지 않고 별도 PR/승인 gate로 처리한다.
7. `v0.1.9..candidate`의 merge PR, PR body, 연결 Issue와 최종 보고서를 근거로 포함 PR 분석 표를 만든다. 직전 release 종료 정리와 단순 transport는 신규 사용자-facing 변화에서 제외한다.
8. 공개 문구는 사용자가 실제로 보는 저장, PDF·인쇄, viewer/editor 호환, Finder preview/thumbnail 변화만 주요 변경으로 설명한다. provenance, workflow default, 분석 telemetry와 단순 version bump는 운영·기술 세부로 분리한다.
9. rehearsal artifact, pre-public draft DMG와 official public DMG를 서로 다른 계층으로 관리한다. rehearsal/draft URL이나 SHA256을 Sparkle, Pages 또는 Homebrew 입력으로 사용하지 않는다.
10. signed/notarized draft DMG 설치 smoke를 official publish 전 차단 gate로 둔다. 실제 앱·Finder provider, 저장·재열기, PDF·인쇄 시작, 업데이트 결과를 실행 여부까지 구분해 기록한다.
11. `require_latest_rhwp=true`, `include_rhwp_in_title=true`를 제안한다. 실행 직전 upstream latest가 바뀌면 publish를 중단하고 새 sync 또는 명시적 예외 승인 여부를 확인한다.
12. official publish, Pages/Sparkle와 Homebrew는 각각 별도 승인 후 수행한다. publish 후 문구·record 보정은 하나의 릴리즈 종료 정리 단계로 모은다.

## 잠정 단계

1. Stage 1: release context와 source identity 확정
   - 최신 앱/upstream release, `main`, `devel`, candidate commit, tag와 `v0.1.9..candidate` 범위를 live 조회한다.
   - `origin/main` 전용 3개 commit과 back-merge 필요성을 판정한다.
   - app/extension version, workflow default, core/studio provenance와 Cask current 상태를 inventory한다.
   - 승인된 identity에 따라 source version/build와 workflow 기본 입력을 정렬한다.
2. Stage 2: 포함 PR 분석과 release communication 작성
   - merge PR, PR body, 연결 Issue와 최종 보고서를 분류해 포함 PR 분석 표를 작성한다.
   - release record, README, Pages 업데이트 문서와 release note 초안을 작성·검증한다.
   - 사용자-facing 변화, 기술 세부, 보안 경계, 알려진 한계와 미실행 수동 gate를 구분한다.
3. Stage 3: source preflight와 rehearsal
   - core/studio/build-info/Cargo fingerprint provenance, strict/portable artifact, ABI/tests, app target, renderer와 universal Release package를 검증한다.
   - 별도 승인 후 Rehearsal workflow 또는 동등한 local rehearsal을 실행한다.
   - rehearsal checksum, DMG layout, delta checklist와 artifact 계층을 확인한다.
4. Stage 4: branch 정렬, release PR/tag와 pre-public signed candidate
   - 필요한 경우 별도 승인으로 `main -> devel` back-merge PR을 먼저 반영한다.
   - 별도 승인 후 `devel -> main` release PR을 생성·검증·merge하고 final candidate를 고정한다.
   - 별도 승인 후 정확한 final candidate에 annotated `v0.1.10` tag를 생성한다.
   - 별도 승인 후 draft Publish를 실행하고 signed/notarized DMG 설치 smoke와 수동 차단 gate를 수행한다.
5. Stage 5: official stable publish와 public surface
   - draft smoke 통과 후 별도 승인으로 official stable Publish를 실행한다.
   - GitHub Release, public DMG, Pages, stable appcast, Sparkle update와 설치본 Finder smoke를 확인한다.
   - public DMG SHA256 확정 뒤 별도 승인으로 Homebrew tap을 반영하고 검증한다.
6. Stage 6: release record, 최종 보고와 종료 정리
   - 실제 tag/commit, workflow run, DMG URL/SHA256, public surface, 수동 smoke와 미실행 항목을 release record와 최종 보고서에 확정한다.
   - publish 이후 문구/record 보정은 하나의 종료 정리 단계와 PR로 묶는다.
   - Task #472 PR·Issue close와 branch/worktree cleanup 조건을 확정한다.

각 Stage 종료 시 `task-stage-report` 절차로 변경과 단계 보고서를 검증·커밋하고 다음 Stage 승인을 요청한다. Stage 안에서도 rehearsal, branch 정렬 PR, `main` merge, tag, draft Publish, official Publish와 Homebrew는 위에 명시한 별도 실행 승인을 받아야 한다.

## 리스크

- Stage 1 전후로 `devel`에 다른 PR이 merge되면 candidate commit과 포함 PR 분석 범위가 달라진다. candidate 이동을 조용히 흡수하지 않고 release owner에게 재확정받는다.
- `origin/main`에만 있는 3개 commit을 확인하지 않고 release PR을 만들면 Pages·release 기록 이력이 누락되거나 충돌할 수 있다. patch와 tree 관계를 조사한 뒤 back-merge 필요성을 별도 승인받는다.
- local toolchain의 strict `librhwp.a` byte hash/size가 reference와 다르다. portable source/header/FFI 통과만으로 strict 통과라고 기록하거나 lock을 임의 갱신하지 않는다.
- upstream latest가 `v0.8.4` 이후로 이동하면 `require_latest_rhwp=true`가 publish를 차단한다. guard를 임의로 해제하지 않고 새 sync 또는 명시적 예외 판단으로 분리한다.
- v0.8.3 누적 변경에는 암호 문서, 중첩 표, 선택·복사와 렌더링 보정이 포함된다. v0.8.4 자체의 배포 채널 복원 설명만 보고 app-facing smoke를 축소하지 않는다.
- source build와 headless policy test는 실제 Finder Preview, PlugInKit provider 선택, LaunchServices cache와 signed 설치본 동작을 대체하지 못한다.
- LaunchServices stale record를 지우기 위한 전역 reset은 다른 앱 연결에도 영향을 줄 수 있다. 활성 provider가 release candidate 하나인지가 판정 기준이며, 표준 대상별 unregister 범위를 우선한다.
- HWP/HWPX 저장과 재열기, PDF·인쇄 WebKit 경계는 자동 renderer test만으로 충분하지 않다. draft 설치본에서 representative manual smoke 결과를 별도로 기록한다.
- rehearsal, draft와 official DMG를 혼동하면 Pages, Sparkle enclosure 또는 Homebrew SHA256이 잘못될 수 있다.
- signing/notarization, Sparkle appcast와 Pages는 GitHub Actions environment와 secret에 의존한다. secret 값은 읽거나 기록하지 않고 존재 여부와 workflow 결과만 확인한다.
- Intel Mac 실기기 smoke를 수행하지 못하면 universal binary 검증과 별개로 미실행 사유와 잔여 위험을 남긴다.
- official publish 이후 사용자-facing 문구 수정이 필요하면 public surface와 release record가 일시적으로 어긋날 수 있다. 하나의 종료 정리 단계로 모아 최종 상태를 다시 검증한다.

## 승인 요청 사항

1. release identity를 `v0.1.10 (16)`, previous release `v0.1.9`, expected core/studio `rhwp v0.8.4` / `496333b...`로 고정한다.
2. release title에는 upstream 반영이 주요 변화 중 하나이므로 `(rhwp v0.8.4)`를 포함하고, 실행 시점에도 upstream latest가 같으면 `require_latest_rhwp=true`를 사용한다.
3. 기준 브랜치는 `devel`, 작업 브랜치는 `local/task472`, 메인 worktree를 사용한다.
4. 위 6개 잠정 단계와 각 단계 종료 승인 gate를 사용한다.
5. Stage 1에서 `origin/main` 전용 3개 commit을 조사하고, 필요한 back-merge는 release source 변경과 분리된 별도 PR·승인으로 처리한다.
6. strict static archive mismatch가 재현되면 rehearsal 전에 strict/portable 결과와 artifact 근거를 다시 보고하고 release owner의 별도 판정을 받는다.
7. 실제 HWP/HWPX 저장·재열기, PDF 저장·인쇄 시작, Finder Preview/Thumbnail, Sparkle update와 signed/notarized draft 설치 smoke를 official publish 전 차단 gate로 둔다.
8. stale LaunchServices record 자체는 전역 reset 사유로 삼지 않고, 활성 provider path와 release candidate 설치본 동작을 판정 기준으로 사용한다.
9. rehearsal, branch 정렬 PR, `devel -> main` merge, annotated tag, draft Publish, official Publish, Pages/Sparkle와 Homebrew 반영은 각각 실행 시점에 별도 승인을 받는다.
10. publish 이후 release communication과 record 보정이 필요하면 하나의 릴리즈 종료 정리 단계와 PR로 묶는다.

이 수행계획서 승인 전에는 구현계획서 작성, source/version/release communication 변경, workflow 실행, `main` 반영, tag 생성 또는 배포 실행을 진행하지 않는다.
