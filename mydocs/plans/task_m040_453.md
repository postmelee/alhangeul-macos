# Task M040 #453 수행계획서

## 목적

알한글의 로컬·오프라인 우선 동작을 유지하면서 신규 설치 후 최초 실행, 기능 도입 이전 설치본의 최초 관측, 실제 버전 업데이트 전환을 익명 이벤트로 구분한다. 영구 사용자·기기·설치 식별자 없이 최소 payload만 공개 수집기로 보내고, 네트워크 장애나 분석 수집 실패가 앱 실행·문서 기능·Sparkle 업데이트에 영향을 주지 않는 비차단 구조를 구현한다.

## 배경

GitHub Release DMG 다운로드와 Homebrew 설치 이벤트만으로는 설치 완료, 최초 실행, Sparkle 업데이트 전환을 구분할 수 없다. 분석 저장소의 Issue #10과 PR #12에서 Cloudflare Worker 공개 수집기와 `occurred_date` 기준 집계 계약이 구현·병합됐고, Issue #11과 PR #13에서 37개 UTC 날짜 재조회, SQLite·CSV 보존, 비공개 대시보드 표시까지 완료됐다.

현재 HostApp의 `UpdateController`는 `SPUStandardUpdaterController`에 updater delegate를 연결하지 않으며, 앱 실행 버전 전환 상태와 분석 outbox도 소유하지 않는다. HostApp에는 이미 outbound network entitlement가 있고 Sparkle appcast를 사용하지만, Sparkle System Profiling과 영구 식별자 기반 분석은 사용하지 않는다.

공개 수집기는 `POST /v1/install-events`에서 UUID v4 `event_id`, `event_type`, UTC `occurred_date`, 이전·대상 버전, 업데이트 채널만 허용한다. 서버는 같은 `event_id`를 7일 동안 중복 제거하고 발생일이 36일을 초과해 오래된 이벤트는 거부한다. 앱은 이 계약에 맞춰 미시도 이벤트 30일 보관, 첫 요청 시작 후 6일 재시도, 64건 FIFO 상한을 지켜야 한다.

## 설계 방향

분석 기능은 `Sources/HostApp` 내부의 독립 서비스 경계로 둔다. 이벤트 모델·버전 전환 판별·outbox 보존 정책·응답 분류는 Foundation 기반의 테스트 가능한 순수 로직으로 분리하고, AppKit/SwiftUI 앱 생명주기와 Sparkle delegate 연결은 얇은 coordinator가 담당한다. `Sources/RhwpCoreBridge`와 문서 데이터 흐름은 변경하지 않는다.

최초 계측 실행에서는 영구 설치 ID를 새로 만들지 않는다. 분석 전용 상태가 없고 이전 버전이 남긴 앱 소유 `UserDefaults` 상태가 확인되면 `existing_baseline`, 이전 실행 증거가 없으면 `first_launch`로 분류한다. 이 방식은 기능 도입 전에 설치했지만 한 번도 실행하지 않았거나 설정을 삭제한 설치본을 완벽히 구분할 수 없으므로, 대시보드와 문서의 “관측된 익명 이벤트” 한계를 유지한다.

Sparkle 경로는 `SPUUpdaterDelegate`에서 `willInstallUpdate` 시점에 pending 전환만 로컬 저장하고 네트워크 요청을 만들지 않는다. 다음 앱 실행에서 현재 버전이 pending 대상 버전과 정확히 일치할 때만 `update(from → to, channel=sparkle)`를 생성한다. 취소·실패·대상 불일치는 성공 이벤트로 만들지 않고, 외부 설치로 확인된 버전 변경은 별도 전환 판별 규칙으로 처리한다.

Outbox에는 전송 payload와 로컬 bookkeeping인 생성 시각·최초 전송 시각만 저장한다. 만료 제거 후에도 64건을 초과하면 가장 오래된 이벤트부터 폐기한다. flush는 앱 실행당 한 번만 비동기로 시작하고, 연결 불가 시 요청 없이 종료한다. 요청 timeout은 5초 이하로 고정하며 event ID·payload·outbox 내용을 로그에 남기지 않는다.

분석은 기본 활성화하되 사용자가 앱 설정에서 비활성화할 수 있는 opt-out 구조를 우선안으로 둔다. 설정 화면에는 네트워크에 도달한 익명 실행·버전 전환 이벤트만 수집하고 전체 설치 수나 고유 사용자 수를 뜻하지 않으며 문서·계정·기기 식별자를 수집하지 않는다는 설명을 표시한다. 공개 수집기 URL은 비밀값이 아니므로 앱 설정에 고정할 수 있지만, 집계 조회 token이나 운영 secret은 앱 bundle에 포함하지 않는다.

## 리스크

- 영구 설치 ID를 사용하지 않으므로 첫 계측 버전에서 기존 설치와 신규 설치를 모든 환경에서 완벽히 구분할 수 없다.
- 이전 버전의 앱 소유 상태가 없거나 사용자가 설정을 삭제하면 기존 설치가 `first_launch`로 관측될 수 있다.
- Sparkle delegate callback과 앱 재실행 사이의 pending 상태가 손상되거나 대상 버전이 달라지면 false update를 만들지 않도록 보수적으로 폐기해야 한다.
- 앱이 여러 창을 만들더라도 flush pass는 프로세스 실행당 한 번이어야 하며 SwiftUI scene 생명주기에 직접 묶으면 중복 실행될 수 있다.
- 비동기 URLSession completion과 앱 종료가 겹치면 첫 시도 시각과 outbox 저장의 원자성이 깨질 수 있다.
- 날짜 경계와 재시도 기간은 UTC 기준이어야 하며 로컬 시간대·일광절약시간의 영향을 받으면 안 된다.
- 기본 활성화 분석에 대한 사용자 기대가 다를 수 있으므로 수집 범위와 비활성화 경로를 명확히 표시해야 한다.
- 공개 endpoint 장애·rate limit·Cloudflare 정책 변화가 있어도 앱 기능은 정상이어야 한다.

## 승인 요청 사항

- 영구 식별자 없이 확인 가능한 이전 앱 상태만 `existing_baseline` 근거로 사용하고, 식별 불가능한 첫 실행은 `first_launch`로 처리하는 한계를 승인 요청한다.
- 익명 분석 기본 활성화와 설정 화면 opt-out, 비활성화 시 기존 outbox 즉시 제거 정책을 승인 요청한다.
- 이 수행계획을 기준으로 구현계획서 작성 단계 진행 승인을 요청한다.
