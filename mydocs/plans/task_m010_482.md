# Task M010 #482 수행계획서

## 목적

평문 HWP3 문서를 WKWebView 기반 HostApp에서 저장할 때 HWP5 출력이 형식 변환 안내 없이 HWP3 원본을 덮어쓰는 회귀를 차단한다.

HWP3 원형 serializer가 없는 현재 범위에서는 일반 저장과 다른 이름 저장 모두 원본 형식 비보존을 명확히 안내하고, 사용자가 선택한 원본과 다른 신규 경로에 HWP5 또는 HWPX 변환 복사본을 저장하도록 계약을 고정한다. 기존 평문 HWP5/HWPX의 정상적인 in-place 저장은 유지한다.

## 배경

현재 `DocumentSaveCommand`와 `DocumentSaveFormat`은 URL·파일명의 확장자로 `.hwp`와 `.hwpx`를 구분한다. HWP3와 HWP5는 모두 `.hwp` 확장자를 사용하므로 평문 HWP3는 `DocumentSaveProtectionPolicy.allowsInPlaceSave(.plain)`과 `.hwp` 형식 일치 조건을 통과한다. 그러나 bundled rhwp Studio의 HWP exporter는 HWP3 원형이 아니라 HWP5 CFB payload를 생성한다.

그 결과 평문 HWP3에서 `Command+S`를 실행하면 native 저장 경로가 HWP5 bytes를 원본 URL에 atomic write할 수 있다. #480과 PR #481은 암호·미지원·판정 불능 문서의 무경고 평문화 overwrite를 막았고, `RhwpStudioDocumentPayload.isHWP3Source`로 원본 bytes 기반 HWP3 식별도 이미 보유한다. 다만 평문 HWP3에는 보호 해제 경고가 발생하지 않아 형식 변환과 원본 비보존 정책이 아직 적용되지 않는다.

## 범위

포함:

- 사용자 원본이 아닌 공개 또는 저장소 테스트 fixture 복사본으로 평문 HWP3의 일반 저장 결과가 HWP5로 변환되는 조건을 재현하고 원본 hash 기준을 고정한다.
- 확장자가 아니라 원본 payload signature로 HWP3 source identity를 판정하고 저장 요청에 캡처한다.
- 평문 HWP3의 in-place 저장을 금지하고 HWP5/HWPX 변환 안내 뒤 save panel로 전환한다.
- 원본과 같은 canonical 경로 및 기존 파일 destination을 거부하고 신규 경로만 허용한다.
- 변환 복사본임을 드러내는 기본 파일명을 제안한다.
- export 전, payload 응답 뒤, write 직전까지 문서 revision·source identity·destination 정책을 재검증한다.
- 저장 성공 뒤 current payload/source URL을 실제 HWP5 또는 HWPX 결과로 갱신해 후속 저장 정책이 새 형식을 기준으로 동작하게 한다.
- 기존 평문 HWP5/HWPX in-place 저장과 #480 보호 문서 평문 복사본 정책의 회귀를 검증한다.
- 사용자 안내와 known limitation을 실제 HWP3 변환 정책에 맞게 보정한다.

제외:

- HWP3 원형 serializer 신규 구현 또는 upstream exporter 알고리즘 변경
- HWP3 문서를 HWP3 형식으로 다시 저장하는 기능
- native 암호 저장과 password-export RPC 연결(#480 Stage 3·4)
- bundled Studio minified JavaScript 수동 수정
- 새 upstream ref sync, public release, 서명, 공증 또는 배포 작업

## 설계 방향

1. `isHWP3Source`처럼 원본 bytes에서 얻은 source identity를 진실 원천으로 사용하고 `.hwp` 확장자는 HWP3/HWP5 구분에 사용하지 않는다.
2. 문서 보호 정책과 형식 변환 정책을 분리한다. 보호 상태가 평문이어도 HWP3 source이면 in-place 저장을 허용하지 않으며, 보호된 HWP3는 보호 해제와 형식 변환을 하나의 사용자 결정 흐름으로 안내해 중복 경고를 피한다.
3. HWP3 변환 요청은 `원본과 다른 신규 destination`을 fail-closed로 강제한다. canonical URL 비교로 원본·별칭 경로를 거부하고, 기존 파일 overwrite도 거부한다.
4. 기본 파일명은 `원본 (변환 복사본).hwp` 또는 `.hwpx`처럼 원본 비보존을 드러내고, 보호 해제까지 동반되면 보호·변환 의미가 모두 오해 없이 전달되도록 명명 규칙을 확정한다.
5. pending save request에 source identity와 변환 의도를 캡처한다. save panel 대기 중 다른 문서가 열리거나 payload가 바뀌면 export/write를 중단한다.
6. HWP exporter 결과는 기존 signature 검증을 유지하고, 저장 성공 뒤 `RhwpStudioDocumentPayload.data`를 출력 bytes로 교체한다. 따라서 HWP5 변환본의 후속 `Command+S`는 더 이상 HWP3 변환 경고를 반복하지 않아야 한다.
7. 취소·정책 거부·export 실패·write 실패에서는 원본 byte hash와 현재 문서 저장 상태를 변경하지 않는다. 변환 payload는 같은 디렉터리의 임시 파일에 완성한 뒤 기존 destination을 교체하지 않는 배타적 rename으로 게시해, write 실패 시 잘린 destination도 남기지 않는다.

## 잠정 단계

1. Stage 1: exact `devel` 기준 평문 HWP3 일반 저장을 재현하고, source identity·변환 출력 signature·원본 hash·신규 destination 계약을 확정한다.
2. Stage 2: HWP3 변환 정책, 경고, 기본 파일명, pending request 재검증을 구현하고 HostApp 단위 회귀를 추가한다.
3. Stage 3: HWP3 → HWP5/HWPX fixture smoke, 기존 HWP5/HWPX 및 #480 보호 문서 저장 회귀, HostApp build와 사용자 문서 보정을 완료한다.

각 단계의 산출물·검증·커밋 경계는 수행계획 승인 뒤 별도 구현계획서에서 확정한다. Stage 1 결과 upstream 변경이 필요하다고 판단되면 해당 변경은 별도 이슈와 승인 대상으로 분리하고, 이 타스크에서 임의로 upstream ref를 바꾸지 않는다.

- 취소, 원본과 같은 destination, 기존 파일 destination, export/write 실패에서 원본 SHA-256 유지
- 신규 destination의 HWP5/HWPX signature와 요청 확장자 일치
- 저장 성공 뒤 source URL·payload·dirty/clean 상태 동기화

## 리스크

- HWP3와 HWP5가 같은 `.hwp` 확장자를 사용하므로 URL 기반 판정으로 되돌아가면 회귀가 재발한다. source payload identity를 pending request와 테스트에 고정해야 한다.
- 보호 상태와 변환 상태를 한 enum에 섞으면 #480 정책 조합이 복잡해지고 경고가 중복될 수 있다. 독립 정책을 합성하고 사용자 결정은 한 번만 받는다.
- save panel이 기존 파일 overwrite 확인을 제공하더라도 HWP3 변환 정책은 원본 비보존 위험 때문에 기존 파일 destination을 별도로 거부해야 한다.
- 저장 성공 뒤 payload가 HWP3 원본 bytes로 남으면 변환 경고가 반복되거나 후속 저장 대상이 잘못 분류될 수 있다. 출력 payload로 source identity가 전환되는지 검증한다.
- HWP3 fixture에 외부 문서나 민감 정보가 포함될 수 있다. 공개·비민감 fixture만 사용하고 사용자 원본은 수정하지 않는다.
- 문서 안내가 이미 공개된 v0.1.10의 실제 동작과 다음 릴리스 후보의 수정 동작을 혼동시킬 수 있다. v0.1.10 문서에는 배포본의 원본 덮어쓰기 위험을 명시하고, 수정된 보호 해제·형식 변환 동작은 현재 기능 설명과 다음 릴리스 기록으로 분리한다.

## 승인 요청 사항

- 위 포함·제외 범위와 3단계 잠정 진행 순서를 수행계획으로 승인받는다.
- HWP3 변환 저장은 원본과 같은 경로뿐 아니라 다른 기존 파일 destination도 거부하고 신규 경로만 허용하는 fail-closed 정책으로 진행한다.
- Stage 1에서는 사용자 원본이 아닌 공개·비민감 fixture 복사본으로 HWP3 → HWP5/HWPX 변환과 원본 hash 보존을 조사한다.
- 수행계획 승인 후에만 구현계획서 `mydocs/plans/task_m010_482_impl.md`를 작성하고, 구현계획 승인 전에는 소스·매뉴얼·테스트를 변경하지 않는다.
