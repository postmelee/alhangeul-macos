# Task M020 #406 수행계획서

## 목적

HOP가 설치된 macOS 환경에서도 HOP가 등록한 `.hwp`, `.hwpx` 문서 타입을 알한글의 지원 대상으로 인식하게 한다.

완료 후에는 LaunchServices가 문서를 `net.golbin.hop.hwp` 또는 `net.golbin.hop.hwpx`로 분류하더라도 Finder의 `다음으로 열기`와 기본 앱 후보에 알한글이 표시될 수 있어야 한다. 같은 문서 타입이 Quick Look preview, Finder thumbnail, 앱 내부 열기 패널에서도 일관되게 처리되어야 한다.

## 배경

알한글 v0.1.7과 macOS 26.5.1을 사용하는 환경에서 HWP/HWPX 파일의 기본 앱 후보에 알한글이 나타나지 않는다는 사용자 제보가 접수됐다. 제보 화면에서는 HOP가 기본 앱으로 등록되어 있었고, Hancom Office Viewer는 후보에 표시되지만 알한글은 표시되지 않았다.

HOP `golbin/hop`의 macOS file association 설정을 확인한 결과, HOP는 자체 UTI인 `net.golbin.hop.hwp`와 `net.golbin.hop.hwpx`를 exported type으로 등록한다. 현재 알한글은 자체 UTI, Hancom 계열 UTI, LibreOffice HWP UTI를 지원하지만 HOP UTI는 HostApp 문서 타입, imported type, Quick Look/Thumbnail 지원 목록, 앱 내부 열기 패널에 포함하지 않는다.

따라서 LaunchServices가 HOP가 설치된 환경의 문서를 HOP UTI로 분류하면 알한글이 호환 앱 또는 extension provider 후보에서 빠질 가능성이 있다. 다만 사용자 파일의 실제 `mdls` 결과를 아직 확보하지 않았으므로, HOP UTI 누락을 재현 가능한 호환성 결함으로 다루되 제보 환경의 단일 확정 원인으로 단정하지 않는다.

## 범위(포함·제외)

포함:

- HostApp 문서 타입에 `net.golbin.hop.hwp`, `net.golbin.hop.hwpx` 지원 추가
- HostApp `UTImportedTypeDeclarations`에 HOP HWP/HWPX 호환 타입 추가
- Quick Look preview와 Finder thumbnail의 `QLSupportedContentTypes`에 HOP UTI 추가
- 앱 내부 열기 패널의 supported content types에 HOP UTI 추가
- plist 정적 검사, HostApp 빌드, HWP/HWPX 문서 열기 회귀 확인
- HOP 설치 환경 또는 HOP UTI로 분류되는 검증 환경에서 `mdls`, LaunchServices, Quick Look/Thumbnail smoke 확인
- 필요한 경우 Finder 통합 troubleshooting 문서에 third-party UTI 확인 기준 보강
- 수행계획서, 구현계획서, 단계 보고서, 최종 보고서, 오늘할일 갱신

제외:

- HOP 애플리케이션 또는 HOP 저장소 변경
- macOS 기본 앱을 알한글로 강제 지정하거나 사용자 설정을 자동 변경하는 기능
- 전역 LaunchServices reset 또는 Finder/Quick Look daemon 강제 종료를 일반 해결책으로 추가
- HOP 외 신규 third-party HWP/HWPX UTI 전수 조사
- 문서 parser 또는 renderer 품질 변경
- release packaging, signing, notarization, Homebrew Cask 변경

## 설계 방향

HOP UTI는 알한글이 소유하는 exported UTI가 아니라 외부 앱이 소유하는 호환 타입으로 취급한다. HostApp의 `UTImportedTypeDeclarations`에는 HOP 설정과 일치하는 identifier, 확장자, conforming type을 선언하고 기존 `CFBundleDocumentTypes`의 `LSHandlerRank=Alternate`와 `CFBundleTypeRole=Viewer`는 유지한다. HWPX의 MIME type은 HOP 선언과 일치하는 `application/vnd.hancom.hwpx`를 사용하되, 기존 알한글 exported HWPX 타입의 MIME 선언은 변경하지 않는다.

라우팅 표면은 다음 네 군데를 동일한 UTI 집합으로 맞춘다.

1. HostApp `CFBundleDocumentTypes > LSItemContentTypes`
2. HostApp `UTImportedTypeDeclarations`
3. Quick Look preview와 Finder thumbnail의 `QLSupportedContentTypes`
4. `DocumentOpenPanel.supportedContentTypes`

이 변경은 파일 내용을 신뢰하는 범위를 넓히지 않는다. HOP UTI로 라우팅된 문서도 기존 HWP/HWPX 입력 검증, parser, renderer, fallback 정책을 그대로 통과한다. Finder 기본 앱 선택 가능 여부는 LaunchServices가 결정하므로 앱은 호환 타입을 정확히 선언하고 설치본 기준 등록 결과를 검증하는 데까지만 책임진다.

가능하면 HOP 설치 상태에서 원본 샘플 복사본의 `mdls` 결과와 Finder `다음으로 열기` 후보를 확인한다. 같은 UTI 선택을 재현하지 못하면 plist와 build 산출물의 선언 검증을 필수 gate로 두고, 실제 HOP 공존 환경 검증은 수동 항목과 잔여 리스크로 명시한다.

## 잠정 단계(3~6단계)

1. Stage 1: HOP UTI 계약과 알한글 지원 표면 재확인
   - HOP의 HWP/HWPX identifier, extension, MIME type, conforming type을 기준 자료와 대조한다.
   - 알한글의 HostApp, Quick Look, Thumbnail, 앱 내부 열기 패널에서 누락 지점을 확정한다.
   - 정적 검증과 설치본 smoke의 판정 기준을 구분한다.
2. Stage 2: HOP HWP/HWPX UTI 호환 선언 구현
   - HostApp 문서 타입과 imported type 선언을 추가한다.
   - Quick Look/Thumbnail 지원 타입과 앱 내부 열기 패널 지원 타입을 같은 기준으로 갱신한다.
   - plist syntax와 Swift compile 결과를 검증한다.
3. Stage 3: HOP 공존 Finder 통합과 문서 열기 smoke 검증
   - 설치본 기준 bundle 선언, LaunchServices/PlugInKit 등록, HWP/HWPX routing을 확인한다.
   - 가능한 환경에서 `mdls`, Finder `다음으로 열기`, `qlmanage` 결과를 확인한다.
   - 재현되지 않는 사용자 환경 의존 항목과 안내 문서 보강 필요성을 분리한다.
4. Stage 4: 통합 검증과 최종 보고
   - 정적 검사, build, HWP/HWPX 열기, Finder/Quick Look/Thumbnail 검증 결과를 정리한다.
   - 잔여 리스크와 사용자에게 안내 가능한 적용 범위를 최종 보고서에 기록한다.

```bash
scripts/check-extension-registration-hygiene.sh --check-only
```

Finder `다음으로 열기` 후보와 앱 내부 열기 패널은 GUI 수동 smoke 항목으로 분리한다. 개발 산출물 등록 해제가 필요하면 표준 smoke helper의 승인된 범위만 사용하며, 전역 LaunchServices reset은 수행하지 않는다.

## 리스크

- LaunchServices의 실제 content type 선택과 기본 앱 후보는 앱 설치 순서, 캐시, 기존 기본 앱, 다른 HWP 지원 앱의 UTI 선언에 영향을 받는다. 정적 선언이 올바르더라도 제보 환경과 동일한 후보 목록을 로컬에서 재현하지 못할 수 있다.
- 사용자 파일의 `mdls` 결과가 아직 없어 실제 선택 UTI가 HOP 타입인지 확정되지 않았다. HOP UTI 추가 후에도 증상이 남으면 설치 위치, 앱 최초 실행, LaunchServices 등록 상태를 별도 진단해야 한다.
- HOP가 향후 identifier, MIME type, conforming type을 변경하면 이번 imported declaration과 차이가 생길 수 있다. 검증 기록에 확인한 HOP source revision을 남겨야 한다.
- imported UTI를 추가해도 이미 캐시된 Finder/Quick Look 결과는 즉시 갱신되지 않을 수 있다. 검증은 fresh sample과 설치본 active path를 기준으로 수행해야 한다.
- `DocumentOpenPanel`은 현재 `.data` fallback을 포함하므로 HOP UTI 추가만으로 사용자 체감 변화가 크지 않을 수 있다. 그래도 지원 타입 목록의 일관성과 향후 fallback 축소 가능성을 위해 명시적으로 포함한다.
