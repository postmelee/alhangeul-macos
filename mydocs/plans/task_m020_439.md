# Task M020 #439 수행계획서

## 목적

upstream `rhwp` full sync 과정에서 `rhwp-core.lock`만 갱신되고 `Sources/RhwpCoreBridge/RhwpCoreBuildInfo.swift`가 이전 release 정보에 머무르는 재발 경로를 제거한다.

core release tag, resolved commit, enabled feature를 단일 자동 갱신 경로로 맞추고, upstream sync PR과 일반 PR CI 및 release workflow에서 불일치를 차단하는 검증 gate를 구축한다. 이를 통해 `HwpThumbnailRenderSignature`가 실제 bundled core identity를 반영하고, stale thumbnail cache signature가 남지 않게 한다.

## 배경

PR #436의 `rhwp v0.8.2` full sync 후보는 `rhwp-core.lock`, Rust dependency와 bundled `rhwp-studio`를 갱신했지만 `RhwpCoreBuildInfo.swift`는 이전 `v0.7.18` 값에 머물렀다. Task #438 Stage 2에서 이 불일치를 독립 검증으로 발견해 PR #436 branch에 최소 보정 commit을 추가했으며, 유사한 수동 보정이 Task #418에서도 필요했다.

현재 저장소에는 `scripts/verify-rhwp-core-build-info.sh`가 있어 lock과 Swift 상수의 release tag, commit, enabled features를 비교할 수 있다. 그러나 `scripts/update-rhwp-core.sh`는 Cargo dependency와 `rhwp-core.lock` skeleton만 갱신하고 build info를 생성하지 않는다. `.github/workflows/rhwp-upstream-sync-pr.yml`도 build info를 갱신·stage·검증하지 않으며, PR CI와 release workflow는 기존 verifier를 필수 gate로 호출하지 않는다.

그 결과 자동 생성된 PR #463도 `rhwp-core.lock`은 `v0.8.4`를 가리키지만 build info는 `v0.8.2`에 남은 상태에서 CI가 성공했다. Task #439를 먼저 완료한 뒤 Issue #375를 별도 타스크로 진행하고, 두 자동화가 `devel`에 반영된 다음 v0.8.4 sync PR을 재생성한다.

## 범위

포함:

- `rhwp-core.lock`에서 release tag, resolved commit, enabled features를 읽어 `RhwpCoreBuildInfo.swift`를 deterministic하게 생성·갱신하는 단일 helper 계약을 정한다.
- stable release tag와 현재 lock version 2를 기준으로 build info 갱신과 검증을 연결한다.
- 기존 `scripts/verify-rhwp-core-build-info.sh`를 자동 갱신 helper와 일관된 key·오류 계약으로 정리한다.
- isolated fixture에서 정상 상태, stale tag, stale commit, stale feature, 누락 key와 갱신 후 수렴을 검증하는 helper test를 추가한다.
- upstream full sync workflow가 lock update 뒤 build info를 갱신하고 검증하며 PR 변경에 stage하도록 한다.
- PR CI가 관련 source·helper·workflow 변경 및 core pin 변경에서 build info verifier를 실행하도록 한다.
- release rehearsal과 publish source preflight에서 build info 정합성을 필수 gate로 확인한다.
- generated sync PR 본문과 checklist가 자동 갱신·검증 결과를 표시하도록 한다.
- core dependency와 CI/release 운영 문서를 새 자동 계약에 맞게 갱신한다.

제외:

- upstream `rhwp` 버전 자체 갱신과 PR #463의 수동 보정·merge
- Issue #375의 `source_cargo_lock_sha256` 실제 upstream 비교 자동화
- `RhwpCoreBuildInfo`에 새로운 제품 metadata를 추가하는 작업
- Thumbnail cache key 구조나 renderer 정책 변경
- Rust static archive strict/portable 검증 정책 변경
- signing, notarization, GitHub Release, Pages, Sparkle, Homebrew 배포 실행
- Issue #463 또는 다른 GitHub PR 상태 변경

## 설계 방향

1. `rhwp-core.lock`을 core identity의 진실 원천으로 유지한다. Swift build info나 workflow 입력값을 별도 진실 원천으로 만들지 않는다.
2. 갱신과 검증 책임을 분리한다. 전용 build-info writer helper를 우선 후보로 두고, `update-rhwp-core.sh`는 lock update 뒤 이 helper를 호출한다. verifier는 생성 결과가 lock과 일치하는지만 검사한다.
3. writer 출력은 고정된 Swift 형식과 key 순서를 사용해 같은 lock 입력에서 byte-identical 결과를 만든다. 값은 shell code나 Swift source injection이 되지 않도록 허용 형식과 quoting을 검증한다.
4. helper test는 tracked `rhwp-core.lock`과 `RhwpCoreBuildInfo.swift`를 직접 훼손하지 않고 `build.noindex/` 또는 임시 fixture 경로를 사용한다. 테스트 가능성을 위해 명시적인 input/output 인자 또는 안전한 test override 계약을 검토한다.
5. sync workflow는 `update-rhwp-core.sh` 이후 build info 갱신·검증을 수행하고 `Sources/RhwpCoreBridge/RhwpCoreBuildInfo.swift`를 명시적으로 stage한다. verification summary와 PR body에도 해당 gate를 기록한다.
6. PR CI와 release workflow는 verifier를 직접 호출해 자동 생성 경로 밖에서 생긴 수동 drift도 차단한다. 변경 분류가 verifier 실행을 누락하지 않도록 관련 path classification을 함께 확인한다.
7. #439와 #375는 workflow·문서 변경 파일이 겹칠 수 있으므로 #439를 독립 PR로 먼저 `devel`에 merge한 뒤 #375를 최신 `devel`에서 시작한다.
8. 현재 열린 PR #463의 갱신·폐기·재생성은 본 타스크의 코드 변경에 포함하지 않고 Task #439 merge 후 별도 승인 절차로 진행한다.

## 잠정 단계

1. Stage 1: current lock reader, update helper, verifier, path classification과 sync/PR/release workflow 호출 graph를 조사하고 build-info writer 및 fixture test 계약을 확정한다.
2. Stage 2: deterministic build-info writer, verifier 정합화와 isolated helper test를 구현하고 local success/failure 경로를 검증한다.
3. Stage 3: upstream sync, PR CI, release rehearsal/publish workflow에 갱신·검증·stage·summary gate를 연결하고 workflow/helper 정적 검증을 수행한다.
4. Stage 4: 관련 운영 문서와 generated PR checklist를 갱신하고 전체 회귀 검증 및 v0.8.4 sync 재생성 handoff 조건을 정리한다.

각 Stage 종료 시 `task-stage-report` 절차로 해당 단계 source와 보고서를 함께 검증·커밋하고 다음 Stage 승인을 요청한다.

## 리스크

- writer와 verifier가 각각 다른 lock parsing 규칙을 가지면 같은 drift가 다른 형태로 재발할 수 있다. 기존 `read-rhwp-core-lock.sh`를 재사용하고 지원 key를 한곳에서 고정해야 한다.
- build info writer가 tracked Swift 파일을 직접 덮어쓰므로 실패 중간 상태나 잘못된 quoting이 source를 손상할 수 있다. 임시 파일 검증 후 atomic replacement 또는 동등한 안전한 쓰기 방식을 검토한다.
- demo commit pin에는 stable release tag가 없을 수 있다. 현재 Swift build info가 stable release tag를 전제로 하므로 demo channel 동작을 무심코 깨뜨리지 않도록 지원 범위를 구현계획에서 명시해야 한다.
- workflow YAML과 embedded shell은 local syntax 검증만으로 GitHub expression·권한·runner 동작을 완전히 보장할 수 없다. PR CI와 실제 v0.8.4 sync workflow 재실행을 최종 운영 검증으로 분리한다.
- `classify-pr-changes.sh`의 path 분류가 불완전하면 verifier나 writer만 바뀐 PR에서 macOS/core gate가 skip될 수 있다.
- release rehearsal/publish workflow에 새 verifier를 추가하면 기존 stale build info가 있던 tag나 branch의 release가 중단될 수 있다. candidate source가 current lock과 일치하는지 먼저 확인한다.
- #375가 같은 workflow와 PR body를 후속으로 수정하므로 병렬 진행하면 충돌과 검증 기준 혼합이 생길 수 있다. #439 merge 후 최신 `devel`에서 #375를 시작한다.
- PR #463을 현재 상태에서 merge하면 stale build info 문제가 실제 release candidate에 들어간다. Task #439와 #375 반영 뒤 sync PR을 재생성할 때까지 merge를 보류한다.

## 승인 요청 사항

1. 기준 통합 브랜치를 `devel`, 작업 브랜치를 `local/task439`로 유지한다.
2. `rhwp-core.lock`을 단일 진실 원천으로 하고 deterministic build-info writer와 기존 verifier를 분리하는 방향을 승인한다.
3. 위 4개 잠정 단계와 isolated fixture, sync/PR/release workflow 검증 범위를 승인한다.
4. stable release 갱신 자동화를 우선 대상으로 하되 demo commit pin 동작을 Stage 1에서 조사해 구현계획에 명시하는 것을 승인한다.
5. Issue #375, PR #463 재생성, public release 실행은 Task #439 범위에서 제외하고 각각 후속 승인 절차로 진행한다.
6. 수행계획 승인 후에만 `task_m020_439_impl.md` 구현계획서와 실제 helper/workflow 변경을 시작한다.

수행계획서 승인 전에는 구현계획서 작성, helper·workflow·manual 변경, PR #463 상태 변경 또는 upstream sync workflow 실행을 진행하지 않는다.
