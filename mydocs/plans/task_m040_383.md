## 목적

GitHub 계정을 사용하지 않는 일반 사용자도 알한글 사용 중 발견한 오류, 렌더링 차이, 설치 문제, 기능 제안, 아쉬운 점을 공식 경로로 쉽게 제보할 수 있게 한다. 기존 GitHub Issues 중심 안내는 유지하되, 공식 이메일 `alhangeul.feedback@gmail.com`을 기본 제보 경로로 노출해 사용자 피드백 진입 장벽을 낮춘다.

## 배경

현재 공식 랜딩페이지는 헤더에서 업데이트, GitHub, 다운로드만 제공하고, FAQ의 오류 제보 안내도 GitHub Issues 중심으로 구성되어 있다. 개발자와 기여자에게는 GitHub Issues가 적합하지만, 비개발자나 GitHub 사용 경험이 없는 사용자는 앱 평가, 추천, 문서별 렌더링 차이, 설치 후 혼란을 공유하기 어렵다.

외부 커뮤니티에서 알한글 추천과 평가, 아쉬운 점이 공유되고 있으므로, 공식 랜딩페이지 안에서 이메일 제보와 GitHub Issue 제보를 함께 안내하는 사용자-facing 접점을 추가한다.

## 설계 방향

헤더의 `문의/제보`는 사용자의 메일 앱을 즉시 열지 않고 랜딩페이지 내 전용 섹션으로 이동하게 한다. 즉시 `mailto:`를 실행하면 사용자가 의도하지 않은 외부 앱 전환을 경험할 수 있고, 개인정보 주의나 제보에 필요한 정보를 먼저 안내하기 어렵기 때문이다.

문의/제보 섹션은 FAQ 근처의 사용자 지원 문맥에 배치한다. 이메일 버튼은 GitHub을 사용하지 않아도 되는 기본 제보 경로로 보이게 하고, GitHub Issues는 재현 절차와 공개 추적이 필요한 사용자에게 보조 경로로 제공한다.

메일 템플릿은 사용자가 바로 보낼 수 있을 만큼 짧게 유지하되 앱 버전, macOS 버전, 문서 형식, 증상, 재현 방법을 입력할 수 있게 한다. 문서 원본에는 개인정보가 있을 수 있으므로 원본 첨부를 기본 요구하지 않고, 필요한 경우 스크린샷이나 설명 위주로 보내도록 안내한다.

스타일은 기존 랜딩페이지의 Apple-like 정적 사이트 톤을 유지한다. 헤더 항목이 늘어나는 만큼 작은 화면에서 텍스트가 겹치거나 다운로드 버튼이 밀리지 않도록 반응형 여백과 글자 크기를 점검한다.

## 리스크

- 헤더 항목이 늘어나면 작은 화면에서 브랜드, 링크, 다운로드 버튼이 겹칠 수 있다.
- `mailto:` 링크는 사용자의 기본 메일 앱 설정에 의존하므로, 웹메일 사용자에게는 직접 주소 복사도 보이게 해야 할 수 있다.
- 문서 원본 제보를 쉽게 유도하면 개인정보가 포함된 파일을 받을 수 있으므로, 원본 첨부 주의 문구가 필요하다.
- GitHub Issues와 이메일 제보의 역할이 불명확하면 개발자용 공개 추적과 일반 사용자 문의가 섞일 수 있다.
- 외부 커뮤니티 링크는 맥락 참고용이며, 랜딩페이지에 직접 노출하지 않는 편이 안전하다.
