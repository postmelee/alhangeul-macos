- 브랜치: `local/task372`

## 목적

지원하지 않거나 잘못된 파일을 열었을 때 현재 viewer 영역과 마지막 정상 문서를 제거하지 않고, 사용자가 닫거나 다시 파일 선택을 시도할 수 있는 window-local 복구 모달을 제공한다. 파일 패널, Finder open, 최근 문서와 drag/drop에서 같은 recoverable opening failure 계약을 사용하고, viewer asset·navigation·WebContent process 실패의 기존 fatal fallback은 그대로 유지한다.

## 배경

선행 #149는 `HwpDocumentInputValidator`로 빈 파일과 HWP/HWPX signature mismatch를 조기에 구분하고, parser 단계의 `document-load-error`를 native failure로 전달하는 경로를 추가했다. #150은 viewer asset, resource/document scheme, navigation, timeout과 WebContent process 종료를 `RhwpStudioWebViewFailure` fatal fallback으로 분리했다.

현재 `DocumentViewerStore.loadDocument(from:)`는 파일 읽기나 opening validation이 실패하면 `errorMessage`를 설정한 뒤 `clearCurrentDocument()`를 호출한다. `DocumentViewerView`는 `errorMessage`가 있으면 전체 `RhwpStudioContainerView`를 `ErrorStateView`로 교체하므로, 직전에 정상적으로 열려 있던 문서와 viewer UI가 사라진다. drag/drop 실패도 현재 문서를 지운 뒤 5초 자동 소멸 banner만 표시한다. 이 동작은 재시도 가능한 사용자 입력 오류와 viewer 자체의 fatal failure를 같은 수준으로 다루는 문제가 있다.

반면 정상 load는 validation과 문서 보호 분류가 끝난 뒤 `finishDocumentLoad`에서 새 payload, filename, source document와 revision을 commit한다. 실패 시 기존 snapshot을 유지하고 별도 recoverable 상태만 표시하면, 정상 load의 commit 경계와 fatal WebView fallback을 크게 바꾸지 않고 Issue #372의 목표를 달성할 수 있다.

## 범위(포함·제외)

포함:

- 실패한 새 입력 때문에 기존 `rhwpStudioDocument`, `sourceDocument`, filename, revision과 unsaved 상태가 제거되지 않도록 store 전이 보강

## 설계 방향

recoverable opening failure는 기존 `errorMessage`, 자동 소멸 `webViewErrorMessage`, fatal `webViewFailure`와 분리된 명시적 상태로 둔다. 상태에는 사용자 안내에 필요한 제목·메시지와 실패 파일의 표시용 이름 정도만 포함하고, 절대 경로나 원본 bytes를 장기 보관하지 않는다. 동일 창에서는 한 번에 하나만 표시하며 새 실패가 발생하면 최신 시도를 대표한다.

새 문서 load는 성공 전까지 현재 정상 문서를 speculative replacement하지 않는 commit-on-success 원칙을 따른다. `beginDocumentLoad`는 진행 중 작업과 stale completion을 정리하되 기존 payload, source, filename, revision, unsaved 상태와 fatal failure를 불필요하게 지우지 않는다. validation이나 파일 읽기가 실패하면 loading 상태만 종료하고 recoverable failure를 표시한다. 성공한 `finishDocumentLoad`에서만 새 문서 상태를 교체하고 recoverable failure를 닫는다. 정상 문서가 없는 창에서 실패한 경우에도 empty viewer 상태를 유지해 다시 열기와 drop이 가능해야 한다.

UI는 `DocumentViewerView`가 기존 viewer/fatal fallback hierarchy 바깥에서 window-local modal을 presentation하도록 구성한다. `닫기`는 recoverable 상태만 해제하고 현재 문서에 영향을 주지 않는다. `다시 시도`는 모달을 해제한 뒤 `DocumentOpenPanel`을 다시 호출하며, 패널 취소는 기존 문서와 오류 상태를 변경하지 않는다. modal dismissal과 `NSOpenPanel.runModal()` 중첩을 피할 수 있도록 action 순서와 test seam을 구현계획에서 확정한다.

파일 패널과 drag/drop은 동일한 상태 전이 규칙을 사용하되 사용자 문구는 입력 경로를 구분할 수 있다. WebView가 문서를 받은 뒤 발생하는 fatal failure는 이번 범위에서 recoverable로 낮추지 않는다. 다만 Stage 1에서 `document-load-error`가 순수 사용자 입력 오류임이 확인되면, 현재 Issue 범위와 fatal 경계를 대조해 구현계획 승인 항목으로 별도 명시하고 승인 없이 확대하지 않는다.

자동 검증은 AppKit panel이나 실제 WebView를 직접 띄우는 테스트에 의존하지 않도록 opening chooser/load transition을 주입 가능한 좁은 seam 또는 순수 presentation policy로 분리한다. 마지막 정상 snapshot 유지, 실패 dismiss, retry 호출, 패널 취소, 다음 정상 load 성공, stale task 무시와 fatal failure 불변을 deterministic하게 검증한다.

## 잠정 단계(4단계)

1. 현행 opening failure와 상태 전이 inventory
   - 파일 패널, Finder/open URL, 최근 문서, native URL drop, dropped bytes의 validation·failure 경로를 표로 정리한다.
   - recoverable input failure와 기존 fatal WebView failure의 경계를 확정한다.
   - 정상 문서, unsaved 상태, loading task와 stale completion의 보존 계약을 확정한다.
2. recoverable opening state와 store 전이 구현
   - recoverable failure model, dismiss/retry action과 commit-on-success load 전이를 구현한다.
   - 실패 전후 snapshot 유지, retry chooser 호출, 패널 취소, 정상 load 성공과 fatal failure 불변을 unit test로 고정한다.
3. window-local 모달 UI와 입력 경로 통합
   - 기존 viewer를 유지한 채 `닫기`·`다시 시도`를 제공하는 SwiftUI modal을 연결한다.
   - 파일 패널, Finder/open URL, 최근 문서와 두 drag/drop 경로의 문구·focus·재진입 동작을 확인한다.
   - 접근성 label, 기본/취소 action과 modal 중복 표시 방지를 검증한다.
4. negative/normal smoke와 문서화
   - PDF, 빈 파일, 알 수 없는 signature 실패 후 기존 문서 유지와 정상 HWP/HWPX 재시도를 검증한다.
   - 정상 문서가 없는 창과 마지막 정상 문서가 있는 창을 모두 확인한다.
   - fatal viewer asset failure가 기존 전체 fallback을 유지하는지 회귀 확인하고 architecture·build/run 문서와 최종 보고에 반영한다.

## 리스크

- `beginDocumentLoad`의 cancel/load ID 처리와 상태 보존 순서를 잘못 바꾸면 이전 비동기 보호 분류 결과가 늦게 commit되거나 loading overlay가 남을 수 있다.
- 실패한 새 입력에서 기존 unsaved 문서를 유지해야 하지만, 성공한 새 문서 열기의 기존 unsaved-change 확인 정책은 이번 범위와 섞이지 않도록 해야 한다.
- SwiftUI sheet/alert가 표시된 동안 `NSOpenPanel.runModal()`을 즉시 호출하면 modal session이 중첩될 수 있다. dismissal 이후 호출 순서를 실제 macOS 12+에서 검증해야 한다.
- native URL drop과 WebView dropped bytes는 source URL/bookmark 보유 여부가 달라 동일 구현으로 과도하게 합치면 최근 문서·Finder 기능이 바뀔 수 있다.
- HWP/HWPX signature는 맞지만 내부 구조가 손상된 파일은 WebView `document-load-error`까지 진행한다. 이 경로를 recoverable로 전환할지는 fatal failure 제외 범위와 충돌하지 않도록 Stage 1에서 명확히 제한해야 한다.
- `DocumentViewerStore`는 현재 HostAppTests target에 직접 포함되지 않는다. 테스트를 위해 제품 의존을 넓게 끌어오기보다 작은 상태/policy seam을 분리하고 `project.yml` 변경을 최소화해야 한다.
