## 배경

PR [#491](https://github.com/postmelee/alhangeul-macos/pull/491)을 `devel`에 병합했다. 검토한 PR head는 `091a3d56e175a3afe1584589b007a5d19471d95b`, 병합 commit은 `eec7869fb958aec8e30df3a4e6cdaf67253c5a5a`다. GitHub 병합 tree `85c36fafa40bdf8acb9bb7de4a37dfc785429b58`은 최신 devel에서 미리 검증한 임시 병합 결과와 일치한다.

PR CI 4개 항목이 성공했고, macOS 검증에는 Rust bridge 준비, decoder 호환, HostApp Debug build와 native renderer smoke가 포함됐다. 최신 devel과 합친 결과에서는 build-info, bundled asset, AppKit 의존 경계, 색상 선택기 DOM fixture 6개, Cargo.lock 검증 fixture와 build-info writer/verifier fixture가 통과했다. 이번 로컬 병합 검토에서는 새 앱 build와 GUI smoke를 수행하지 않았으므로 릴리스 후보 검증에서 다시 수행한다.

업스트림 annotated tag는 위 expected commit을 가리킨다. 그 commit의 원본 `Cargo.lock` SHA256 `a094d90fbf3d1f312eb746468334cce5d862ad147dc2eb276062fc3e49cbc373`은 bundled manifest와 일치한다. 앱과 두 extension의 source version/build는 아직 `0.1.10 (16)`이며, 두 release workflow 기본값은 `0.1.10`, `v0.1.9`, `v0.8.4`다.

2026-09-06 시작 시 `origin/main`은 `7162a80fdadf4e121623be1da9c1a7d933ef0fac`, `origin/devel`은 위 준비 기준이며 `origin/main...origin/devel`의 commit 수는 `5 / 69`다. 이 수치만으로 content 누락이나 back-merge 필요성을 판단하지 않는다. 이전 release transport와 PR #477 main 종료 정리, PR #478 devel 기록 반영을 구분해 source tree를 대조한다. 로컬 fetch 후 `v0.1.11` tag는 없었다.

## 설계 방향

1. 버전·workflow 입력과 릴리스 문서를 준비한 뒤 실제 산출물을 검증한다. 이슈·계획 승인, 구현계획 승인, 단계별 실행을 구분한다.
2. source provenance는 release tag와 resolved commit으로 고정한다. core lock, Cargo resolution, Swift build-info와 Studio manifest가 같은 기준인지 확인하고 upstream latest 변경 시 실행 입력을 다시 판단한다.
3. strict staticlib hash/size 검증과 CI에서 사용하는 portable source/header/ABI 검증을 별개로 기록한다. 로컬 mismatch가 나면 실패를 숨기거나 lock을 갱신하지 않고 허용 기준을 보고한다.
4. `main` 전용 이력의 실제 content를 확인해 release transport와 문서 종료 정리를 구분한다. 누락 content가 있으면 반영 경로를 제안하고, commit 수 차이만으로 back-merge를 만들지 않는다.
5. 사용자용 변경 요약은 앱에서 확인한 동작을 기준으로 작성한다. upstream CLI·agent·다른 배포 채널의 개선을 macOS 앱 기능으로 확대해 설명하지 않는다.
6. 암호 문서와 HWP3는 보호·변환 경고, 원본 보존과 복사본 저장을 검증한다. 암호 유지 저장과 HWP3 원형 저장 지원을 새 기능으로 약속하지 않는다.
7. rehearsal, signed draft와 official DMG의 URL·SHA256·검증 기록을 분리한다. draft 설치 smoke를 통과한 후보만 official publish 대상으로 삼는다.
8. Finder 검증은 실제 provider 실행 경로와 표준 등록 위생 절차를 사용한다. 개발 산출물은 `build.noindex/` 아래에 두며 smoke 종료 시 개발 등록을 해제한다.
9. 이미 승인한 실행 범위는 다시 묻지 않는다. 새 단계의 구체적인 후보와 검증 결과를 준비한 뒤 필요한 다음 승인을 요청한다.
10. publish 후 문구·배포 기록 보정은 하나의 종료 정리 단계와 PR로 모은다. 공식 tag를 문서 정정 때문에 다시 지정하지 않는다.

## 리스크

- source 준비 중 devel이나 upstream latest가 이동하면 포함 범위와 실행 입력이 달라진다. 현재 기준과 diff를 비교해 새 반영 여부를 판단한다.
- v0.8.4 → v0.8.6은 누적 upstream 변경이며 기존 앱 수정과 통합 회귀가 생길 수 있다. 기존 PR CI 성공만으로 새 signed 후보의 GUI 동작을 보장하지 않는다.
- Issue #480 후속 암호 저장 구현은 포함되지 않는다. PR #481 및 #483 변경의 원본 보호와 별도 복사본 경계가 유지되는지 검증한다.
