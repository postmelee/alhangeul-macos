# Task #455 수행 계획서

## 목적

bundled `rhwp-studio`의 `PDF로 저장...` 메뉴와 HostApp toolbar의 PDF 내보내기를 하나의 알한글 native 저장 흐름으로 통합한다. 메뉴와 `NSSavePanel`, 저장 취소·오류, atomic write와 Finder 표시는 알한글이 담당하고, PDF 본문은 편집기의 현재 페이지 SVG를 offscreen `WKWebView.createPDF(configuration:)`으로 변환해 생성한다. HWP/HWPX 모두 중간 `exportHwp`와 native bitmap renderer를 거치지 않도록 PDF 저장 경로를 정리한다.

## 배경

- GitHub Issue: #455
- Milestone: v0.1
- 문서 prefix: `task_m010_455`
- 작업 브랜치: `local/task455`
- 대상 통합 브랜치: `devel`
- 이슈 URL: https://github.com/postmelee/alhangeul-macos/issues/455

현재 bundled `rhwp-studio`의 파일 메뉴에는 `file:print-to-pdf` 명령이 있으나 항목이 비활성이고, 브라우저 인쇄 창에서 PDF 저장 대상을 선택하도록 안내한다. HostApp bridge는 이 명령을 native command로 가로채지 않는다. 반면 toolbar의 `file:export-pdf`는 알한글의 `NSSavePanel`과 atomic write, Finder 표시를 사용하지만, 편집 문서를 `exportHwp` 바이트로 만든 뒤 `RhwpDocument`와 render tree 기반 page bitmap을 거쳐 PDF를 생성한다. 이 때문에 HWPX에도 불필요한 HWP 중간 산출이 생기고 PDF 텍스트 검색·선택을 보장하기 어렵다.

인쇄 경로의 `RhwpStudioPrintController`는 이미 편집 상태를 정리한 뒤 upstream embed RPC의 `pageCount`와 `getPageSvg`로 페이지 SVG를 받고, offscreen `WKWebView.createPDF(configuration:)` 결과를 `PDFDocument`에 페이지 단위로 합친다. #455는 이 SVG 변환부를 인쇄와 저장이 함께 사용할 수 있는 HostApp 서비스로 분리하고, PDF 저장의 command·payload·UI·파일 기록 책임을 native 계층에 일관되게 배치한다.

## 범위

포함:

- bundled 메뉴의 `file:print-to-pdf` 항목을 HostApp 환경에서 활성화하고 알한글 native PDF 저장 동작과 일치하는 도움말 제공
- `file:print-to-pdf`와 toolbar의 `file:export-pdf`를 같은 native PDF export command로 routing
- PDF 요청 전 active editor 상태를 settle하고 upstream embed RPC에서 page count와 각 페이지 SVG 수집
- page count와 SVG 배열을 검증하는 명시적 native payload contract 구성
- `RhwpStudioPrintController`의 offscreen WKWebView, page metrics, `WKWebView.createPDF`와 PDFKit page merge 로직을 재사용 가능한 SVG→PDF 생성 서비스로 분리
- SVG의 실제 page metrics를 기준으로 페이지별 크기와 가로/세로 방향 보존
- 알한글이 `NSSavePanel`, 취소, 중복 요청 방지, 오류 표시, atomic write와 저장 후 Finder 표시를 담당
- HWP와 HWPX의 현재 편집 상태가 PDF에 반영되고 원본 파일은 변경되지 않는지 검증
- 다중 페이지의 page count, page size·orientation, nonblank 출력과 대표 텍스트 검색·선택 검증
- 인쇄와 PDF 저장의 공통 SVG 변환 책임 및 Quick Look/Thumbnail bitmap 경로와의 경계를 architecture 문서에 반영

제외:

- 일반 `file:print`와 macOS print panel UX 변경
- Quick Look/Thumbnail의 render tree 기반 bitmap renderer 변경
- bundled `rhwp-studio` upstream asset 직접 수정
- upstream `rhwp` core 또는 embed RPC protocol 자체 변경
- HWP/HWPX 저장 exporter와 형식별 `Command+S` 동작 변경
- PDF 편집, 암호화, 메타데이터와 접근성 태그 전면 구현
- 서명, 공증, 패키징과 public release 실행

## 설계 방향

두 메뉴 진입점은 명령 이름만 다르고 같은 native PDF export 요청으로 수렴시킨다. injected HostBridge가 upstream handler보다 먼저 `file:print-to-pdf`를 가로채고, 문서가 있을 때 항목의 disabled 상태와 브라우저 인쇄 안내를 HostApp 저장 동작에 맞게 보정한다. toolbar와 내부 메뉴 모두 알한글이 먼저 목적지를 선택한 뒤 하나의 pending PDF 요청만 유지하고, 사용자 취소 시 SVG 수집이나 파일 쓰기를 시작하지 않는다.

PDF payload는 HWP/HWPX 바이트가 아니라 `{ fileName, pageCount, pages }` 형태의 page SVG 묶음으로 통일한다. JavaScript는 editor settle 후 `pageCount`와 `getPageSvg`를 호출하고, Swift는 양수 page count, 배열 길이와 비어 있지 않은 SVG를 검증한다. 따라서 HWPX도 `exportHwp` 중간 변환 없이 현재 편집기의 렌더 결과를 사용한다.

현재 `RhwpStudioPrintController` 안의 offscreen `WKWebView` 순차 로드, DOM page metrics 계산, `WKPDFConfiguration`, `createPDF`, PDFKit merge는 별도 생성 책임으로 추출한다. 인쇄 controller는 완성된 `PDFDocument`로 print operation을 실행하고, PDF export controller는 같은 생성 결과를 atomic write한다. WebKit 객체와 navigation callback은 main actor에서 관리하고, 완료·오류·중복 callback을 단일 종료 경로로 정리한다.

저장 UI와 파일 시스템 책임은 계속 HostApp에 둔다. `DocumentPDFExportPanel`이 `.pdf` 목적지를 정규화하고, export controller가 완성된 PDF data만 atomic write한 뒤 성공 URL을 반환한다. Coordinator는 pending 상태를 해제하고 Finder를 표시하며, 취소나 실패에서는 원본 문서와 목적지 파일 상태를 잘못 갱신하지 않는다. `Sources/RhwpCoreBridge`와 Quick Look/Thumbnail renderer에는 AppKit/WebKit 또는 PDF 저장 책임을 추가하지 않는다.

자동·정적 확인:

- bridge native command set에 `file:print-to-pdf`가 포함되고 upstream browser print handler보다 먼저 intercept되는지 확인
- 내부 메뉴와 toolbar가 모두 동일한 SVG payload 요청과 native PDF export handler로 수렴하는지 확인
- PDF 요청이 `exportHwp`, `exportHwpBase64`, `RhwpDocument`, `HwpPreviewPDFRenderer`를 호출하지 않는지 확인
- page count와 SVG 배열 길이·빈 문자열 검증, 잘못된 payload의 오류 처리 확인
- SVG metrics에서 유효한 page size를 만들고 비정상 값은 안전한 기본값 또는 명시적 오류로 처리하는지 확인
- 저장 취소·실패·중복 요청에서 pending controller와 destination 상태가 정리되는지 확인
- 임시 목적지에 대한 atomic write와 유효한 `%PDF` data, PDFKit page count 확인

수동 smoke:

- HWP와 HWPX를 각각 열고 편집한 뒤 내부 `PDF로 저장...`과 toolbar PDF 내보내기를 실행해 같은 native `NSSavePanel`이 표시되는지 확인
- 두 진입점의 결과가 현재 편집 내용을 포함하고 원본 HWP/HWPX의 hash·수정 시각을 바꾸지 않는지 확인
- 단일 페이지, 다중 페이지, 가로 방향이 포함된 대표 문서에서 PDF page count, 각 page media box와 방향, nonblank content 확인
- PDFKit 검색 또는 `pdftotext`로 대표 한글 텍스트를 찾고 Preview에서 선택 가능한지 확인
- 저장 취소 시 파일이 생성되지 않고, 기존 파일 덮어쓰기·실패 시 사용자 오류와 상태 정리가 올바른지 확인
- 기존 `file:print`가 계속 macOS print panel을 열고 내용 있는 preview를 표시하는지 회귀 확인

## 리스크

- upstream `getPageSvg`가 glyph를 path로 변환하거나 폰트를 outline 처리하는 경우 시각적 PDF는 정상이어도 텍스트 검색·선택이 제한될 수 있다. 대표 문서로 실제 PDF text layer를 검증하고 미달 시 upstream SVG 계약의 후속 범위를 분리해야 한다.
- 페이지 SVG의 width/height, viewBox와 CSS pixel 단위가 혼재하면 PDF media box 또는 방향이 달라질 수 있으므로 DOM metrics와 SVG 속성의 우선순위를 구현계획에서 명시해야 한다.
- offscreen `WKWebView` navigation과 `createPDF`는 main-thread lifecycle에 의존하므로 controller가 조기 해제되거나 callback이 중복 완료되지 않게 소유권을 유지해야 한다.
- 다중 페이지를 순차 변환하고 PDFKit으로 합치는 경로는 대용량 문서에서 시간과 메모리를 사용할 수 있다. 요청 중복을 막고 단계별 page data를 불필요하게 장기 보관하지 않아야 한다.
- bridge가 disabled menu의 click을 가로채기 전에 무시하면 native command가 전달되지 않는다. HostApp override와 capture handler의 순서 및 accessibility disabled 상태를 함께 검증해야 한다.
- 인쇄와 저장이 공용 renderer를 쓰더라도 오류 문구와 완료 동작은 다르므로 renderer가 직접 alert, print panel 또는 Finder 표시를 소유하지 않도록 경계를 지켜야 한다.
- `project.yml`이 Xcode project의 원본이므로 새 source/test 파일을 명시적으로 추가해야 한다면 `project.yml`을 수정하고 XcodeGen 생성 결과를 검증한다.
