# Task M900 #618 수행계획서

2026-11-19 · [이슈 #618](https://github.com/postmelee/alhangeul-macos/issues/618) · 대상 `devel` · 기준 `3ed7d3eb9cbe586979507395776beb5c29d7f3e4`

## 목적

공식 rhwp v0.9.1의 Studio·WASM 빌드를 알한글의 글꼴 어댑터 및 빌드 증명과 호환시켜 자동 동기화 후보 PR 생성 차단을 해소한다. 기존 v0.9.0 빌드와 실제 문서 첫 렌더링 동작을 보존한다.

## 배경

[자동 동기화의 Studio 빌드](https://github.com/postmelee/alhangeul-macos/actions/runs/44482822101/job/135420298236)는 공식 v0.9.1 `981ce66b4183b13c1a3b5907e04a8969c8c42034`까지 해석한 뒤 `src/main.ts`에서 중단되었다. 공식 소스를 실패 커밋 `4b753e5`의 Node 어댑터에 직접 넣으니 5개 대상 중 `main.ts`와 `wasm-bridge.ts`가 실패했다. 현재 기준에서는 #616의 임시 변환이 `canvas-view.ts`에서도 실패해 6개 중 3개가 통과했다. 개별 변환 결과이며 제품 빌드 결과나 설치본 장애를 의미하지 않는다.

`main.ts`에서 `hostFontLayoutEnabled`의 추가로 import 순서가 바뀌었다. `wasm-bridge.ts`도 upstream import 첫 심벌이 바뀌었으며, 기존 어댑터가 추가하던 `resolveRendererLocalFontCandidates`가 이미 import되어 있다. 기존 #616 어댑터가 의존하는 초기 렌더링 진행 상태 일부도 삭제 또는 재구성되었다.

## 범위

- 포함: 고정된 v0.9.0 `c9095c5f67632e6721e800ccc7fb43ea49d26682` 및 v0.9.1의 글꼴 공급/출력 transform과 타입 검사, 같은 SHA의 WASM·Studio·manifest·receipt, 기존 동기화 검사에서의 후보 생성 가능성.
- 포함: #9170이 반영된 v0.9.1에서 실제 WKWebView 첫 화면, 반복 열기 및 취소, 로컬 글꼴, HWP/HWPX·PDF 수용 검증. v0.9.0 임시 경로 보존.
- 제외: upstream 직접 수정, 설치본이나 공개 앱 설정 변경, 기존 정상 설치본 덮어쓰기, 병합, 서명·공증·공개 배포, 신규 의존성 또는 주변 리팩터링. 외부 CI 재실행 및 후보 게시가 필요할 때에는 해당 단계 승인 범위를 먼저 확인한다.

## 설계 방향

대상 모듈의 고유 named import를 찾아 기존 심벌과 타입 import를 보존하고 필요한 심벌만 한 번 추가한다. 순서·허용 공백이 달라도 처리하되, 대상 누락·모호한 중복·원본 불일치에서는 실패를 유지한다. 새 엔진의 글꼴 기능과 앱이 삽입하는 화면·출력 보완의 중복 실행 여부도 확인하며, 단순 문자열 치환으로 끝내지 않는다.

v0.9.0과 v0.9.1은 검증된 정확한 upstream 커밋과 적용된 변환 조합이 일치해야 한다. #616의 v0.9.0 임시 경로는 유지한다. 지원 후보 v0.9.1에서 #9170의 문서 초기화 및 취소 계약을 사용한 첫 화면 검증이 통과하는지 확인하고, 통과하기 전까지 임시 변환을 제거한 제품 빌드를 배포 가능한 것으로 간주하지 않는다. 대응 소스와 변환 목록이 provenance 및 strict verifier에도 일치해야 한다.

## 예상 변경 파일

- `scripts/studio-font-menu-adapter.mjs` 및 `scripts/studio-initial-render-adapter.mjs`: 글꼴 import 처리, 버전별 첫 로드 변환 선정.
- `scripts/build-rhwp-studio.mjs` 및 Studio 자산 검증 경로: 실제 적용 소스·fingerprints·receipt 계약. 엄격 검증 유지.
- `scripts/ci/test-studio-font-*.cjs` 및 대응 회귀: 누락·중복·새 심벌 순서·기존 버전 보존.
- 생성 파일 갱신이 필요한 경우에는 정식 생성 절차와 provenance를 사용한다. 문서는 기존 `mydocs/plans/`, `mydocs/working/`, `mydocs/report/`, `mydocs/orders/`에 두고 새 공식 기술 문서 루트는 추가하지 않는다.

## 잠정 단계

1. 두 태그와 대상 소스, 현재 빌드·검증 경로의 기준을 잠근다. 실패와 변환의 호환성 조건을 회귀로 기록한다.
2. 글꼴 transform과 버전별 변환 목록을 최소 변경으로 구현하고 실패 폐쇄, 타입 검사 및 자산 증명을 검증한다.
3. 같은 upstream 커밋의 WASM·Studio 빌드를 각각 확인하고 실제 macOS WKWebView 첫 화면·취소·글꼴·PDF를 검사한다. v0.9.0 우회가 유지되는지와 v0.9.1의 수용 여부를 구분하여 기록한다.
4. 통과·실패·미실행의 증거를 최종 보고로 묶고, 승인된 검증 경로에서 후보 PR 생성 준비 여부를 정리한다.

## 검증 계획

- Node 회귀: 정확한 두 태그 입력, 바뀐 import 심벌 순서와 이미 있는 심벌, 타 모듈의 동명 심벌, 대상 중복/누락, v0.9.0 전용 초기 렌더링 변환 및 unknown commit 거부.
- build 검증: 두 태그별 TypeScript, 공식 WASM 입력과 Vite Studio 빌드, manifest/receipt·산출물 fingerprint 일치 및 strict verifier, 기존 동기화 검사. 성공하지 않은 자산을 제품 후보로 승격하지 않는다.
- macOS 통합: 표준 `build.noindex/`와 smoke 절차에 따라 새 프로세스 첫 뷰포트, 연속 파일 열기, 진행 중 교체·취소, 폰트 공급/해제, HWP/HWPX와 PDF의 표시·출력을 확인한다. macOS를 쓸 수 없으면 실제 앱 항목을 미실행으로 기록한다.

## 리스크

새 upstream 자체가 host 글꼴 공급을 처리해 앱 보완과 이중 등록할 수 있고, 정확한 소스 목록이 바뀌면 기존 receipt와 검증기가 서로 어긋날 수 있다. 실제 Mac 접근 없이 WKWebView 첫 프레임 또는 취소의 정확성을 선언하지 않는다. 배포는 별도 결정으로 유지한다.

이 수행계획(범위·검증 기준·제외 항목·문서 위치)을 승인하면 다음 단계로 구현계획서를 작성한다. 이 승인 전에는 구현계획서·제품 코드·자산을 변경하지 않는다.
