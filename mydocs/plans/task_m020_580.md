## 1. 목적

Finder의 반복 Quick Look·썸네일 요청에서 글꼴 목록 준비 비용을 줄이고, 정상 다수 파일 표시가 렌더 자원 한도 때문에 기본 아이콘으로 남는 현상을 개선한다. 실제 face/style 선택·원본 현재성·권한·취소·lease 수명과 기존 메모리/동시 실행 한도를 함께 보존한다.

완료 결과는 #569의 Mac 웹 안내와 같은 최종 후보 수용으로 인계한다. Windows 입력이나 새로운 upstream 릴리즈를 선행 조건으로 추가하지 않는다.

## 2. 배경

#565 설치 감지·설정·권한, #567 공식 v0.8.7 Studio 연결, #568 출력·확장 연결은 devel에 반영되었다. HostApp 최초 활성화의 중복 탐색은 #567에서 이미 합쳤으며 이번 대상은 확장의 매 요청 준비다.

#569 Stage 2의 최적화된 Developer ID 로컬 서명 확장에서 같은 Thumbnail PID의 exactHit 10건 metadata 중앙값은 OFF 1008.69ms, ON 독립 workload 두 번 1051.00/1018.37ms였다. 대응 provider 전체 응답에서 약 98%를 차지하며 largerBucketHit도 약 1초였다. 실제 Finder GUI Thumbnail 55건 중 성공 24건·busy 31건, 별도 제어 `qlmanage -t` 63건은 모두 성공했다. 전체 signed 157건·직접 probe 530건의 표본과 조건을 구분한다.

이 수치는 앱 시작·화면 paint·순수 CoreText scan 시간이 아니다. busy 오류 코드만으로 admission·렌더 슬롯·공유 bytes budget 중 원인을 단정하지 않는다. Stage 1에서 비용과 실패 경계를 더 나누어 확인한다.

측정 진실 원천은 미병합 `local/task569`의 Stage 2 커밋 `60ea06a384ce5ba9e43b60a30278ce1268efe237`과 이후 계획 정렬 커밋 `e55cbaf6`이다. 해당 브랜치의 `mydocs/tech/task_m020_569_finder_measurement.md`, `mydocs/working/task_m020_569_stage2.md`, 선별 assets와 `build.noindex/task569/stage2/` 원시 근거를 보존했다. 공개 이슈에는 핵심 표를 포함했으며 미게시 커밋의 공개 파일 링크를 만들지 않았다.

## 4. 설계 방향

1. 전체 준비의 지배 구간을 분리한다. CoreText 목록, 정규화·stat, 공급 metadata/current 검증, 관리 manifest, 준비 대기, cache lookup, 렌더 대기를 구분하고 busy 발생 경계를 기록한다. UUID·단조 시간·PID·image UUID로 요청을 대응하며 실패를 성공 표본에 합치지 않는다.
2. 재사용 가능한 목록/metadata와 요청별 snapshot·lease를 구분한다. 진행 중 준비는 합치되 한 요청의 취소/해제가 다른 요청의 유효한 데이터를 닫지 않게 한다. 재사용 조건·변경 알림·재검사·실패 복구를 구현계획에 명시한다.
3. bitmap hit 전 확인 비용을 줄이되 검증을 생략하지 않는다. 정책/관리 상태와 원본 identity의 현재성을 유지하고 실제 읽기는 기존 FD/hash/face 검증을 따른다. 이름만 같거나 stat만 같은 원본을 정확한 face 적용으로 판정하지 않는다.
4. 정상 요청의 대기와 실제 과부하를 구분한다. 같은 키는 기존 병합을 유지하며 다른 문서는 제한된 대기로 렌더 슬롯을 기다리게 하는 방향을 검토한다. 2건 렌더·16건 admission·96항목/64MiB bitmap·공유 전송 budget을 늘리지 않는다. 초과 부하는 명시 busy 정책을 유지한다.
5. HostApp bookmark나 지속 목록을 확장에 무조건 전달하지 않는다. 각 확장의 sandbox 권한과 CoreText scope를 보존한다. 공통 catalog service를 바꾸면 HostApp 시작·설정·출력 소비자도 영향 범위에 따라 회귀한다.
6. #569 측정 코드의 필요한 부분은 고정 커밋과 비교하여 이 타스크의 진단/검증으로 재사용한다. 미병합 #569 전체 커밋을 무조건 cherry-pick하거나 #569 전체 PR을 먼저 끝내는 순환 의존성을 만들지 않는다. 구체 파일 반영·CI 실행 경로는 구현계획에서 확정한다.

최초 잠정 목표는 같은 signed 환경의 exact/larger warm metadata 중앙값 **200ms 미만**, provider 응답 중앙값 **300ms 미만**이었다. 2026-10-11 작업지시자의 “현재 검증 결과를 수용하도록 Stage 4 완료 기준을 보정하고, 추가 최적화는 후속 작업으로 분리한 뒤 #580 Stage 5를 진행해줘” 승인으로 현재 후보 `580.4.3`의 결과를 수용한다. metadata <200ms는 유지하고, ON provider 중앙값 **328~343ms**는 이 고정 후보·표본에 한해 수용한다. provider <300ms는 후속 최적화 목표로 분리하며 #580 완료나 #569 Mac 수용·안내·출시 준비를 막지 않는다. 임의의 새로운 일반 상한을 정하거나 원래 목표 통과로 기록하지 않는다.

각 warm 조건 10건 이상·같은 PID의 ON 독립 workload 두 번·OFF 대조, 정상 자동 Thumbnail 186건 busy 0, face/bytes·현재성·취소/lease·한도·변경/복구, 실제 Finder/Quick Look·원래 설치본/등록 복원은 완료 조건으로 유지한다. 최초 miss·다수 파일 대기·별도 PID와 화면 paint를 분리하고 지연 한계를 기록한다. [Stage 4 승인 기록](../working/task_m020_580_stage4.md#13-stage-4-완료-기준-보정과-후속-분리)과 [후속 #581](https://github.com/postmelee/alhangeul-macos/issues/581)을 따른다. OS 일반 성능 기준이나 제품 전체 출시 완료로 주장하지 않는다.

## 7. 검증 계획

- 수행계획만 변경하는 착수는 파일명·9개 섹션·상대 링크·오늘할일 형식·`git diff --check`·작업 트리를 검증한다. 제품 전체 빌드/기존 전체 테스트를 반복하지 않는다.
- 정확성: 실제 production 상태 기계의 동시 준비 횟수, 한 요청 취소/전체 취소, invalidation 중 준비·읽기·cache hit, 오류 후 복구와 lease 획득/해제의 대응을 확인한다. 구현을 그대로 복제하는 테스트를 만들지 않는다.
- 현재성: OFF/ON, CoreText 등록 변화, 새 PID, 원본 교체·삭제·복구·권한 상실, 관리 선택/객체 변경을 구분한다. 실제 OS 변화와 격리 환경 주입 결과는 각각 기록한다.
- 부하: 동일/다른 키·10개 파일·최초/반복·크기 변화·상한 초과 요청에서 실제 렌더 최대 2건·admission 16건과 제한된 대기를 검사한다. stale·취소된 요청에 PNG를 반환하지 않고 실패를 무조건 default cache로 고정하지 않는다.
- 성능: baseline과 같은 HWP/HWPX·OFL Gowun Batang fixture·OFF/ON·exact/larger hit·새 PID·동시 수를 사용한다. 공급 metadata와 전체 callback 구간을 대응하고 화면 paint·OS 요청 생략을 분리한다. Release 최적화와 sandbox/sign 여부를 기록하며 직접 CLI와 signed 결과를 합치지 않는다.
- 빌드/회귀: 변경 경계의 FontLibrary/HostApp tests·확장 probe, no-AppKit 및 matcher/Studio asset receipt를 확인한다. 공유 catalog를 변경하면 HostApp·PDF/인쇄·native 영향 회귀를 추가하며 새 C ABI는 사용하지 않는다.
- signed Finder: 후보 SHA·source/lock/asset receipt·hash·인증서·고유 fixture·기존 설치본 백업/복원 계획이 준비된 뒤 구체 로컬 시험 승인을 받는다. 승인된 표준 smoke에서만 등록하고 종료 시 소유 등록·앱·fixture를 정리한다. #569의 이전 후보 승인을 새 바이너리 승인으로 간주하지 않는다.
- 최종 인계: 실제 face/style·bytes 근거와 화면/PNG를 확인하고 #569의 최종 사용자 수용을 대체했다고 선언하지 않는다. 최소 macOS/Intel 실제 실행 등 확보되지 않은 환경은 미검증으로 기록한다.

## 8. 리스크

- 알림만 믿는 metadata 재사용은 파일의 제자리 교체·권한/비활성 변화에서 stale bitmap을 반환할 수 있다. 원본 확인과 실패 복구 비용을 정확성 조건과 함께 수용한다.
- actor reentrancy·공유 Task 취소·snapshot lease 공유는 중복 준비나 잘못된 해제를 만들 수 있다. 준비 세대와 요청별 수명을 구분하고 변경 도중 요청을 대조한다.
- 렌더 대기는 메모리 증가·취소 후 작업 잔류·순서 역전·timeout을 만들 수 있다. 최대 대기 수와 bytes 읽는 시점을 제한하며 물리 실행 한도를 유지한다.
- busy는 여러 한도에서 발생하므로 준비 비용 개선만으로 다수 파일 오류가 해결됐다고 가정하지 않는다. 발생 경계와 실제 Finder 결과를 함께 검증한다.
- OS cache·extension PID·Release 최적화·OS 부하는 비교를 왜곡할 수 있다. 같은 workload 조건과 유효 UUID 구간을 확인하고 숫자만으로 한컴/모든 OS 지원을 확대하지 않는다.
- #569의 미병합 진단 코드·오늘할일과 이 브랜치의 변경이 겹칠 수 있다. 각각의 브랜치·보고를 보존하고 병합 이후 승인된 통합 절차로 대조한다.
