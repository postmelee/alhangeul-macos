# Task M014 #110 수행계획서

## 목적

Swift/CoreGraphics native renderer에서 `Placeholder`와 `FormObject` 계열 노드를 정적 프리뷰로 표시한다. 목표는 Quick Look preview, Finder thumbnail, PDF/CoreGraphics fallback에서 문서에 존재하는 양식 컨트롤이나 placeholder 영역이 비어 보이거나 crash하지 않게 하고, 지원하지 못하는 타입은 명확한 fallback으로 드러내는 것이다.

## 배경

현재 앱 저장소의 `rhwp-core.lock`과 bundled `rhwp-studio`는 upstream `edwardkim/rhwp v0.7.13` (`b3e16ef212af81ef37d973ddb86d6816d3804642`) 기준이다. upstream render contract에는 `RenderNodeType::Placeholder`, `RenderNodeType::FormObject`, `PaintOp::Placeholder`, `PaintOp::FormObject`가 있고 Canvas/WebCanvas/CanvasKit 계열도 정적 placeholder/form object preview 경로를 가진다.

현 `devel` 기준 Swift 모델에는 #121 작업 결과로 `PlaceholderNode` 디코딩과 기본 dashed box/label 렌더링이 이미 들어와 있다. 반면 `FormObjectNode`는 아직 `formType`, `caption`, `text`만 디코딩하고, `CGTreeRenderer`는 `.formObject`를 렌더링하지 않는다. 따라서 이번 작업은 기존 Placeholder 구현을 검증하고 필요한 경우 upstream contract에 맞게 보강하되, 주된 구현 범위는 FormObject 정적 preview와 fallback 정책으로 둔다.

M014의 #280 visual diff harness, #282 Quick Look/Thumbnail native compositor, #116 watermark/effect gate, #122 image fill/tile/placement, #121 RawSvg/Placeholder 기본 fallback 결과를 기준선으로 사용한다. `samples/form-01.hwp`와 `samples/hwpx/form-002.hwpx`는 #280에서 form/placeholder fixture로 등록되어 있으며, 현재 기준 diff는 각각 약 `0.8066%`, `15~16%` 수준으로 기록되어 있다.

## 범위

포함:

- 현 Swift `PlaceholderNode` 디코딩과 렌더링이 upstream v0.7.13 payload와 sample에서 맞는지 확인
- `FormObjectNode`의 `fore_color`, `back_color`, `value`, `enabled`, `name` 등 정적 표시용 필드 디코딩 검토 및 필요한 모델 확장
- button, checkbox, radio, edit/text input, combo/list 등 form type별 최소 정적 preview 구현
- unknown/unsupported form type은 crash 없이 bbox 안에 명확한 fallback으로 표시
- bbox, clipping, transform, flow rendering gate가 기존 renderer 규칙을 따르는지 확인
- Quick Look preview, Finder thumbnail, PDF/CoreGraphics fallback에서 같은 policy가 적용되는지 확인
- `samples/form-01.hwp`, `samples/hwpx/form-002.hwpx`와 작업 중 확인한 form fixture의 visual diff 전후 수치 기록

제외:

- 실제 입력/클릭 가능한 form interaction
- Form query/edit API 연동
- 저장 가능한 form mutation
- RawSvg/OLE/chart 렌더링 추가 보강
- HostApp native viewer/editor overlay 작업
- upstream `rhwp` 수정 또는 unreleased commit pin 적용
- Skia/PageLayerTree 기본 렌더 경로 전환

## 설계 방향

구현은 upstream static preview 의미를 CoreGraphics/CoreText에 맞게 재해석한다. 사용자-facing 목표는 interactive control이 아니라 문서 안의 양식 객체가 비어 보이지 않는 정적 표시다.

1. current path와 payload를 먼저 inventory한다.
   - `RenderTree.swift`의 `FormObjectNode` 필드와 sample render tree JSON의 실제 key를 비교한다.
   - `CGTreeRenderer`에서 `.formObject`가 현재 무시되는 지점과 `Placeholder` helper 재사용 가능성을 정리한다.
   - #121의 `Placeholder` 구현이 #110 범위에서 충분한지, label/색상/bbox 처리만 보강하면 되는지 판단한다.
2. FormObject 모델 확장은 실제 payload에 맞춰 좁게 한다.
   - `form_type`, `caption`, `text`, `value`, `name`, `enabled`, `fore_color`, `back_color`처럼 정적 preview에 필요한 필드만 우선 디코딩한다.
   - unknown field를 렌더 실패로 보지 않고 fallback 판단 자료로 둔다.
3. 타입별 preview는 최소 도형으로 구현한다.
   - button은 bevel이 과하지 않은 rect와 caption/text 중심 label로 표시한다.
   - checkbox/radio는 선택 상태를 value로 해석할 수 있을 때만 check/dot을 표시하고, 불명확하면 empty state로 둔다.
   - edit/text input은 배경, border, value/text label을 bbox 안에 그린다.
   - unsupported type은 type/name label이 있는 fallback box로 표시한다.
4. renderer 공통 규칙을 유지한다.
   - `shouldRenderFlowContent`, `validTopLeftRect`, clipping, color conversion, label fitting은 기존 helper와 같은 규칙을 따른다.
   - AppKit/UIKit/WebKit 의존을 `RhwpCoreBridge`에 직접 추가하지 않는다.
5. visual diff와 사용자-facing non-blank 개선을 분리해 기록한다.
   - fallback box가 추가되면 diff 수치가 늘 수 있으므로, empty/crash 방지와 pixel parity를 함께 판단한다.

## 잠정 단계

1. Stage 1: Placeholder/FormObject current path inventory와 baseline 측정
   - `samples/form-01.hwp`, `samples/hwpx/form-002.hwpx` 기준 render tree JSON, node count, native PNG, visual diff baseline을 남긴다.
   - #121에서 들어온 Placeholder 구현의 실제 sample 영향과 FormObject 누락 범위를 분리한다.
2. Stage 2: FormObject payload 모델과 static preview 정책 설계
   - upstream v0.7.13 payload key와 Swift 모델 필드를 맞추고, type별 fallback/label/value 해석 정책을 정리한다.
3. Stage 3: RenderTree 디코딩과 CoreGraphics FormObject 렌더링 구현
   - 정적 preview용 필드를 추가하고, button/checkbox/radio/input/fallback 렌더링을 구현한다.
   - Placeholder helper와 label fitting helper는 가능한 한 공유하되 의미가 다른 표현은 분리한다.
4. Stage 4: visual diff, smoke, 회귀 검증
   - form target sample과 M014 공통 sample set을 전후 비교하고, Quick Look/Thumbnail/PDF fallback non-crash를 확인한다.
5. Stage 5: 최종 보고와 PR 게시 준비
   - 지원된 form type, fallback된 type, 남은 interactive/edit API 제외 사항, 후속 이슈 여부를 정리한다.

수용 기준:

- `Placeholder` node가 `.unknown`이나 빈 영역으로 사라지지 않고 기존 #121 fallback 정책을 유지한다.
- `FormObject` node가 더 이상 무시되지 않고 bbox 안에 정적 preview 또는 명확한 fallback으로 표시된다.
- button, checkbox, radio, input 계열은 문서 내용을 해치지 않는 최소 도형과 label/value를 표시한다.
- unsupported form type은 crash 없이 type/name을 알 수 있는 fallback으로 보인다.
- Quick Look preview, Finder thumbnail, PDF/CoreGraphics fallback이 같은 renderer path를 사용한다.
- #116 watermark, #122 image fill/tile/placement, #121 RawSvg/Placeholder sample이 회귀하지 않는다.
- visual diff 수치와 fallback 여부가 stage 문서와 최종 보고서에 남는다.

## 리스크

- upstream `FormObjectNode` payload shape가 form type이나 HWP/HWPX에 따라 다르면 Swift 모델을 너무 좁게 잡았을 때 일부 필드가 누락될 수 있다.
- `value`의 선택 상태 표현이 checkbox/radio/input 사이에서 다를 수 있어 잘못된 check/dot 표시가 생길 수 있다.
- static preview가 rhwp-studio CanvasKit과 픽셀 단위로 다를 수 있고, fallback box 추가로 visual diff가 오히려 증가할 수 있다.
- label fitting을 잘못 적용하면 작은 form bbox에서 text가 control border와 겹칠 수 있다.
- Placeholder fallback과 FormObject unsupported fallback 표현이 비슷하면 사용자가 객체 종류를 구분하기 어려울 수 있다.
- `RhwpCoreBridge`에 AppKit/UIKit/WebKit 의존을 추가하면 소유 경계와 코드 규칙을 위반할 수 있다.
