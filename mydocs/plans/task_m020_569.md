# Task M020 #569 — Mac 로컬 글꼴 사용의 성능 확인·사용 안내·출시 수용

- 이슈: [#569](https://github.com/postmelee/alhangeul-macos/issues/569), 상위 [#562](https://github.com/postmelee/alhangeul-macos/issues/562)
- 마일스톤: M020 — 글꼴 마이그레이션 / v0.2 계열
- 기준: `devel` / `dac73a589dc17143e744da6a12a51d638a81fb77` (PR #579 merge), 작업 `local/task569`
- 시작 승인: 2026-10-10. 작업지시자가 Mac 로컬 글꼴 사용을 중심으로 Finder 비용 확인·웹 안내·릴리스를 제안하고, 해당 진행 순서에 “진행해줘”로 착수를 승인했다.
- 현재 단계: 기존 구현·이슈·배포 정책 확인과 수행계획 작성. 구현계획 및 제품·웹 소스 수정 전 수행계획 승인을 받는다.

## 1. 목적

이미 구현된 **Mac에 설치된 글꼴 사용**을 다음 v0.2.x 출시의 사용자 기능으로 준비한다. Finder에서 반복 요청할 때의 글꼴 준비 비용을 확인하고, 실제 앱 동선을 설명하는 웹 안내를 작성하며, 같은 출시 후보의 Mac 사용자 시나리오를 수용한다.

Windows ZIP 가져오기(#566)는 독립 후속이다. Mac 출시 준비를 Windows 완료에 종속시키지 않되 #569의 Windows 수용과 상위 #562 전체 완료 조건을 남긴다. 이번 Mac 부분의 PR에는 `Closes #569`를 넣지 않는다.

## 2. 배경

#565의 설치 감지·설정·권한, #567의 공식 rhwp v0.8.7 연결·기존 글꼴 목록 적용, #568의 PDF·인쇄·native·Quick Look·Thumbnail 연결이 `devel`에 병합되었다. [소비자 인계](../tech/task_m020_568_consumer_handoff.md)와 [#568 최종 보고](../report/task_m020_568_report.md)를 출발점으로 사용한다.

- 공개 최신 stable은 확인 당시 v0.2.2다. 다음 구체 버전·build number·출시일은 후보 확정 때 정한다.
- HostApp 최초 활성화의 중복 탐색은 #567에서 합쳤다. 새 성능 대상은 확장의 **매 요청 CoreText 목록 준비**다.
- 기존 signed 로그 32건의 metadata 준비는 최소 453.64ms / 중앙값 1,089.77ms / 최대 2,949.45ms이며 동시 대기를 포함한다. 앱 전체 실행 지연이나 순수 CoreText scan 시간으로 바꾸어 설명하지 않는다.
- 기존 signed PDF·인쇄와 Finder 증거는 서로 다른 단계 빌드다. 이번에는 출시 후보 commit·설정·원본·소비자를 묶어 최종 수용한다.
- 현재 웹 `docs/index.html`은 v0.2.2와 기존 기능을 안내한다. `main`의 `docs/**` merge는 Pages 자동 배포를 유발하므로 개발 초안과 공개 반영 시점을 구분한다.

## 3. 범위

포함:

- Mac 출시 대상 face/형식·소비자 지원과 알려진 제한의 확인됨/조건부/미지원/미검증 표.
- 최초·반복 Quick Look, 다수 파일 Thumbnail, 동시 요청·cache hit의 metadata 준비 횟수/시간과 전체 응답시간 측정. 같은 환경의 공급 OFF 대조를 함께 기록.
- 설치 설정·원본/관리 객체 변화·재실행 때 결과 freshness를 유지하는 성능 개선 필요성 판단. 개선 구현이 필요하면 별도 성능 이슈와 구체 계획으로 추적.
- 설정(⌘,) → 글꼴 → **Mac에 설치된 글꼴 사용** → 기존 글꼴 목록 선택 → 문서/PDF 확인·재실행의 단계별 웹 안내.
- 필요한 권한·다시 감지·폴더 다시 선택, 설치 원본 의존성과 **보관한 글꼴 → 글꼴 가져오기…**의 차이, 지원 제한과 문제 해결 안내.
- 같은 후보의 설정·권한·실제 face/style·문서 저장/재열기·PDF·인쇄 경로·Finder·원본 상실/복구 수용과 실제 스크린샷/직접 확인 경로.
- Mac 출시 판단 자료와 후속 Windows 수용 인계, 최종 보고 및 `devel` 대상 부분 PR.

제외:

- #566 Windows 입력 구현과 Windows 완료 판정, #562/#569 전체 완료 처리.
- 새 core pin·upstream API/ABI, renderer 기본 backend 전환, TTC/가변/HFT·전체 shaping 지원 확대.
- 사용자 한컴 앱 제거, 임의 원본 글꼴 변경·영구 OS 설치/비활성화, 상용 font bytes의 저장소 업로드.
- 실제 프린터 전송, 전역 Finder/LaunchServices cache 초기화.
- 이번 수행계획 승인만으로 구체 버전 태그·서명/공증 workflow·GitHub Release·Pages/appcast/Cask 공개 작업 실행. 후보와 산출물을 준비한 뒤 기존 release gate의 구체 승인 범위를 확인한다.

## 4. 설계 방향

- 기존 설치 참조·공식 matcher·필요 face bytes·관리 snapshot/lease를 재사용한다. 성능 측정 때문에 글꼴 공급 정책이나 선택 결과를 먼저 바꾸지 않는다.
- metadata 준비, bytes 읽기, 렌더, cache hit, 대기, 전체 응답을 구분하고 sample 수·PID·동시 수·문서/원본 identity·backend·빌드 SHA를 함께 기록한다. OS가 실제 새 요청을 보냈는지도 확인한다.
- 반복 측정은 동일 파일/크기, 크기 변경, 별도 파일 묶음과 새 프로세스를 나눈다. metadata 시간과 시스템 thumbnail cache로 요청이 생략된 시간을 혼동하지 않는다.
- 최적화는 오래된 face를 반환하지 않아야 한다. 변경 알림·공유 정책 revision·선택 원본 검증·취소/lease·2건 렌더/16건 admission/96항목·64MiB bitmap 한도를 보존한다. 단순 무기한 목록 재사용을 전제하지 않는다.
- 측정 결과로 출시 영향과 개선 범위를 판단한다. 제품 코드 개선이 필요하면 독립 이슈/계획 승인을 받은 후 진행하고 결과를 이 수용표에 인계한다.
- 웹 안내는 기존 사이트 스타일을 재사용한 `docs/fonts/index.html`을 우선 검토하고 홈에서 찾아갈 링크를 제공한다. 정상 흐름과 필요한 경우의 권한 복구를 구분한다. 실제 메뉴명과 스크린샷을 대조하며 개발 초안에 미출시 기능을 현재 공개 지원으로 표시하지 않는다.
- 기능명은 **Mac에 설치된 글꼴 사용**으로 통일한다. 모든 한컴 글꼴 추출·한컴 제거 후 지속 사용·모든 macOS font 형식 지원을 약속하지 않는다.
- 제품 UI가 꼭 바뀌어야 할 때만 변경하고 스크린샷/직접 조작 창을 제공한다. 도움말 링크의 위치·필요성은 기존 앱 메뉴를 확인한 뒤 구현계획에 적는다.
- public release 실행은 별도 운영 이슈(M900)와 release runbook으로 추적한다. #569의 Mac 준비 완료와 출시 실행, 전체 Windows 수용 완료는 각각 기록한다.

## 7. 검증 계획

- 계획 문서만 변경하는 착수 단계는 파일명/링크·오늘할일 형식·`git diff --check`·작업 트리를 확인한다. 제품 전체 빌드/기존 전체 테스트를 반복하지 않는다.
- Stage 1에서 기존 signed 로그와 진단 지점을 대조해 최소 반복 수·문서 묶음·동시 수·측정 구간과 출시 판단 기준을 구현계획에 확정한다. 기존 1.09초를 목표값이나 새 측정값으로 쓰지 않는다.
- `build.noindex/task569/`에 격리 fixture·로그·앱을 둔다. 이전 타스크의 보존 증거와 사용자 OS 글꼴은 수정하지 않는다. 공식 OFL 원본의 출처/hash와 실제 설치 원본을 구분한다.
- 설정 OFF/ON, 정상 반복, 앱/확장 새 PID, 원본 상실/복구, 관리 선택/제거/복구와 필요한 권한 복구를 확인한다. 원본 상실은 정확 적용 성공이 아닌 명시 상태/대체로 판정한다.
- 관련 Swift/JS tests와 no-AppKit·matcher/Studio asset receipt 검증은 변경된 경계에 맞춰 수행한다. 진단만 바뀌면 해당 경계 회귀만, 공유 동작이 바뀌면 영향 소비자의 실제 수용까지 수행한다.
- PDF 실제 저장 bytes의 face/style·원문/검색과 화면을 확인하고 인쇄 payload·패널 취소를 별도로 기록한다. 물리 출력과 혼동하지 않는다.
- signed Finder 검증이 필요한 단계에는 대상 앱·보관함·교체/복원 범위를 구체화한 뒤 승인된 표준 smoke만 사용한다. 시험 후 원래 앱·등록 상태를 복원하고 소유 부산물을 정리한다.
- 웹은 기존 스타일·키보드/링크·모바일 폭·명암·스크린샷의 정보 노출과 실제 메뉴를 확인한다. 화면 변경을 작업지시자에게 제공한다. 코드와 사이트 공개 시점의 버전 안내를 일치시킨다.
- 최소 macOS/Intel 실제 실행 등 확보되지 않은 환경은 미검증으로 남겨 출시 판단에 포함한다. 컴파일/다른 OS 성공으로 대신하지 않는다.

## 8. 리스크

- OS가 thumbnail 요청을 생략하거나 extension PID가 바뀌면 성능 비교가 왜곡될 수 있다. 요청 로그·PID·cache 상태·동시 대기를 분리한다.
- metadata 재사용 최적화는 새 설치/삭제·동명 교체·정책 변경에서 stale 결과를 만들 수 있다. 성능 수치와 정확성을 함께 수용해야 한다.
- signed 확장의 설치 원본 권한과 HostApp 권한은 다르며 설정 bookmark가 자동 전달되지 않는다. 소비자별 실제 결과를 안내에 반영한다.
- 이전 단계의 서로 다른 signed 빌드를 최종 후보 전체 통과로 취급하면 출시 근거가 부정확해진다. 최종 후보의 필요한 동작을 묶어서 확인한다.
- 공개 웹이 다음 기능을 현재 v0.2.2에서 제공하는 것처럼 보일 수 있다. `main`/Pages 반영 시점과 release gate를 맞춘다.
- TTC/가변/HFT·복합 typography·실제 한컴 제거·물리 프린터 등의 제한은 기능 소개와 별개로 남는다. Mac 부분 완료로 Windows 또는 상위 이슈를 닫지 않는다.

## 9. 승인 요청 사항

이 수행계획의 **Mac 선출시 준비 범위와 5단계 진행**을 승인 요청한다. 승인 후 구현계획을 작성하여 Stage 1 측정 계약·후보 검증 방법부터 구체화한다. 성능 구조 변경, 새 ABI/core pin, 구체 signed 설치 시험 또는 공개 release gate는 대상과 결과가 준비된 시점에 범위를 확인한다.

현재 승인으로 Windows를 기다리지 않고 Mac 성능 확인·사용 안내·출시 수용을 준비하는 방향을 기록했다. 구체 patch/build number·서명 대상·workflow 입력과 최종 공개 시점은 확정하지 않았다.
