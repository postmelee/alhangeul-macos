# Task M900 #356 수행계획서

## 목적

다음 public release부터 릴리즈 노트를 코드 전체 diff 또는 path 기반 checklist 초안이 아니라, 직전 공개 릴리즈 이후 merge된 PR, 연결 Issue, 작업 최종 보고서를 1차 입력으로 작성하도록 매뉴얼과 자동화를 보강한다.

확정된 작업 식별자는 다음과 같다.

| 항목 | 값 |
|------|----|
| GitHub Issue | #356 |
| GitHub milestone | `Release Operations` |
| 문서 분류 코드 | M900 |
| 기준 브랜치 | `devel` |
| 작업 브랜치 | `local/task356` |

## 배경

`v0.1.5` public release 과정에서 GitHub Release body에 placeholder 문구가 남았고, 이후 본문을 직접 보정했다. 또한 `v0.1.5`에는 PR #324, PR #326, PR #329, PR #334, PR #349, PR #352 등이 포함되었지만, 초기 보정 문구는 전체 PR, Issue, 최종 보고서 분석 없이 앱 자체 변화가 크지 않다는 식으로 축약됐다.

현재 `scripts/ci/write-release-delta-checklist.sh`는 `previous_release_ref..candidate_ref` 범위의 변경 파일 path를 분류하는 보조 도구다. 이 도구는 누락 확인에는 유용하지만, release note의 사용자-facing 판단을 대신하기 어렵다. 따라서 release note 작성의 1차 입력을 merge PR과 연결 Issue, `mydocs/report/task_*_report.md` 분석으로 고정하고, path 기반 delta checklist는 보조 자료로 격하해야 한다.

최근 PR #355 변경으로 `scripts/ci/write-release-notes.sh`가 `mydocs/release/v<version>.md`의 `GitHub Release 본문 구조 후보`를 사용하도록 보강됐고, `scripts/ci/check-release-notes-template.sh`에는 상세 문서 링크와 placeholder 금지 검증이 추가됐다. 이번 작업은 그 다음 단계로, 포함 PR 분석 표와 GitHub Release의 PR/Issue section을 표준 구조와 검증에 포함한다.

## 범위

포함:

- `previous_release_ref..candidate_ref` 범위의 merge PR 목록을 만드는 절차 문서화
- 각 PR의 title/body, linked Issue, `mydocs/report/task_*_report.md`를 읽는 release note 작성 절차 문서화
- PR별 분류 기준을 사용자-facing, 개발자-facing, 운영/배포, 문서-only, upstream sync로 정의
- `mydocs/release/v<version>.md` 표준 구조에 `포함 PR 분석` 표 추가
- GitHub Release와 Pages의 `변경 요약` / `알한글 앱 변화`를 사용자-facing 판정 항목만 기준으로 작성한다는 규칙 명시
- path 기반 delta checklist는 누락 확인용 보조 자료로만 사용한다는 규칙 명시
- GitHub Release body에 직접 반영된 PR과 해결된 Issue를 #N 형식으로 명시하는 section 추가
- 해결된 Issue와 관련 Issue 구분 기준 문서화
- release note generator/checker 또는 별도 helper의 자동화 보강
- GitHub 공개 본문 작성 시 `--body-file`과 `scripts/validate-github-body.sh`를 사용하고, `#123` 뒤에 한글 조사가 붙지 않게 하는 검증 경로 유지

제외:

- 새 public release 실행
- `v0.1.5` GitHub Release body 또는 Pages 문구의 즉시 재수정
- 전체 코드 semantic diff 자동 분석
- PR/Issue 자동 분류의 완전 자동 승인
- 제품 기능 구현
- Homebrew Cask 배포

## 설계 방향

릴리즈 노트 생성 흐름을 `PR/Issue/report 분석 -> 포함 PR 분석 표 -> 공개 표면 요약 -> path delta checklist 보조 확인` 순서로 재정렬한다.

1. release owner가 `previous_release_ref`와 `candidate_ref`를 확정하면, 해당 범위에서 merge commit 또는 GitHub API 기준 merged PR 목록을 수집한다.
2. 각 PR에 대해 title, body, closing keyword, linked Issue, 관련 작업 최종 보고서를 확인한다.
3. PR별 row에 분류, 사용자-facing 여부, 공개 요약 반영 여부, 해결된 Issue, 관련 Issue, 근거 문서, 비고를 기록한다.
4. `변경 요약`과 `알한글 앱 변화`는 `포함 PR 분석`에서 사용자-facing으로 판정된 항목만 기준으로 작성한다.
5. GitHub Release body에는 사용자 요약 뒤쪽에 직접 반영된 PR과 해결된 Issue section을 두고, 단순 참고 Issue는 관련 Issue로 분리한다.
6. path 기반 delta checklist는 영향 영역 누락 확인과 smoke 필요 영역 점검에만 사용한다.
7. 공개 GitHub body는 body file로 작성하고 `scripts/validate-github-body.sh`를 통과한 뒤 등록한다.

## 잠정 단계

1. Stage 1: 현행 release note 경로와 요구사항 분석
   - release 매뉴얼, `write-release-notes.sh`, `check-release-notes-template.sh`, `write-release-delta-checklist.sh`, release workflow의 현재 역할을 정리한다.
   - `v0.1.5` 기록을 사례로 포함 PR 분석 표에 필요한 column을 확정한다.
2. Stage 2: release record와 매뉴얼 표준 구조 보강
   - `mydocs/release/v<version>.md`의 표준 구조에 `포함 PR 분석` 표를 추가한다.
   - 공개 요약은 사용자-facing PR만 기준으로 작성하고, 해결된 Issue와 관련 Issue를 분리하는 규칙을 문서화한다.
3. Stage 3: 자동화 helper와 release note generator 보강
   - merge PR 목록과 기본 분석 표 초안을 만들 helper 또는 기존 generator 옵션을 구현한다.
   - GitHub Release body에 직접 반영된 PR/Issue section을 생성 또는 검증하도록 `write-release-notes.sh`와 checker를 보강한다.
4. Stage 4: workflow/CI 연결과 검증
   - rehearsal/publish workflow 또는 PR CI에서 새 helper dry-run과 template check가 깨지지 않게 연결한다.
   - `scripts/validate-github-body.sh`를 GitHub 공개 본문 검증 경로에 유지한다.
5. Stage 5: 단계 보고, 최종 보고, PR 준비
   - 검증 결과와 잔여 수동 판단 영역을 보고서에 남기고 최종 보고서와 PR body 초안을 준비한다.


실제 GitHub Release 등록 또는 수정은 이번 작업 범위에서 수행하지 않는다. 필요한 경우 별도 release 실행 이슈와 작업지시자 승인 gate에서 `--body-file`을 사용한다.

## 리스크

- GitHub API와 git log 기준 merged PR 목록이 다를 수 있으므로, 자동화 결과는 release owner가 확인해야 한다.
- PR body의 closing keyword가 없거나 작업 문서가 누락된 경우 해결된 Issue를 과대 계산할 수 있다.
- upstream sync PR은 사용자-facing 변화와 provenance 변경이 섞일 수 있어 단순 분류만으로 공개 요약을 확정하면 안 된다.
- `mydocs/report/task_*_report.md` 파일명은 milestone과 task 번호를 포함하므로, linked Issue 번호만으로 보고서를 찾지 못하는 경우 수동 보정 경로가 필요하다.
- GitHub Release body에 PR/Issue section을 추가할 때 `#123` 뒤에 한글 조사가 바로 붙으면 GitHub autolink가 깨질 수 있다.
- 새 helper가 GitHub API 인증에 의존하면 로컬 CI와 GitHub Actions에서 실패할 수 있으므로, 가능한 한 git metadata 기반 경로와 `gh` 사용 경계를 분리해야 한다.
