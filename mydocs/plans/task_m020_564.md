# Task #564 — 공통 글꼴 가져오기·관리 기반 수행계획서

- 상태: 수행·[구현계획](task_m020_564_impl.md) 승인, Stage 3 완료 및 Stage 4 승인 대기

## 1. 목적

Mac 자동 탐색과 Windows 폴더·ZIP 입력이 공통으로 사용할 글꼴 검증·독립 저장·관리 기반을 구현한다. 원본 앱이나 파일이 없어져도 관리 복사본을 읽을 수 있도록 하고, 후속 화면·출력 경로에 검증된 리소스를 전달할 계약을 제공한다.

## 2. 배경

[#563 최종 보고서](../report/task_m020_563_report.md)와 [글꼴 마이그레이션 설계](../tech/font_migration_design.md)를 기준으로 한다. 공개 TTF·OTF의 독립 복사본 공급은 실험에서 확인했으나 제품 importer, App Group 저장소, 충돌·복구·삭제 처리는 미구현이다. TTC는 face 목록 확인과 실제 face 선택이 달랐으며, 가변 글꼴은 공개 1종의 일부 weight만 검증했다.

현재 `Sources/Shared`는 앱·확장 공통 helper를 소유하고, `FontResourceRegistry`는 프로세스 단위 등록을 담당한다. 기존 등록을 영구 저장소로 간주하지 않는다. 현재 HostApp entitlement에 App Group 설정이 없어 identifier·서명·접근 검증이 필요하다.

## 3. 범위(포함·제외)

포함:

- App Group 저장 위치·identifier·entitlement 설정과 HostApp 접근, 접근 실패의 명시적 처리.
- 실제 파일 구조·크기·해시 검증, SFNT face와 다국어 이름·스타일·버전·가변 축·사용 조건 메타데이터.
- 독립 복사, 중복 판정, 동명 충돌과 활성 선택 유지, 부분 실패·취소 결과.
- 원자적 manifest 게시, 프로세스 간 writer 잠금, 재시작·중단·용량 부족·손상 복구.
- 목록·삭제·재등록을 위한 서비스 계약, snapshot·lease·안전한 물리 삭제.
- 후속 소비자를 위한 불투명 리소스 ID와 검증된 bytes 읽기 인터페이스 및 회귀 검증.

제외:

- Mac 자동 탐색·위치 선택 및 가져오기 UI(#565), Windows 폴더 순회·ZIP 해제(#566).
- 문서 이름 resolver와 Studio CSS/CanvasKit 연결(#567), PDF·인쇄·확장 renderer 연결(#568).
- 웹페이지 안내·전체 제품 수용(#569), HFT 해석, 상용 글꼴 재배포, 한컴 앱 삭제.

확장의 실제 저장소 소비·서명 통합 검증은 #568 소유다. 이번 App Group 기반 검증을 확장의 렌더링 완료로 보고하지 않는다.

## 4. 설계 방향

- `FontLibrary/v1` 아래 해시 기반 불변 객체와 원자적으로 교체되는 manifest를 둔다. 같은 입력 핸들에서 읽은 bytes로 검증·해시·복사를 일치시키고 staging → 객체 게시 → manifest 게시 순서를 따른다.
- writer 잠금 안에서 최신 세대를 다시 읽는다. 미지원 schema를 덮어쓰지 않고, 실패 시 기존 유효 목록과 객체를 보존한다. 내구성·복구 지점은 구현계획에서 명시한다.
- 동일 해시는 중복으로, 이름이 같고 bytes가 다른 항목은 충돌로 다룬다. 기존 활성 선택을 유지하며 버전 문자열로 자동 교체하지 않는다. 일반·굵게 스타일을 구분한다.
- 객체·SFNT face index·가변 축을 구분하고 다국어 원본 이름을 보존한다. CoreText descriptor 수를 collection face 수로 간주하지 않는다.
- 저장 성공·적용 가능·실제 렌더링·fallback 상태를 분리한다. static TTF·OTF를 우선하며 TTC와 가변 항목은 검증된 지원 범위를 넘겨 적용 성공으로 표시하지 않는다.
- snapshot의 generation·digest에 선택 face·axes를 포함한다. 논리 삭제 후에도 실행 중 lease가 참조하는 객체는 유지한다. Stage 3에서 확정한 lease 파일의 kernel 잠금 소유 여부로 생존을 확인하며 시간 경과만으로 lease를 폐기하지 않는다.
- 원본 경로·bookmark는 로컬 출처 정보로 한정한다. 공급 인터페이스는 허용된 리소스 ID만 받고 객체 무결성을 확인한다. 로컬 복사 허용 근거와 임베딩 허용 근거는 별도로 보존한다.
- 잠정 입력 한도(파일 64 MiB, 입력 4,096개·1 GiB, 탐색 깊이 32)는 실측 전 확정하지 않는다. 공통 기반은 파일·누적 bytes 한도를 검증하고 탐색 깊이는 후속 입력 계층에 인계한다.

## 7. 검증 계획

- 정상 TTF·OTF, collection, 가변, 손상·확장자 불일치·미지원 입력을 검증한다. 테스트 자산은 사용 조건과 출처를 보존하고 사용자 원본을 변경하지 않는다.
- 같은 해시의 반복 입력, 동명 다른 버전, 일반/굵게, 다국어 이름, 일부 파일 실패·취소에서 항목별 결과와 기존 활성 선택을 확인한다.
- staging/객체/manifest 게시 경계에 장애를 주입한다. 별도 프로세스 재실행과 동시 writer로 복구·원자성·잠금 계약을 확인한다.
- 원본을 격리한 새 프로세스에서 관리 bytes 읽기, 관리 객체 변조 거부, 원본 권한 상실과 관리 저장소 접근 실패를 구분한다.
- snapshot 획득 중 삭제, 프로세스 종료·비정상 종료·식별 불확실 상황에서 참조 객체 보존과 정리 조건을 검증한다.
- App Group identifier·entitlement·실제 서명된 HostApp 접근을 확인한다. macOS 12 컴파일과 macOS 12 실행은 별개로 기록한다. 필요한 서명 자격이나 최소 OS 환경이 없으면 미검증 수용 항목으로 남겨 보고한다.
- [빌드·검증 가이드](../manual/build_run_guide.md)의 변경 유형별 최소 검증을 수행한다. 독립 테스트와 제품 빌드를 구분하고, `.app`/`.appex`는 `build.noindex/` 아래에 둔다. 확장 등록이 필요하면 표준 smoke 절차와 해제를 따른다.
- 문서 링크·`git diff --check`·관련 CI를 확인한다. 제품 화면/PDF 렌더링 성공은 이번 저장소 테스트로 대신 판정하지 않는다.

## 8. 리스크

- App Group 설정과 서명 환경에 따라 실제 접근 결과가 다를 수 있다. 일반 디렉터리 테스트만으로 배포 접근을 검증했다고 보지 않는다.
- 충돌 키를 과도하게 정규화하면 다른 글꼴을 합칠 수 있다. 원본 이름과 식별자를 보존하며 상세 resolver는 후속 계약으로 분리한다.
- 큰 입력·악성 메타데이터·파싱 실패가 메모리와 처리 시간에 영향을 준다. 크기 제한과 실패 격리를 검증한다.
- 게시 도중 종료나 잘못된 lease 정리는 유효 데이터 손실을 만들 수 있다. 복구와 물리 삭제는 별도 실패 시나리오로 검증한다.
- TTC·가변 메타데이터 수집만으로 실제 선택을 보장하지 않는다. 제한 상태가 후속 UI·renderer까지 유지되어야 한다.
- 글꼴별 복사·사용·임베딩 조건은 동일하지 않다. 메타데이터만으로 사용 허가를 자동 확정하지 않는다.

## 9. 승인 요청 사항

- #564 공통 기반을 위 범위와 잠정 4단계로 진행한다.
- 수행계획 승인 후 구체적인 파일·API·복구 절차·테스트를 담은 구현계획서를 작성한다.
- 구현계획 승인 후 소스 구현에 착수한다. 이번 수행계획 작성 단계에서는 제품 소스와 매뉴얼을 변경하지 않는다.
