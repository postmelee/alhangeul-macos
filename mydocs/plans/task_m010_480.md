# Task M010 #480 수행계획서

## 목적

암호 문서를 WKWebView 기반 HostApp에서 저장할 때 암호화가 사용자에게 알리지 않고 제거되는 문제를 막고, upstream `rhwp v0.8.4`가 제공하는 HWP/HWPX 암호 export 기능을 native 저장 흐름에 안전하게 연결한다.

암호 문자열은 저장 시점에만 사용하고 영속화하지 않으며, 암호 입력 취소·export 실패·저장 실패가 원본 파일 변경으로 이어지지 않는 계약을 확립한다. HWP3 입력은 실제 지원 가능한 출력 형식과 보호 정책을 별도로 명시해 사용자 기대와 검증 기준을 일치시킨다.

## 배경

Alhangeul v0.1.10은 upstream `rhwp v0.8.4`, commit `496333b27d21ddb9114ba9ae340bcb895870c9a7`의 암호 문서 열기와 암호화 serializer를 포함한다. Bundled WASM binding에는 `exportHwpWithPassword`와 `exportHwpxWithPassword`가 존재하고, upstream Studio는 `다른 이름으로 저장` 대화상자에서 `암호 설정...`을 선택했을 때 이 전용 exporter를 호출한다.

HostApp은 macOS 저장 패널과 원본 URL 접근을 소유하기 위해 Studio의 저장 메뉴·단축키를 capture 단계에서 가로챈다. 현재 `RhwpStudioHostBridgeScript`는 HWP에 `exportHwpBase64`/`exportHwp`, HWPX에 `exportHwpx`만 요청하고, `DocumentSaveContract`, `DocumentSavePanel`, `RhwpStudioWebView`의 pending request에도 문서 보호 상태나 출력 암호가 없다. 따라서 암호 문서를 연 뒤 `Command+S`를 실행하면 평문 export 결과가 원본 URL에 atomic write될 수 있다.

Upstream Studio의 production host RPC도 현재 암호 exporter와 원본 보호 상태를 공개하지 않는다. 단순히 bundled minified asset을 직접 수정하거나 unreleased upstream commit을 안정 기준으로 고정하지 않고, 현행 release-tag provenance 정책을 지키면서 즉시 안전장치와 완전한 암호 저장 연결의 선행 조건을 구분해야 한다.

## 범위

포함:

- v0.1.10 설치본과 exact bundled Studio 기준으로 HWP3/HWP5/HWPX 암호 문서의 열기, 일반 저장, 암호 저장 가능 표면을 재현하고 평문화 조건을 고정한다.
- Studio와 HostApp 사이에 원본 보호 상태, 출력 보호 의도, format, byte count를 전달·검증하는 저장 계약을 설계한다.
- 완전한 암호 export 연결 전이라도 암호 문서의 무경고 in-place 평문 overwrite를 차단한다.
- HWP/HWPX native 저장 또는 다른 이름 저장에서 사용자가 평문 복사본과 암호 보호 저장을 명시적으로 선택할 수 있는 UX를 설계·구현한다.
- 암호 저장을 선택하면 새 암호와 확인 값을 입력받고, 후속 저장마다 재입력하며, 취소·오류 시 원본을 변경하지 않는다.
- 암호 문자열이 JavaScript/native 로그, 최근 문서, autosave metadata, UserDefaults, Keychain, 분석 event와 작업 문서에 남지 않는지 검증한다.
- HWP5/HWPX 보호 저장·재열기와 HWP3 입력 정책을 fixture 및 HostApp 회귀로 고정한다.
- README, v0.1.10 업데이트/릴리스 기록과 known limitation을 실제 native 지원 범위에 맞게 보정한다.

제외:

- 열 때 입력한 암호를 보관하거나 자동 재사용하는 기능
- DRM, 배포용 문서, HWP5 `EncryptVersion` 1~3 등 upstream 미지원 보호 형식
- upstream 암호화 알고리즘 또는 파일 포맷 serializer 자체 변경
- bundled Studio minified JavaScript의 수동 patch
- unreleased upstream branch/floating ref를 stable core·Studio 기준으로 채택하는 작업
- Quick Look/Thumbnail에서 암호 문서를 해독하거나 암호를 입력받는 기능
- public patch release, 서명, 공증, GitHub Release, appcast, Homebrew 배포 실행

## 설계 방향

1. 보호 상태와 암호 문자열을 분리한다. HostApp과 Studio는 `plain`/`passwordProtected` 같은 상태와 출력 의도만 장기 상태로 유지하고 실제 암호 문자열은 한 번의 export 요청 지역 범위에서만 전달한다.
2. 기본 안전 정책은 암호 문서의 무경고 보호 해제를 금지하는 것이다. 보호 상태가 확정되지 않거나 암호 exporter가 준비되지 않은 경우 in-place 저장을 허용하지 않고, 명시적 평문 복사본 저장 또는 취소로 제한한다.
3. 저장 순서는 `옵션 선택 → 암호 확인 → export → payload 보호 상태 검증 → atomic write → Studio clean 동기화`로 고정한다. 앞 단계가 실패하면 다음 단계로 넘어가지 않는다.
4. 출력 암호는 최소 길이와 확인 일치를 저장 전 검증하고, 문자열 보간·URL·파일명·오류 메시지·telemetry에 포함하지 않는다. JavaScript 문자열의 완전한 zeroize는 보장할 수 없으므로 DOM과 지역 참조를 즉시 비운다.
5. HWP3 입력은 upstream public exporter가 실제로 생성하는 형식이 HWP3 원형인지 HWP5 EncryptVersion 4 변환인지 Stage 1에서 실증한 뒤 UI 문구와 완료 기준을 고정한다.
6. 현재 production host RPC에 필요한 표면이 없으면 upstream integration contract를 별도 선행 변경으로 분리한다. Alhangeul에는 release tag로 제공된 표면만 sync하고, 그 전에는 안전 차단을 유지한다.
7. 문서 보호 여부를 CFB/ZIP signature만으로 추정하지 않는다. 가능한 경우 upstream parser/WASM이 판정한 상태를 source of truth로 사용하고, 응답에는 암호가 아닌 enum/boolean만 포함한다.
8. 기존 평문 HWP/HWPX 저장, 저장 후 같은 URL 후속 `Command+S`, save panel 취소, dirty/clean 동기화 계약은 회귀시키지 않는다.

## 잠정 단계

1. Stage 1: exact v0.1.10 기준 HWP3/HWP5/HWPX 저장 재현, 보호 상태·export RPC·HWP3 출력 정책을 조사하고 즉시 안전장치와 upstream 선행 조건을 확정한다.
2. Stage 2: 문서 보호 상태와 저장 의도 계약을 추가하고, 암호 문서의 무경고 in-place 평문화 overwrite를 차단하는 HostApp 회귀를 구현한다.
3. Stage 3: 승인된 RPC 표면을 사용해 native 암호 설정 UI와 HWP/HWPX password export를 연결하고 취소·오류·후속 저장 보안 계약을 구현한다.
4. Stage 4: HWP3/HWP5/HWPX fixture round-trip, 기존 평문 저장 회귀, HostApp build/smoke와 릴리스 문서 보정을 완료한다.

Stage 1에서 upstream release tag 없이는 Stage 3을 안전하게 구현할 수 없다고 판정되면, Stage 2 안전 차단까지 완료한 뒤 upstream 선행 이슈/PR과 후속 sync 조건을 별도 승인받는다. 이를 우회하기 위해 minified bundle이나 floating ref를 사용하지 않는다.

암호 저장 fixture 검증은 HWP5와 HWPX 각각 다음 계약을 자동화한다.

- 암호 문서 열기 성공
- 편집 후 무경고 plain in-place overwrite 거부
- 암호 저장본의 무암호·오답 열기 거부
- 올바른 암호 재열기와 편집 내용 확인
- 암호 입력 취소, export 실패, write 실패에서 원본 byte hash 유지
- 명시적 평문 복사본 저장 시 원본 보존과 사용자 경고 확인
- 저장 완료 뒤 dirty/clean 상태와 후속 `Command+S` 재입력 확인

HWP3는 원본 형식 보존 또는 HWP5 변환 중 Stage 1에서 승인된 정책에 따라 동일한 보호·재열기 기준을 적용한다. 수동 smoke에는 release artifact 복사본 또는 사용자 원본이 아닌 test fixture만 사용하며, 로그와 보고서에는 실제 암호를 기록하지 않는다.

## 리스크

- Production Studio host RPC가 password exporter와 source protection state를 노출하지 않아 Alhangeul 변경만으로 완전한 기능 연결이 불가능할 수 있다. 이 경우 upstream integration surface와 release tag가 선행되어야 한다.
- 암호 문서 감지를 DOM 대화상자 관찰이나 오류 문자열에 의존하면 Studio UI 변경에 취약하고 오탐이 생길 수 있다. parser/WASM의 명시적 상태 계약을 우선한다.
- 암호 입력을 Swift에서 JavaScript로 전달하는 과정에서 script 문자열, 오류, Web Inspector 또는 로그에 노출될 수 있다. 구조화된 message contract와 비로그 정책을 검증한다.
- 암호 export 뒤 payload signature만 검사하면 실제 보호 여부를 보장하지 못한다. 보호 상태 metadata와 무암호 재열기 거부 fixture를 함께 사용한다.
- 평문 복사본 저장 UX가 모호하면 사용자가 원본 보호가 유지된다고 오해할 수 있다. 원본 overwrite 차단과 명시적 경고를 분리한다.
- HWP3 입력이 HWP5로 변환되면 형식 보존 기대와 내용 손실 위험이 생긴다. Stage 1에서 exporter 결과와 content-loss 보고 표면을 확인한 뒤 정책을 확정한다.
- 테스트 fixture 암호를 운영 암호처럼 다루거나 문서에 실제 사용자 암호를 기록할 위험이 있다. 공개 테스트 전용 값만 코드에 두고 작업 기록에는 값 자체를 남기지 않는다.
- 새 upstream release를 기다리는 동안 기능을 한 번에 완료하려고 floating ref를 사용하면 release provenance를 훼손한다. 안전 차단을 독립적으로 먼저 제공한다.

## 승인 요청 사항

- 위 포함·제외 범위와 4단계 잠정 진행 순서를 수행계획으로 승인받는다.
- Stage 1에서는 사용자 원본이 아닌 암호 fixture 복사본으로 평문화 재현과 byte hash 비교를 수행한다.
- Stage 1 결과 production host RPC 확장이 필요하면 upstream 선행 이슈/PR을 별도 범위로 제안하고, 작업지시자 승인 전에는 외부 저장소 변경이나 unreleased pin을 진행하지 않는다.
- 수행계획 승인 후 구현계획서 `mydocs/plans/task_m010_480_impl.md`를 작성해 단계별 산출물·검증·커밋 경계를 다시 승인받는다.
