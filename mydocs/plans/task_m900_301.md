# Task M900 #301 수행계획서

## 목적

`v0.1.4` public release를 준비하고, release runbook의 승인 gate에 따라 signed/notarized DMG, GitHub Release, Pages/Sparkle, Homebrew gate까지 실행 가능한 상태로 정렬한다.

확정된 release identity는 다음과 같다.

| 항목 | 값 |
|------|----|
| GitHub Issue | #301 |
| GitHub milestone | `Release Operations` |
| 문서 분류 코드 | M900 (`task_m900_301.md`) |
| release version | `0.1.4` |
| build | `10` |
| previous release ref | `v0.1.3` |
| expected rhwp tag | `v0.7.13` |
| 기준 브랜치 | `devel` |
| 작업 브랜치 | `local/task301` |

## 배경

최신 공개 앱 릴리즈는 `v0.1.3`이고, 현재 `devel`의 `rhwp-core.lock`과 bundled `rhwp-studio` manifest는 upstream `rhwp v0.7.13` 기준으로 맞춰져 있다. 반면 앱과 extension의 plist version은 아직 `0.1.3 (9)`이고, release rehearsal/publish workflow 기본 입력도 `version=0.1.3`, `previous_release_ref=v0.1.2`, `expected_rhwp_tag=v0.7.12`에 머물러 있다.

따라서 이번 작업은 새 기능 구현이 아니라 `v0.1.4 (10)` public release를 위한 source metadata, release communication, 검증 기록, publish input을 정렬하는 배포 실행 타스크다.

전용 `Release Operations` milestone을 새로 만들어 릴리즈 실행 이슈를 모으는 방향이 장기적으로 적합하므로, 작업지시자의 명시 승인으로 GitHub milestone을 생성하고 #301을 해당 milestone으로 이동했다. 운영 milestone 문서 코드는 `M900` 예약 영역을 사용한다.

## 범위

포함:

- HostApp, Quick Look, Thumbnail extension plist version을 `0.1.4 (10)`으로 갱신
- `Release Rehearsal DMG`, `Release Publish DMG` workflow 기본 입력을 `0.1.4`, `v0.1.3`, `v0.7.13` 기준으로 갱신
- `mydocs/release/v0.1.4.md` release record 초안 작성
- `docs/updates/v0.1.4.html`, `docs/updates/index.html` 갱신
- README 최신 공개 릴리즈 요약 갱신 여부 판단과 필요 시 갱신
- release note 후보와 delta checklist를 실제 사용자-facing 변화 기준으로 보정
- source preflight, rehearsal, public publish, Pages/Sparkle, Finder smoke, Homebrew gate 결과를 release record에 기록

제외:

- upstream `rhwp` 수정
- unreleased `rhwp` commit pin 적용
- Developer ID credential, notary credential, Sparkle private key, GitHub token 값 기록
- public DMG SHA256 확정 전 Homebrew Cask를 사용자 설치 경로로 안내
- public publish, GitHub Release 게시, Pages/Sparkle 갱신, Homebrew tap 반영을 승인 gate 없이 실행

## 설계 방향

릴리즈 실행 순서는 `mydocs/manual/public_release_runbook.md`를 우선한다. 각 위험 구간은 별도 승인 gate로 취급한다.

1. release candidate source를 `0.1.4 (10)`과 `rhwp v0.7.13` provenance 기준으로 정렬한다.
2. source-level 검증과 release helper dry-run으로 publish 전 결함을 먼저 제거한다.
3. rehearsal DMG는 public artifact로 사용하지 않고 layout, checksum, delta checklist 확인에만 쓴다.
4. public publish는 `main` 반영과 `v0.1.4` tag 확정 후, release owner 승인으로만 실행한다.
5. official stable release에서만 Sparkle stable appcast와 Pages deployment를 성공 조건에 포함한다.
6. Homebrew는 public DMG URL과 SHA256이 확정된 뒤 별도 승인 gate로 진행한다.

## 잠정 단계

1. Stage 1: release context와 source metadata 정렬
   - app/extension plist, release workflow default, existing release docs, current lock/manifest를 대조한다.
   - `0.1.4 (10)`, `previous_release_ref=v0.1.3`, `expected_rhwp_tag=v0.7.13` 기준으로 source metadata를 갱신한다.
2. Stage 2: release communication 작성
   - `mydocs/release/v0.1.4.md`, Pages release note, updates index, README 최신 요약을 정리한다.
   - `rhwp v0.7.13` 사용자-facing 변화와 알한글 앱 변화, known limitations를 구분한다.
3. Stage 3: source preflight와 rehearsal
   - lock/provenance, bundled asset, no-AppKit, Debug/Release build, render smoke, release helper dry-run을 수행한다.
   - 승인 후 rehearsal DMG 또는 workflow를 실행하고 delta checklist 초안을 보정한다.
4. Stage 4: main/tag/public publish gate
   - `devel` release candidate를 `main`에 반영할 PR 준비 자료를 완성한다.
   - `v0.1.4` tag, `Release Publish DMG`, GitHub Release, Pages/Sparkle은 release owner 승인 후 실행한다.
5. Stage 5: post-publish 확인과 Homebrew gate
   - public artifact, SHA256, signing/notarization/Gatekeeper, Pages, appcast, Finder smoke, Sparkle update smoke를 기록한다.
   - Homebrew 반영은 public DMG SHA256 확정 후 별도 승인으로 처리한다.

## 리스크

- release workflow 기본 입력이 stale한 상태에서 workflow_dispatch를 실행하면 lock guard에서 실패하거나 잘못된 delta checklist가 생성될 수 있다.
- `rhwp v0.7.13`은 렌더링/저장 호환성 변화가 많으므로 release note에서 앱 viewer, Quick Look, Thumbnail 영향과 한계를 분리해야 한다.
- public publish는 GitHub Actions release environment secret과 Pages environment 설정에 의존하므로, secret 값은 기록하지 않고 존재와 검증 결과만 남겨야 한다.
- rehearsal DMG, 개발용 zip, public DMG의 산출물 계층을 섞으면 Homebrew SHA나 Sparkle enclosure가 잘못될 수 있다.
- Intel Mac 실기기 smoke, GUI Quick Look preview, Sparkle update smoke를 실행하지 못하면 성공으로 기록하지 않고 미실행 사유를 남겨야 한다.
- 운영 milestone은 제품 버전과 직접 대응하지 않으므로, 문서명과 오늘할일 표기에서 `M900+` 예약 영역을 일관되게 사용해야 한다.
