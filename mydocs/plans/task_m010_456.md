# Task #456 수행 계획서

## 목적

HostApp WKWebView의 HWP/HWPX 형식별 저장 메뉴를 알한글 native 저장 경로에 연결한다. exporter, 저장 패널과 현재 문서 상태를 하나의 형식 계약으로 묶어 `.hwp`에는 HWP payload, `.hwpx`에는 HWPX payload만 기록되게 한다. HWPX로 저장한 뒤 `Command+S`를 실행해도 같은 URL에 `exportHwpx` 결과를 저장하도록 macOS 제자리 저장 동작을 완성한다.

## 배경

- GitHub Issue: #456
- Milestone: v0.1
- 문서 prefix: `task_m010_456`
- 작업 브랜치: `local/task456`
- 대상 통합 브랜치: `devel`
- 이슈 URL: https://github.com/postmelee/alhangeul-macos/issues/456

bundled `rhwp-studio`에는 `file:save-as-hwp`, `file:save-as-hwpx`, `exportHwp`, `exportHwpx`가 존재한다. 반면 현재 `RhwpStudioHostBridgeScript`의 native command와 export payload는 일반 `file:save`/`file:save-as` 및 HWP exporter 중심이고, `DocumentSavePanel`은 HWP 제목·확장자·UTType만 구성한다. `RhwpStudioWebView.Coordinator`도 `.hwp` 원본만 제자리 저장 대상으로 인정한다.

Issue #142 작업은 `Command+S` 제자리 저장과 `Command+Shift+S` 다른 이름 저장을 분리했지만 HWPX 저장 확대를 제외했다. 그 결과 형식별 메뉴는 upstream 브라우저 저장 fallback에 남고, HWPX 원본이나 HWPX로 저장한 문서의 다음 `Command+S`는 알한글 native 저장 계약으로 이어지지 않는다.

## 범위

포함:

- HWP/HWPX를 명시적으로 나타내는 HostApp 저장 형식 모델 도입
- `file:save-as-hwp`, `file:save-as-hwpx`를 injected bridge에서 native command로 routing
- 선택 형식에 따라 `exportHwp` 또는 `exportHwpx`를 호출하는 format-aware payload 생성
- pending save 상태에 저장 대상과 저장 형식을 함께 보관하고 message payload 형식을 검증
- `DocumentSavePanel`의 제목, 기본 파일명, 확장자와 `UTType`을 선택 형식에 맞게 구성
- HWP와 HWPX 원본의 security-scoped 제자리 저장 및 실패 시 형식 보존 save-as fallback
- HWPX로 저장한 URL을 현재 source document로 갱신하고 이후 `Command+S`에서 `exportHwpx` 유지
- 일반 `file:save-as`가 현재 HWP/HWPX 형식을 보존하고, 형식별 메뉴는 요청 형식으로 변환 저장
- 저장 성공 후 HostApp과 `rhwp-studio`의 파일명·dirty/clean 상태 및 최근 문서 상태 동기화
- HWP CFB signature와 HWPX ZIP/container signature, 재열기와 대표 내용 보존 검증
- 저장 ownership과 형식 정책을 architecture 문서에 반영

제외:

- upstream `rhwp` core 또는 bundled `rhwp-studio` asset 직접 수정
- upstream HWPX exporter가 지원하지 않는 모든 요소의 완전 무손실 보장
- native viewer/editor 저장 엔진 구현
- autosave/recovery 형식 정책 전면 변경
- PDF 메뉴 또는 PDF 생성 backend 변경
- 서명, 공증, 패키징과 public release 실행

## 설계 방향

저장 형식은 파일명 문자열을 흩어져 검사하지 않고 `hwp`와 `hwpx` 두 경우를 가진 명시적 모델로 둔다. 이 모델이 확장자, 기본 파일명 정규화, 저장 패널 title/UTType, JavaScript exporter method와 native validation의 공통 기준이 된다.

native command는 일반 저장, 일반 다른 이름 저장, HWP로 저장, HWPX로 저장을 구분한다. 일반 저장은 현재 source URL의 지원 확장자에서 형식을 결정하고, source가 없으면 기본 HWP 정책을 유지한다. 일반 다른 이름 저장은 현재 source 형식을 보존한다. 형식별 메뉴는 요청 형식을 명시해 save panel과 exporter를 같은 값으로 호출한다.

pending save는 단순 URL이 아니라 destination과 format을 함께 가진 요청 단위로 관리한다. export response에도 형식을 포함하고, Swift 쪽은 pending format과 response format, destination extension이 모두 일치할 때만 atomic write를 수행한다. 저장 성공 후 current source document를 새 URL로 갱신하고 `rhwp-studio`의 `notifySaved` contract를 호출해 다음 `Command+S`, unsaved guard와 표시 파일명이 저장 결과 형식을 따르게 한다.

기존 `.hwp` 제자리 저장, save panel fallback, 저장 취소와 오류 처리, 최근 문서 갱신은 유지한다. `Sources/RhwpCoreBridge`에는 AppKit/저장 UI 책임을 추가하지 않는다.

## 리스크

- HWPX exporter가 특정 HWP 전용 요소를 완전히 보존하지 못할 수 있으므로 형식 지원과 완전한 round-trip 보장을 구분해야 한다.
- extension만 바꾸고 exporter를 잘못 선택하면 손상 파일을 만들 수 있으므로 format을 pending request와 response 양쪽에서 검증해야 한다.
- HWPX source를 저장한 뒤 current source format을 HWP로 되돌리면 후속 `Command+S`에서 형식이 바뀌므로 URL·format·WebView 파일명 갱신을 하나의 완료 처리로 묶어야 한다.
- security-scoped write 실패 후 fallback이 다른 형식의 panel을 열면 사용자 의도와 결과가 달라질 수 있다.
- native 저장 성공 후 HostApp dirty state만 지우고 upstream document state를 지우지 않으면 종료/열기 guard가 중복 표시될 수 있다.
- 대용량 문서의 base64 bridge는 메모리 비용이 있으므로 기존 HWP 저장 대비 불필요한 복사를 늘리지 않아야 한다.
- `project.yml`이 Xcode project의 원본이므로 테스트 target 변경이 필요하면 `project.yml`을 수정하고 생성 결과만 검증한다.
