## 1. 목적

Mac에 설치된 한글의 글꼴 또는 Windows에서 옮긴 글꼴 폴더·ZIP을 알한글로 가져오기 위한 지원 범위와 설계를 확정한다. 이번 이슈는 조사·설계와 최소 기술 검증을 소유하며, 제품 기능 구현은 하위 후속 이슈에서 수행한다.

첫 수용 시나리오는 **Mac의 글꼴 가져오기 → 알한글 재실행 → 한컴 한글이 없는 환경에서도 문서 표시와 PDF 출력 유지**로 둔다. 한컴 앱의 파일을 계속 참조하는 방식만으로 이 요구를 충족했다고 판단하지 않는다.

## 2. 배경

사용자는 Mac을 사용하며, Mac에 설치된 글꼴을 알한글로 불러온 후 한컴 한글을 삭제하고 싶다고 밝혔다. OS에 설치된 글꼴과 한컴 앱 내부에만 존재하는 글꼴을 구분해야 하며, 설치 경로 탐색뿐 아니라 독립적인 보관·로드·이름 매칭이 필요하다.

현재 앱 화면은 bundled `rhwp-studio`, PDF·인쇄는 전용 WebView renderer, Quick Look·Thumbnail은 native renderer 경로를 사용한다. 각 경로의 기존 대체 글꼴 정책 때문에 파일을 가져오거나 목록에 이름을 표시하는 것만으로 실제 적용을 보장할 수 없다.

조사 시작 기준은 `rhwp-core.lock`에 고정된 `rhwp v0.8.6`, resolved commit `f1f9c6ae58344ee9368996d3543f76b9345cf227`이다. 최신 upstream의 동작과 현재 제품에 포함된 동작을 구분한다.

## 3. 범위

### 포함

- Mac 한글 설치본의 글꼴 위치와 OS에 설치된 글꼴의 차이, Windows 글꼴 폴더·ZIP 입력 구조 조사.
- TTF·OTF·TTC, collection face, 가변 글꼴, 굵기·스타일 및 한글·영문 family/full/PostScript 이름의 지원 가능성 확인.
- 자동 탐색, 사용자 위치 선택, 샌드박스 접근, 앱 관리 저장소 및 확장 프로세스의 글꼴 공유 설계.
- 원본 참조와 독립 복사의 비교, 중복·버전 충돌·등록·삭제·재실행 정책 정리.
- WebView 화면과 PDF의 최소 적용 검증 및 Quick Look·Thumbnail·선택 가능한 Skia 경로의 공급 경계 조사.
- 글꼴별 사용·복사·출력 임베딩 조건, 검증 자산 확보 및 후속 이슈 완료 기준 구체화.

### 제외

- 완성된 가져오기 UI·공통 관리 계층·출력 연동의 제품 구현.
- HFT 해석·변환, Windows 전용 내보내기 프로그램, 다른 PC 자동 접속.
- 사용자 한컴 앱 삭제 또는 시스템 글꼴 제거·교체.
- 상용 글꼴 파일의 저장소·제품 번들 재배포.
- 원본 한글의 모든 문서 배치 완전 재현, core pin 갱신, 릴리스·서명·공증·배포.

## 4. 설계 방향

1. Mac과 Windows 입력은 공통 글꼴 식별·관리 계약을 공유한다. Mac 사용자 시나리오를 먼저 검증하되 Windows 입력을 수용할 수 있게 설계한다.
2. 한컴 앱 삭제 후 독립 사용을 위해 앱 관리 저장소에 복사하는 방식을 우선 검토한다. 복사·사용 조건이 맞지 않거나 읽을 수 없는 글꼴은 이유를 표시한다.
3. 시스템 설치 글꼴은 설치 주체를 단정하지 않는다. 앱 전용 글꼴과 구분하고, 접근 가능 여부와 파일 확보 가능 여부를 따로 확인한다.
4. 파일명보다 내부 글꼴 이름·스타일·face를 기준으로 문서와 연결한다. 가져온 글꼴과 기존 fallback의 우선순위를 명시한다.
5. 화면·PDF·확장이 같은 글꼴을 사용할 수 있는 저장·공급 계약을 설계한다. WebView 로컬 글꼴 열거 API에만 의존하지 않는다.
6. 원본이 없는 상황은 격리된 테스트 원본과 앱 재실행으로 재현한다. 실제 사용자 한컴을 삭제하지 않으며, 실설치 환경 검증이 남으면 미검증으로 기록한다.
7. 최소 실험은 승인된 구현계획에 따라 수행하고, `rhwp-studio` 변경이 필요하면 upstream 소유 범위와 앱 측 연결 범위를 구분한다.

## 7. 검증 계획

- 시작 단계: 이슈 OPEN·마일스톤 확인, 기준 브랜치 최신화, 문서 9개 표준 섹션·링크·오늘할일 행 확인, `git diff --check`와 단일 커밋 확인.
- 조사: 공급자·Apple 공식 자료와 실제 확인한 설치본의 버전을 기록한다. 환경이 없으면 추정과 실측을 구분하고 대체 자산의 한계를 남긴다.
- 형식·이름: 한글·영문 별칭, regular/bold, TTC face, 중복·버전 충돌, 손상·미지원 파일을 확인한다.
- 독립 보관: 원본 파일을 참조할 수 없도록 격리한 뒤 앱/실험 프로세스를 재시작한다. 시스템에 남은 동일 글꼴이 성공을 가장하지 않는 대조군을 둔다.
- 실제 적용: 화면상의 이름 표시 외에 선택된 face/리소스와 글리프·측정 근거를 확인한다. PDF에서는 폰트 리소스 및 한글 검색·복사·ToUnicode를 확인한다.
- 출력 경로: Quick Look·Thumbnail·Skia에서 추가 구현이 필요한 부분과 검증 환경을 기록하고 #568 이슈에 인계한다. 개발용 확장 등록이 필요하면 표준 smoke 절차와 종료 후 해제를 따른다.
- 실험용 `.app`·`.appex`가 필요하면 `build.noindex/` 아래에 둔다. 사용자 문서·한컴 설치본·시스템 폰트는 삭제·수정하지 않는다.

## 8. 리스크

- 한컴 버전·배포 방식별 위치가 달라 자동 탐색만으로 모든 경우를 처리하지 못할 수 있다.
- 샌드박스와 확장 프로세스 권한 때문에 최초 위치 선택 및 저장소 공유 구성이 필요할 수 있다.
- WebView/native/PDF가 서로 다른 글꼴을 선택하거나 기존 fallback이 가져온 글꼴을 가릴 수 있다.
- 이름이 같은 다른 버전·스타일, TTC·가변 글꼴에서 매칭과 공급 방식이 달라질 수 있다.
- 복사·사용·임베딩 허용 조건과 실제 파일 확보 가능성이 다르므로 일괄 지원을 사전에 약속하지 않는다.
- 폰트 캐시나 시스템 설치본이 원본 독립성 검증을 왜곡할 수 있다. 격리 대조군과 미검증 환경 표기가 필요하다.
- 같은 글꼴이라도 줄바꿈·배치 완전 동일성을 보장하지 않으며, PDF Unicode 회귀는 별도 관문으로 둔다.
