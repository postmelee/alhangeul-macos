# Issue #492 수행 계획서

## 목적

HostApp에 bundled된 `rhwp-studio`의 글자색 및 형광펜 사용자 지정 색상 선택기가 macOS WKWebView에서 안정적으로 열리도록 호환성 경계를 보강한다. 색상 선택 전후의 텍스트 선택 영역과 편집기 포커스를 보존하고, upstream generated asset을 직접 수정하지 않는 앱 소유 대응과 반복 가능한 검증 기준을 마련한다.

## 배경

- GitHub Issue: [#492](https://github.com/postmelee/alhangeul-macos/issues/492)
- 관련 upstream 관찰: [edwardkim/rhwp#6635](https://github.com/edwardkim/rhwp/issues/6635)
- Milestone: `v0.1`
- 문서 prefix: `task_m010_492`
- 통합 브랜치: `devel`
- 작업 브랜치: `local/task492`
- 기준 통합 SHA: `b8c45fb`

현재 HostApp은 release tag `v0.8.4`, resolved commit `496333b27d21ddb9114ba9ae340bcb895870c9a7`의 `rhwp-studio` dist를 WKWebView에 표시한다. 관찰된 구현은 툴바 버튼의 `mousedown`에서 숨겨진 `input[type=color]`의 합성 `click()`을 호출하며, 해당 input은 크기가 0인 상태다. macOS WKWebView에서 글자색 버튼을 눌러도 시스템 색상 선택기가 열리지 않는 현상이 확인됐고, 형광펜의 “다른 색...” 경로도 유사한 구조를 사용한다.

upstream #6635는 일반 웹 UI의 표준 활성화와 접근성 의미론을 독립적으로 추적한다. 이 타스크는 그 수정 여부와 관계없이 현재 알한글 제품이 포함한 웹 UI를 WKWebView에서 지원하는 다운스트림 호환성 작업이며, upstream 이슈를 선행 조건이나 차단 관계로 두지 않는다.

포함:

## 설계 방향

upstream dist는 toolbar DOM과 편집 명령을 소유하고, Alhangeul은 macOS WKWebView에서 필요한 플랫폼 호환성만 소유한다. 따라서 generated asset을 패치하지 않고 기존 local CSS overlay 또는 `WKUserScript` 기반 HostApp compatibility layer에서 해결한다.

Stage 1에서는 크기 0인 input이 실제 native popover 실패의 원인인지, 합성 activation의 사용자 제스처 전달 또는 포커스 이동이 원인인지 분리한다. 우선안은 기존 `alhangeul-wkwebview-overrides.css` 안에서 color input에 유효한 native anchor 영역을 제공하는 CSS-only 보정이다. 이 방식이 버튼 클릭 영역, 선택 영역 또는 접근성 활성화를 깨뜨리면 HostApp이 문서 로드 후 idempotent하게 설치하는 좁은 compatibility script를 대안으로 검토한다.

compatibility script가 필요할 경우 기존 `RhwpStudioHostBridgeScript`와 WKWebView user script 주입 경계를 재사용하되, 중복 event listener 설치를 막는 flag와 대상 DOM 존재 여부 검사를 둔다. 마우스·키보드 활성화 처리와 선택 영역 보존을 분리하고, 색상 변경 이벤트를 중복 발생시키지 않는다. 새로운 bundled local asset을 추가하는 방식은 sync exclusion, manifest `local_overlay_paths`, asset 검증 변경이 함께 필요하므로 기존 CSS 또는 Swift-owned script로 해결할 수 없을 때만 선택한다.

AppKit `NSColorPanel` bridge는 웹의 기존 color input과 편집 명령 계약을 크게 바꾸므로 기본안에서 제외한다. 웹 네이티브 선택 경로로 안정화할 수 없다는 근거가 확인될 때 별도 설계 판단과 승인을 요청한다.

## 잠정 단계(3~6단계)

1. Stage 1: 재현과 원인 경계 확정
   - 현재 source resource 및 Debug app bundle에서 글자색과 형광펜 사용자 지정 색상 경로를 각각 재현한다.
   - 이벤트 순서, input rect, native picker 표시, 선택 영역과 포커스 변화를 기록한다.
   - CSS-only 보정과 HostApp compatibility script 대안을 비교하고 구현계획서(`task_m010_492_impl.md`)를 작성한다.
2. Stage 2: 최소 호환성 보정과 자동 검증
   - 승인된 ownership 경계에 따라 local CSS 또는 HostApp script를 최소 수정한다.
   - 중복 handler, generated asset 직접 수정, sync/provenance 회귀를 막는 정적 또는 단위 검증을 추가한다.
3. Stage 3: HostApp 빌드와 WKWebView interaction smoke
   - HWP/HWPX 문서에서 글자색과 형광펜 사용자 지정 색상을 적용한다.
   - 마우스·표준 활성화, 취소·반복 실행, 선택 영역·포커스·undo/redo와 app bundle resource를 검증한다.
4. Stage 4: 최종 보고와 PR 게시 준비
   - 원인, 적용한 다운스트림 호환성 경계, 자동 검증과 수동 smoke 결과를 최종 보고서에 정리한다.
   - 오늘할일을 완료 처리하고 `devel` 대상 PR 게시 절차로 인계한다.

각 단계는 단계 보고와 작업지시자 승인을 거친 뒤 다음 단계로 진행한다. upstream 이슈 처리, dependency 갱신과 public release는 이 타스크에서 자동 진행하지 않는다.

WKWebView interaction smoke 후보:

- HWP 및 HWPX 문서를 각각 열고 편집 가능한 텍스트 범위를 선택한다.
- 글자색 버튼을 마우스로 활성화해 시스템 색상 선택기가 보이는지 확인한다.
- 색상을 선택하고 기존 선택 범위에 글자색이 적용되며 편집기 포커스가 복구되는지 확인한다.
- 색상 선택을 취소한 뒤 다시 열어도 정상 동작하는지 확인한다.
- 형광펜 팔레트의 사용자 지정 색상 경로에서도 같은 절차를 반복한다.
- 표준 버튼 활성화와 접근성 activation 경로를 가능한 범위에서 확인한다.
- 색상 적용 후 undo/redo가 한 번의 사용자 동작으로 일관되게 처리되는지 확인한다.
- source와 Debug app bundle의 local compatibility resource가 동일하고 generated asset hash가 불필요하게 바뀌지 않았는지 확인한다.

정확한 재현 문서, DOM 계측 방법, 테스트 assertion과 수동 smoke 환경은 Stage 1 구현계획서에서 고정한다.

## 리스크

- 크기 0인 color input이 native popover 표시 실패의 유일한 원인이 아닐 수 있다.
- color input의 영역을 단순히 키우거나 버튼 위에 배치하면 편집기 선택 영역 또는 버튼 접근성 hit target을 빼앗을 수 있다.
- 합성 `click()`과 직접 input activation을 동시에 남기면 picker 또는 formatting event가 중복 발생할 수 있다.
- WKWebView의 user activation과 native color popover 동작은 macOS/WebKit 버전에 따라 달라질 수 있다.
- bundled studio 업데이트로 toolbar DOM id나 구조가 바뀌면 local selector 또는 script가 무효화될 수 있다.
- Swift 문자열 기반 JavaScript 검증은 native picker 자체를 자동으로 열 수 없으므로 최종 판정에는 수동 WKWebView smoke가 필요하다.
- 새 local asset을 추가하면 sync exclusion과 manifest provenance를 함께 변경하지 않을 경우 다음 full sync에서 유실될 수 있다.
- Debug app 실행이 LaunchServices에 개발 산출물을 등록할 수 있으므로 표준 build/run hygiene 절차를 지켜야 한다.

## 승인 요청 사항

1. 위 포함·제외 범위와 4단계 진행 구조 승인
2. Stage 1에서 CSS-only 보정을 우선 검토하고, 선택 영역 또는 활성화 계약을 충족하지 못할 때만 HostApp compatibility script로 확장하는 방향 승인
3. upstream #6635와 무관하게 현재 bundled studio의 WKWebView 호환성을 다운스트림이 소유하는 경계 승인
4. 다음 단계로 재현·원인 계측과 구현계획서(`mydocs/plans/task_m010_492_impl.md`) 작성을 진행할지 승인

승인 전에는 HostApp 소스, local CSS, asset 검증 스크립트 또는 매뉴얼을 변경하지 않는다. Stage 2 구현, Stage 3 앱 실행·interaction smoke와 PR 게시도 각 앞 단계 결과를 보고한 뒤 별도 승인받는다.
