## 설계 방향

### 명시적인 복구 결과와 세션 연결

upstream은 명령 경계에서 실패를 처리하고 복구 완료 후 결과를 발행한다. HostApp은 브라우저에 내용이 보이거나 특정 오류 문구라는 이유만으로 복구 성공을 추론하지 않는다. 이벤트 전송 방식·스키마 버전·capability와 성공 조건은 Stage 1에서 확정한다. 다음은 요구 필드와 의미이며 확정된 upstream API 이름이 아니다.

| 항목 | 요구 의미 |
|------|-----------|
| 버전·capability | 지원하는 오류 계약을 명시하고 미지원 번들과 구분 |
| 오류 코드·operation·이벤트 ID | 실패한 명령과 진단을 연결하고 반복 이벤트를 구별 |
| 복구 결과 | 내용, 편집 상태, history, dirty 및 후속 명령의 유효성을 확인한 결과. 성공·실패·불명을 구별 |
| 문서 식별 | native load와 editor 내부 문서 교체를 모두 식별. 현재 load token/loadID/documentEpoch와 대응 |
| 순서·revision | 늦은 결과가 새 문서나 치명적 실패를 덮어쓰지 않도록 처리 순서를 검증 |

메인 프레임·신뢰된 Studio origin 및 현재 세션의 이벤트만 수용한다. 임의 페이지나 오래된 문서의 이벤트로 상태를 정상화하지 않는다. 이벤트 상세에 문서 본문·경로·사용자 정보가 불필요하게 포함되지 않도록 한다. 일반 전역 예외와 구조화된 명령 실패의 중복 보고 정책도 계약에 포함한다.

현재 번들에는 계약이 없으므로 합성 payload 테스트와 실제 제품 수용을 구분한다. 알한글 수신부를 먼저 준비할 수 있지만, 공개 upstream API와 안정 release 반영이 없으면 실제 번들에서의 복구 성공 검증을 완료했다고 보고하지 않는다. upstream 계약이 기존 공개 API로 충족되지 않으면 필요한 요구사항을 명시하고 실제 연결에 필요한 단계·승인을 다시 정렬한다.

### 오류별 상태와 화면

복구 성공은 기존 WKWebView·세션·history·dirty를 유지하고, 사용자의 실패 명령·재시도 방법·진단 상세를 비차단 형태로 제공한다. 같은 오류가 반복될 때 중복 배너를 쌓지 않되 진단 확인은 가능하게 한다. 내용 유지 문구는 계약 검증이 끝난 경우에만 사용한다.

무결성 불명·복구 실패·프로세스 종료는 편집과 모델 기반 저장을 중지한다. 기존 화면을 유지할 수 있으면 읽기 전용으로 남기고, 프로세스 종료 등으로 화면을 확보할 수 없으면 그 상태를 정확히 안내한다. 마지막 화면은 복구 가능한 문서 bytes와 구분한다. fatal 뒤 들어온 세션·export·저장 callback은 기존 상태를 다시 활성화하거나 destination에 게시하지 않도록 검토한다.

현재 메시지 allowlist는 호환 대상과 종료 조건을 기록한다. 기존 예외 처리 변경은 #223, #235 이슈의 회귀 자료와 함께 검증하며 새로운 문자열 예외를 추가하지 않는다. 초기화·리소스·로드 실패를 복구 성공으로 낮추지 않는다.

### 유효한 복구본과 재시작

기존 editor snapshot DTO는 metadata이며 편집 문서 bytes가 아니다. 원본 입력 bytes 역시 오류 직전의 미저장 편집본이 아니다. upstream recovery draft와 HostApp의 내보낼 수 있는 bytes를 혼동하지 않는다.

Stage 1에서 사전 복구본의 공급 API, 생성 성공·형식 검증, 세션/revision·시각, 보관 수명·용량·성능, 암호·보호 문서 정책을 조사한다. 기존 source protection과 저장 정책을 우회하는 평문 복구본을 만들지 않는다. 안전한 사전 bytes를 확보하지 못하면 복구본 없음 상태를 제공하고 손상 여부가 불명인 현재 모델을 새로 export하지 않는다.

복구본 내보내기는 원본과 별도 destination을 사용하고 원본 바이트·편집 세션·dirty를 저장 완료로 바꾸지 않는다. 재시작은 미저장 편집 손실 가능성을 명시하고 취소할 수 있게 한다. 내보내기 취소·실패 시 재시작으로 자동 진행하지 않는다. 재시도 전에 복구본을 비우지 않고 교체 성공과 보존 정책을 확인한다. #525 이슈의 ‘저장하지 않음’과 복구 후보 폐기 정책은 별도 작업으로 유지한다.

- upstream 계약이 아직 없으며 안정 release 반영 전에는 현재 번들로 실제 성공 경로를 검증할 수 없다.
- WKWebView를 계속 표시하더라도 프로세스가 죽으면 마지막 화면이 유지된다는 보장이 없다. 시각 snapshot과 문서 복구본의 공급 가능성을 따로 판단한다.
- 전체 문서 사전 export는 대용량 문서 성능·메모리 비용과 보호 문서의 평문 보관 위험이 있다. 공급 정책을 확정하지 않고 매 입력마다 export하지 않는다.
- SwiftUI 조건 분기와 asynchronous callback이 세션을 재생성하거나 저장 차단을 우회할 수 있으므로 실제 container 통합을 검증한다.
- 알한글의 호스트 UX 개선만으로 원래 제보나 upstream 선택·삭제 결함이 해결됐다고 말할 수 없다.

## 승인 요청 사항

1. #594 범위를 위 오류 계약·복구 성공 시 세션 보존·치명적 오류 복구 UX 및 통합 검증으로 진행한다.
2. upstream 편집 알고리즘과 분리하고, 계약 미지원 번들의 한계를 명시하며 안정 버전 반영은 별도 승인 범위로 둔다.
3. 위 잠정 4단계를 기준으로 구현계획서를 작성한다. 실제 제품 코드 변경은 구현계획 승인 후 시작한다.
