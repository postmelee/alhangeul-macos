### 실제 Sparkle와 사용자 상태

2026-11-11 08:12 KST에 Sparkle UI로 설치·재실행했다. 업데이트 전 PID 53322, 자동 재실행 PID 53906과 0.2.4/22를 기록했다. About은 rhwp v0.9.0 (c9095c5)을 표시했다. 저장되지 않은 기존 문서 복구 알림은 ‘나중에’를 선택해 보존했다. KTX HWP의 노선도·요금표와 HWPX 보도자료 9쪽 표시를 확인했다. 처음 열었을 때의 빈 화면과 렌더링 완료 후 화면을 구분하고, 최초 표시 지연을 성능 PASS로 확대하지 않았다.

수동 등록 전에 preview·thumbnail이 `/Applications`의 0.2.4를 선택했다. `smoke-sparkle-extension-refresh.sh --expected-version 0.2.4 --expected-build 22` 기본 모드가 `Registration repair used: 0`으로 통과했다. helper의 캐시 초기화·소유 샘플 mdimport는 표준 보조 확인이며, 별도로 생성한 검색 대조 파일은 수동 색인하지 않았다. Finder에서 두 문서의 실제 미리보기와 새 이름의 썸네일을 확인했다. 기존 기본 열기 앱인 한컴 Viewer는 유지했다.

앱별 설정과 시스템 최근 문서 파일을 실행 전에 백업했다. 시험에서 추가된 최근 문서·창 위치·열기 폴더는 복원했고, 실제 업데이트의 유지보수·검색 요청·마지막 확인·분석 기록만 새 값으로 유지했다. 기존 글꼴 관련 설정과 복구본을 삭제하지 않았다. 최종 `/Applications` 앱과 Homebrew receipt는 0.2.4로 남긴다.

### Homebrew 검증

실제 tap의 style·일반 audit를 통과했다. 별도 tap CI는 없었다. 기존 0.2.2 receipt에서 upgrade했지만 당시 앱 bytes는 이미 Sparkle로 0.2.4였으므로 별도의 0.2.2 앱 업데이트로 세지 않는다. 제거 후 앱 부재를 확인하고 신규 install을 수행했다. 네 bundle은 모두 0.2.4/22·arm64/x86_64이며 설치 전후 실행 파일 해시가 같았다. 앱·preview·thumbnail은 Sparkle 설치본과도 일치했다. --zap은 사용하지 않았다. Homebrew 신규 설치본의 첫 실행에서는 macOS가 인터넷 다운로드 확인을 기다렸고, Apple 검사 통과 안내의 ‘열기’를 선택한 뒤 정상 첫 창과 공식 0.2.4 확장 두 개의 등록을 확인했다.

등록 위생 도구는 검증용 두 앱 내부의 `org.sparkle-project.Sparkle.Updater` 기록을 상위 개발 앱 등록으로 집계했다. 정확한 보조 앱 경로까지 한정해 해제를 시도했으나 macOS가 -10814를 반환해 이 두 오래된 기록은 남아 있다. 현재 활성 preview·thumbnail은 모두 `/Applications/Alhangeul.app`의 0.2.4다. 전역 LaunchServices 초기화와 검증 산출물 삭제는 하지 않았다. 이를 등록 위생 전체 PASS로 기록하지 않는다.

검색 대조군 TXT는 8.9초에 처음 검색됐지만, Homebrew 설치 변경 전 마지막 관측인 248.3초까지 HWP·HWPX의 한글 본문 결과는 없었다. 영어 본문과 종료 후 검색의 추가 조회도 비었으나 이는 후속 Homebrew 설치 후 관측이므로 원래 Sparkle 설치 상태의 600초 검증으로 합산하지 않는다. test mode 추출은 성공했고 원인·회귀 여부는 확정하지 않았다. [공개 후 검증 요약](../report/assets/task_m900_601/postpublish.json)에 범위를 기록했다.

실제 Mac의 검색 미확인은 [#587](https://github.com/postmelee/alhangeul-macos/issues/587)로 추적한다. 작업지시자가 2026-11-11 “검색은 #587로 남기고 대체 근거 수용·#601 종료”를 명시 승인했다. [Gate 8](../manual/public_release_runbook.md#gate-8-최초-설치와-실제-sparkle-업데이트-수용)의 예외 판단으로 양 VM 검색과 실제 설치 importer 추출을 수용한다. 실제 Mac 검색 자체는 미확인으로 유지한다. 최소 macOS 12와 Intel 실기기 GUI는 미실행이다.

## GitHub Release 본문 구조 후보

### 변경 요약

- 편집 명령이 실패해도 문서 상태가 복구되면 같은 창에서 계속 편집할 수 있습니다.
- 딸기 Regular 글꼴을 가져오면 sample10 HWP3·HWPX 표지에 지정된 굵은 글자를 화면과 PDF에서 볼 수 있습니다.

### 포함된 rhwp 변화

문서 엔진과 내장 Studio를 공식 [rhwp v0.9.0](https://github.com/edwardkim/rhwp/releases/tag/v0.9.0)으로 갱신했습니다. 편집 오류의 복구 상태를 앱에 전달하고, 기본 글꼴 서버가 응답하지 않을 때도 대체 글꼴로 문서를 열 수 있습니다.

### 알한글 앱 변화

- 여러 구역에 걸친 선택을 삭제하면 내용과 선택을 보존하고 편집을 중단합니다. 삭제하려면 한 구역씩 선택해 주세요.
- 복구를 확인한 문서에서는 실행 취소·다시 실행과 저장을 이어갈 수 있습니다. 복구를 확인할 수 없으면 편집과 저장을 중단해 이전 저장본을 보호합니다. 오류 안내에서 상세 정보를 복사할 수 있습니다.
- HWPX가 조판을 시작하기 전에 앱에 가져온 HFT 대응 글꼴을 연결합니다. 딸기 Regular만 있는 경우에도 문서에 지정된 굵기를 PDF에 적용하고 글자를 한 번씩 검색·복사할 수 있습니다.

## 공개 전 확인 사항

제보 원본 문서에서의 타이핑 지연은 이번 복구·초기화 검사로 성능을 판정할 수 없다. 동일 HWPX의 Windows 한컴 출력과 비교하면 표지의 대상 글줄이 약 4pt 오른쪽에 놓인다. 같은 OTF를 고정한 rhwp 대조에서 저장된 줄에 그림 오른쪽 여백 8.52pt가 다시 적용돼 중심이 4.26pt 이동했다. 이 후보에는 해당 위치 보정이 없다. [공식 태그의 줄 배치 계산](https://github.com/edwardkim/rhwp/blob/c9095c5f67632e6721e800ccc7fb43ea49d26682/src/renderer/layout/paragraph_layout.rs#L7101)

공식 Studio 외부 글꼴 공급자는 화면에 그릴 face를 제공하며 Rust의 첫 조판은 계약 범위 밖이다. 이 HWPX에서 공식 호스트 공급 경로의 딸기 읽기는 0회였고, 알한글은 조판 전에 공급 가능한 원본을 연결했다. [공식 공급자 계약](https://github.com/edwardkim/rhwp/blob/c9095c5f67632e6721e800ccc7fb43ea49d26682/rhwp-studio/HOST_FONTS.md#L29-L57)

실제 Mac의 Finder·Spotlight 본문 검색은 #587에서 추적한다. v0.2.3 당시 실제 Mac은 일반 TXT 검색부터 재현이 일정하지 않았고, 당시 VM 결과와 실제 importer 추출을 대체 근거로 수용했다. v0.2.4 서명본은 설치 후 첫 검색, 앱 종료 후 검색, 재설치 및 실제 업데이트를 별도로 검증한다. 공개 승격에는 버전별 Pages 안내 파일도 필요하다.

공개 입력 후보는 직전 참조 v0.2.3, expected_rhwp_tag v0.9.0, require_latest_rhwp=true, 제목 Alhangeul v0.2.4, draft=true, prerelease=false다. 공개 기준 main 커밋 확정 후 동일한 서명·공증 DMG로 설치와 업데이트를 검증하고 공개 승인을 받는다.
