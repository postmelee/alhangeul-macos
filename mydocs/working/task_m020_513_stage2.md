# Task M020 #513 Stage 2 — 자동 설치 판정 경로와 조건 분리

## 현재 관찰

| 실행 | 조건 | 발견 | 설치 전 본문 검색 |
|---|---|---|---|
| A | 기존 중첩 설치·수동 baseline 색인·일반 등록·60초 대기·첫 실행 | 실행 전후 60초 MISS | 미실행 |
| B | 같은 bytes/mtime, 새 중첩 경로, 수동 등록/색인 없이 첫 실행 | 36.28초 PASS | 60초 FAIL 및 추가 180초 FAIL |

B에서 실제 `mdimport -t`는 HWP3/HWP5/HWPX 모두 소유 후보를 선택하고 본문을 추출했다. 후보 종료 후에도 기존 문서는 검색되지 않았다. 이어 발견 후 새로운 HWP 하나만 생성하자 수동 색인 없이 그 파일만 검색됐다. 기존 문서의 재색인과 발견 후 신규 문서의 자동 색인이 갈린다. A와 B는 사전 등록 외에도 수동 baseline 색인 및 실행 전 대기 조건이 다르므로 사전 등록 하나를 원인으로 단정하지 않는다.

## 판정 경계

B의 corpus는 helper의 snapshot 검사를 추가하기 전에 준비됐다. `copytree(copy2)` 원본의 수정 시각/크기와 준비 시 저장한 fixture SHA-256이 설치된 corpus와 동일하고 설치 시각보다 앞섬을 확인하여 보강했다. 이 보강 경위를 원시 state의 snapshot_provenance에 남겼다. 이후 실행은 prepare 시 snapshot을 저장한다.

원시 state와 진단은 로컬 build.noindex/task513에만 보존한다. 기존 동일 bundle ID/버전/importer 변경 시각의 반복 등록 이력은 catalog 제거만으로 초기화되었다고 가정하지 않는다. 사용자 기존 앱과 시스템 database는 변경하지 않는다.

## 검증 절차 보완

- automatic 모드에서 수동 등록/재색인을 제외하고 실제 검색과 후보 선택을 구분한다.
- 설치 전 txt 환경·본문 부재, corpus hash/수정 시각 유지, 첫 실행 횟수, 진단 조작 이력을 검사한다.
- Applications 바로 아래 direct 소유 앱 위치와 사전 일반 등록 한 조건을 비교할 수 있게 한다.
- direct 앱은 정확한 경로와 directory device/inode, corpus owner marker를 확인한다.
- 발견 경과 시간과 관찰 시각을 기록한다.

## 남은 비교

이전 importer catalog와 프로세스가 제거된 뒤 direct 위치, 일반 사전 등록만 추가한 경로, importer 소스 변경 시각만 바꾼 진단을 비교한다. 수동 timestamp 진단 결과는 일반 최초 설치 통과로 쓰지 않는다. 제품 코드 변경은 아직 하지 않았다.

## 정리 관찰

B에서 새 문서의 자동 검색까지 확인한 뒤 소유 앱/문서 제거, 원래 앱 hash 및 provider 보존, 시험 프로세스 부재를 확인했다. 그러나 importer catalog는 반복 60초 대기 뒤에도 삭제된 경로를 유지했다. LaunchServices dump에는 해당 소유 경로의 등록 레코드가 0개임을 별도 확인했다. 이 상태에서는 다음 설치 시험을 겹치지 않고 catalog 제거를 기다린다. 전역 reset이나 daemon 종료는 수행하지 않는다.

B의 catalog는 네 번의 60초 MISS와 추가 대기 이후 같은 cleanup 재호출에서 PASS가 됐으며 최종 cleaned다. 별도 등록 명령/source 제거/reset은 없었다. 조회를 쉬었던 구간이 있었지만 그 효과를 단독 원인으로 단정하지 않는다.

## direct 첫 시험의 혼입 요인

C의 direct 시험은 첫 실행 60초와 추가 발견 60초 모두 MISS였다. 실제 후보 프로세스는 1개였다. 다만 direct 앱 디렉터리를 먼저 mkdir하는 초기 구현 때문에 설치 앱 root mtime이 원본과 달랐다. 작은 일반 디렉터리 대조에서 ditto의 새 destination은 원본 mtime을 보존하고 미리 만든 destination은 보존하지 않음을 재현했다. 이를 수정하고 부분 복사 실패 소유권 회귀를 추가했다. C는 순수 위치 비교나 정상 설치 수용 기준의 근거로 쓰지 않는다. 같은 C 후보의 후속 재등록/timestamp 실험은 초기 조건을 명시한 진단으로만 남긴다.

C에서 앱 실행과 파일/시각을 그대로 두고 `lsregister -f`만 다시 수행해도 이후 60.58초 발견은 MISS였다. 재등록만으로 충분하다는 증거는 얻지 못했다. 이어 importer 디렉터리 시각만 바꾸는 진단을 수행한다.

C에서 importer 디렉터리 mtime만 바꾼 뒤 60초 발견은 MISS였다. 이어 앱 디렉터리 mtime만 추가로 바꾸자 14.16초에 발견됐다. 이 두 시각 갱신 사이에는 재복사·재실행·추가 등록을 하지 않았다. 실제 후보의 HWP3/HWP5/HWPX 본문 추출도 PASS다. 이는 이전 재설치 절차의 여러 조작 중 재복사·재실행 없이도 발견을 유도한 관찰이며, touch 하나의 단독 원인이나 일반 최초 설치 성공을 뜻하지 않는다.

C는 시각 갱신 후 발견돼도 기존 문서 본문 검색이 60초 내 나타나지 않았다. 이어 앱만 종료/재실행하여 실행 이벤트의 영향을 비교한다. helper의 재실행 결과가 first-launch로 표시되지 않도록 실행 횟수와 재실행 label을 구분했다.

C의 시각 갱신 후 앱 재실행에서도 기존 문서 검색은 60초 timeout이었다. 수동 `mdimport -i`는 사용하지 않았다. 이후 표준 cleanup으로 C를 정리한다.

## 단계 검증과 인계

운영 회귀 16개, bundle 회귀 3개, source bundle 계약, Python 구문 및 diff 검사를 통과했다. 이 단계의 완료는 자동 설치 판정 도구와 실패 재현 기록에 한정한다. 실제 최초 설치 수용 기준은 미완료이며 Stage 3에서 소스 시각 비교, 정리 최종 확인과 보고서를 이어간다. 소유 앱/문서가 제거되어도 catalog가 남으면 cleaned로 표시하지 않는다.
