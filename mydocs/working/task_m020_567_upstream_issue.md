## 게시 본문

### 배경과 현재 기능

Studio의 기존 로컬 글꼴 처리를 재사용하면서, 임베드 호스트가 제공하는 글꼴을 연결할 수 있는 선택적 확장점을 제안합니다.

Studio에는 이미 다음 기능이 있습니다.

- `queryLocalFonts()`를 통한 글꼴 목록 조회와 필요한 글꼴 파일 데이터 읽기
- 해당 경로를 사용할 수 없을 때 후보 글꼴의 존재 여부 검사
- 글꼴 이름·별칭 매칭과 CanvasKit용 글꼴 데이터 준비

이 제안은 로컬 글꼴 감지 기능을 새로 만드는 것이 아니라, 기존 처리 경로에 브라우저 외의 데이터 공급원을 연결하려는 것입니다.

조사 기준은 `devel`의 `722fb38af361ed3508aef7ca0ac3a8fdc5d3c0db`이며, 주요 관련 코드는 [local-fonts.ts](https://github.com/edwardkim/rhwp/blob/722fb38af361ed3508aef7ca0ac3a8fdc5d3c0db/rhwp-studio/src/core/local-fonts.ts)와 [canvaskit-renderer.ts](https://github.com/edwardkim/rhwp/blob/722fb38af361ed3508aef7ca0ac3a8fdc5d3c0db/rhwp-studio/src/view/canvaskit-renderer.ts)입니다.

### 해결하려는 문제

호스트가 글꼴 목록과 파일 읽기 권한을 가지고 있어도, Studio의 실행 환경에서 `queryLocalFonts()`를 사용할 수 없거나 호스트가 관리하는 글꼴이 브라우저 감지 목록에 포함되지 않으면 기존 경로에 연결하기 어렵습니다. 후보 글꼴의 존재 여부를 검사하는 것만으로는 CanvasKit에 전달할 원본 데이터를 얻을 수 없습니다.

예를 들어 호스트가 승인된 글꼴 목록을 전달하고, Studio가 문서에서 실제로 사용하는 글꼴만 요청할 수 있으면 전체 파일을 미리 읽거나 브라우저 전역 API를 흉내 내지 않고도 기존 글꼴 처리 기능을 활용할 수 있습니다.

구체적인 사용 사례는 네이티브 macOS 호스트에서 Studio를 사용하는 경우입니다. 다른 임베드 호스트에도 적용할 수 있는 구조를 기대하지만, 여러 제품의 수요가 확인되었다는 의미는 아닙니다.

### 제안하는 최소 범위

호스트가 선택적으로 연결할 수 있는 다음 경계를 제안합니다. 구체적인 API 이름과 전달 형식은 기존 아키텍처에 맞춰 논의하고 싶습니다.

1. **글꼴 목록 제공:** family·full name·PostScript name·style 등 기존 매칭에 필요한 정보와, 경로를 노출하지 않는 글꼴 식별자를 제공합니다.
2. **필요한 데이터 읽기:** Studio가 선택한 글꼴의 파일 데이터를 비동기로 요청합니다. 목록 조회 시 전체 글꼴 파일을 읽도록 요구하지 않습니다.
3. **변경과 연결 해제 처리:** 목록 갱신 또는 공급자 해제 시 이전 요청과 관련 캐시를 정리합니다. 같은 이름의 글꼴 파일이 교체되어도 이전 데이터가 계속 사용되지 않아야 합니다.

호스트별 통신 방식은 어댑터가 담당하고, Studio는 글꼴 공급 계약만 알도록 하는 방향입니다. iframe용 새 RPC나 특정 WebView 프로토콜까지 한 번에 도입하자는 제안은 아닙니다.

### 호환성과 검증 기준

- 공급자를 지정하지 않으면 기존 브라우저 감지·저장·렌더링 동작을 유지합니다.
- 기존 이름·별칭 매칭을 재사용하고, 동일 family의 Regular/Bold 등 서로 다른 face를 구분합니다.
- 호스트의 파일 경로나 권한 정보를 Studio 저장소에 보관하지 않습니다. 호스트 제공 목록의 영속 저장 여부는 별도 논의가 필요합니다.
- 글꼴 읽기 실패·목록 변경·연결 해제 후에는 오래된 비동기 결과가 다시 적용되지 않아야 합니다. 사용할 수 없는 글꼴은 기존 대체 글꼴 처리로 이어집니다.
- 내부 식별자나 렌더링용 이름이 저장 문서의 글꼴명으로 기록되지 않아야 합니다.
- 렌더러별 적용 범위를 명시하고 검증합니다. 한 경로에서의 성공을 모든 화면·출력 경로의 지원으로 간주하지 않습니다.

### 범위에서 제외할 사항

운영체제별 폴더 탐색·설치·접근 권한, 네이티브 메시지 통신, 가져오기 UI, 글꼴 보관함, 공급 우선순위와 중복 충돌에 대한 제품 정책은 호스트가 담당합니다. Rust 조판 엔진 변경과 PDF·인쇄 지원 확대도 이번 제안에 포함하지 않습니다.

### 대안과 논의하고 싶은 점

호스트에서 `queryLocalFonts()` 호환 함수를 주입하거나 Studio 자체 패치를 유지하는 대안도 가능합니다. 다만 전자는 브라우저 API의 동작과 저장·갱신 흐름을 맞춰야 하고, 후자는 Studio 업데이트마다 변경분을 유지해야 합니다. 명시적인 작은 확장점이 이 비용을 줄일 수 있는지 논의하고 싶습니다.

- 기존 확장점으로 이 사용 사례를 처리할 수 있는 권장 방법이 있을까요?
- 별도 공급자 연결이 적절하다면 기존 `local-fonts` 계층에 두는 것이 맞을까요?
- 최초 구현에서 필요한 목록·데이터 읽기·변경 통지의 최소 계약과 렌더러 지원 범위는 어디까지가 적절할까요?

방향이 맞는다면 작은 구현과 회귀 테스트를 준비해 기여하고자 합니다. 현재는 설계 제안 단계이며, API나 구현이 확정된 상태는 아닙니다.
