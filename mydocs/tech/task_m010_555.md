## 1. 지금 필요한 계정 준비

아래는 최초 연결 절차다. 작업지시자의 Chrome 직접 진행 요청에 따라 앱 생성 화면을 준비했고, 작업지시자가 이메일을 수정하고 최종 ‘앱 만들기’를 실행했다. 이후 에이전트가 `postmelee`를 Threads 테스터로 초대했고, 작업지시자가 초대와 기본 조회 인증을 수락했다. 발급 토큰은 저장소 밖의 보호된 임시 파일(디렉터리 700, 파일 600)로 전달하여 probe에 사용했다. 토큰·API 원본 응답·게시물 본문은 대화나 저장소에 기록하지 않았으며 GitHub secret 등록과 운영 활성화는 수행하지 않았다.

- 앱 이름: `알한글 소식`, Meta 앱 ID: `1601095448152539`, Threads 앱 ID: `1584332403182930`.
- 앱은 게시되지 않은 상태이며 `threads_basic`만 테스트 준비 완료다. 선택 권한은 추가하지 않았다.
- 작업지시자가 Threads의 **웹사이트 권한 → 초대**에서 수락했고, 앱의 사용자 토큰 생성기에 `postmelee`와 ‘액세스 토큰 생성하기’ 버튼이 나타난 것을 확인했다.
- 토큰 생성기의 인증 화면은 기본 조회 외에 게시·답글 관리·인사이트·답글 조회도 기본 선택했다. **액세스 권한 수정**에서 네 선택 권한을 모두 해제하고 프로필·게시물 기본 조회만 남겼다. 작업지시자가 ‘postmelee 계정으로 계속’을 실행한 뒤 ‘postmelee님을 위한 토큰 생성됨’을 확인했다.

1. [Meta 개발자 앱 대시보드](https://developers.facebook.com/apps/)에서 개발자 등록·로그인을 완료하고 앱을 만든다. 이름 예시는 `알한글 소식`이며, 사용 사례는 **Access the Threads API**를 선택한다.
2. 앱의 **Use cases**에서 Threads 사용 사례를 열어 `threads_basic`을 확인한다. 본인 글 조회에 필요한 기본 권한이며, 이번 조사에는 게시·댓글 관리·다른 계정 검색 권한을 추가할 필요가 없다.
3. **App roles → Roles → Add People → Threads Tester**로 `postmelee`를 초대한다. Threads에서 `@postmelee`로 로그인하고 **계정 설정 → Website permissions**에서 초대를 수락한다.
4. 앱의 **이용 사례 → Threads API 액세스 → 설정 → 사용자 토큰 생성기**에서 `@postmelee`의 토큰을 생성한다. 실제 화면은 공개 Threads 테스터 계정용 장기 액세스 토큰을 생성한다고 안내한다. 초대 수락 전에는 테이블이 비어 있다. 인증 화면의 **액세스 권한 수정**에서 선택 권한 네 개를 모두 끄고 기본 조회만 남긴 뒤 요청 권한과 계정을 확인한다.
5. 토큰은 대화·이슈·문서에 붙여 넣지 않는다. 아래 명령을 사용자 터미널에서 실행하고 숨김 입력에 토큰을 입력한다. 명령줄 자체에는 토큰이 들어가지 않는다.

```sh
python3 /Users/melee/Documents/projects/rhwp-mac/scripts/ci/threads-news.py probe
```

토큰을 다시 입력하려면 기존 `THREADS_ACCESS_TOKEN` 환경변수가 없는 사용자 터미널에서 실행한다. 이미 환경변수가 설정되어 있으면 도구는 그 값을 우선 사용한다. 토큰 값을 확인하려고 환경 전체나 변수 내용을 출력하지 않는다.

보호된 로컬 파일로 전달할 경우 본인 소유·권한 `600`의 일반 파일만 `--token-file`로 지정할 수 있다. 심볼릭 링크, 그룹/다른 사용자 읽기가 가능한 파일은 거부한다. 저장소에 토큰 파일을 커밋하지 않는다. 최초 확인에서는 별도 저장 없이 숨김 입력을 사용하는 편이 간단하다.

출력 JSON은 계정 ID, 조회 개수, 필드 반환 개수, 예시 글 판정만 포함한다. 이 요약은 후속 확인에 사용할 수 있다. 도구의 출력에는 게시물 본문과 토큰이 없지만 별도로 API 원본 응답이나 토큰 발급 화면 전체를 공유하지 않는다.

- `probe_complete`: 설정한 API 조회에서 pagination 종료를 관찰함. 모든 과거 글이 제공되었다거나 Stage 1 전체가 완료되었다는 뜻은 아니다.
- `probe_partial` / 종료 코드 2: 기본 5페이지 조사 상한에 도달함. 필요하면 `--max-pages`로 범위를 늘린다.
- 종료 코드 1: 인증·응답·데이터 계약 오류. 본문과 token URL을 생략한 오류만 표시한다.
- `example_classification=candidate`: 예시 shortcode가 실제 조회 결과에 있고 대상 작성자·태그·원문 조건을 통과함.
- `stage1_complete=false`: 도구는 API/임베드 관찰 결과만 반환하고 사람의 단계·운영 승인 여부를 자동 판정하지 않는다.

최초 응답에서 계정 ID를 확인하면 다음 실행에는 `--expected-user-id`로 같은 계정인지 고정 검증한다. 다른 작성자의 프로필을 일반 공개 검색으로 조회하는 방법으로 대체하지 않는다.

## 2. 공식 문서에서 확인한 계약

2026-09-15 공식 문서를 직접 조회했다. 웹 검색 도구에서 일부 페이지를 열지 못했으나 해당 공식 URL에 대한 읽기 전용 HTTP 요청으로 본문을 확인했다. 아래 내용은 실제 계정 실측과 구분한다.

| 항목 | 확인한 계약 | 구현 반영 |
|---|---|---|
| 본인 글 조회 | `GET /{threads-user-id}/threads`, 공식 예제의 `v1.0/me/threads` | 고정 HTTPS API host의 읽기 전용 endpoint만 사용 |
| 본인 조회 권한 | `threads_basic` | Stage 1 본인 조회 조사에 사용. 공개 재표시의 허용 근거는 별도 확인 필요 |
| 작성자 | `owner`는 본인이 소유한 최상위 글에만 반환 | 계정 ID와 username을 함께 대조, 필수 identity가 없으면 미확인 |
| 주제 태그 | `topic_tag`는 실제 태그가 있는 글에만 반환 | 전체 요청이 성공했을 때 필드 부재는 태그 없음. 본문 검색으로 대체하지 않음 |
| 재게시물 | `reposted_post`는 재게시물에만 반환, `media_type`에 `REPOST_FACADE`가 있음 | 둘 중 하나로 재게시를 확인하면 제외 |
| 답글 | 답글은 별도 Retrieve User Replies 문서의 endpoint로 조회 | 본인 원문 목록만 조회. 원문 fields에 문서화되지 않은 `is_reply`를 강제로 요청하지 않음 |
| 원문 링크 | 저작권 관련 게시물에서 `permalink`가 생략될 수 있음 | 링크가 없으면 제외하고 링크를 조작해 만들어내지 않음 |
| 긴 글/미디어 | `text_attachment`, `children`, video thumbnail 등 별도 필드 | 실제 응답 구조·표시 범위는 미확정. probe에서 존재 개수를 확인 |
| 특수 글 | `ghost_post_status`는 ghost post에만 반환 | 임시 글을 상시 소식 후보에 넣지 않음 |
| 페이지네이션 | before/after cursor와 limit 사용 | API가 준 next URL을 토큰과 함께 따라가지 않고 cursor로 요청 재구성 |

출처: [Retrieve User Posts](https://developers.facebook.com/docs/threads/retrieve-and-discover-posts/retrieve-posts), [Meta 공식 Postman 목록 조회](https://www.postman.com/meta/threads/documentation/dht3nzz/threads-api?entity=request-34203612-116161fc-75af-4a09-a972-66d6f64ddb10).

`topic_tag`/`reposted_post` 부재를 일괄 미확인으로 두었던 초기 계획의 모호함은 공식적으로 문서화된 조건에 한해 해소했다. 단, 필드 요청이 실패한 응답을 성공으로 취급하거나 지원 안 되는 필드를 자동으로 빼고 재시도하지 않는다. 문서상 선택 필드와 필수 identity/타입 필드를 구분한다.

### 앱 대시보드에서 추가로 확인한 표시 제한

2026-09-15 생성한 앱의 **이용 사례 → Threads API 액세스 → 권한 및 기능**과 [Meta 공식 권한 참조](https://developers.facebook.com/docs/permissions/)의 `threads_basic` 행을 Chrome에서 직접 확인했다. 본인 게시물을 앱 안에 표시하되 작성자 본인에게만 보이도록 하는 용도를 명시한다. 본인 게시물 API 조회 가능 여부와 불특정 방문자에게 본문을 공개 표시할 수 있는지는 별개의 조건이다. 기존 계획의 `threads_basic`만으로 공개 소식 카드를 제공한다는 전제는 확정 근거가 부족하므로 보류한다.

같은 화면의 `threads_profile_discovery`는 공개 계정과 공개 게시물 접근을 설명한다. 공식 권한 참조의 전체 설명은 경쟁사 분석 용도를 명시하므로 이 권한을 추가하면 제품 소식 공개가 허용된다고 판단하지 않는다. `threads_keyword_search`도 소셜 미디어 활동 관리와 사용자가 검색한 공개 콘텐츠 표시를 설명한다. 두 권한 모두 추가하지 않았다.

### 공개 화면 보정 제안 — 자동 선별과 공식 임베드 검토

예시 원문의 **공유하기 → 퍼가기 코드**에서 Threads가 제공하는 공식 임베드 미리보기와 코드를 확인했다. 코드는 원문 URL을 가진 `blockquote.text-post-media`와 `https://www.threads.com/embed.js`로 구성되며 게시물 본문을 코드에 복사하지 않는다.

최초에는 수동으로 선정한 URL 목록을 제안했으나, 사용자의 자동 연결 가능 여부 질문에 따라 [공식 oEmbed 안내](https://developers.facebook.com/documentation/threads/tools-and-resources/embed-a-threads-post)와 [API 참조](https://developers.facebook.com/documentation/threads/reference/oembed)를 추가 확인했다. 영문 원문은 외부 웹사이트 표시와 API를 통한 프로그래밍 방식의 임베드 생성을 명시한다. 최신 안내의 예시는 `https://graph.threads.com/v1.0/oembed?url=...`이며 인증 매개변수가 없다.

2026-09-15 위 endpoint에 예시 URL만 보내 **토큰 없이 HTTP 200**과 `type=rich`, `provider_name=Threads`, `html`, `width=658`을 확인했다. 반환된 임베드의 URL은 `/t/DdTIl2SEsaU`와 임베드용 추적 query로 정규화되었고 `https://www.threads.com/embed.js`를 포함한다. 기존 Postman 예시의 standard access 제한을 현재 oEmbed 전체에 그대로 적용하지 않는다. 실제 임베드 렌더링·운영 검증과 엔드포인트 응답 성공은 구분한다.

검토할 자동 연결 구조:

1. 비공개 수집 작업에서 본인 API로 작성자와 실제 `알한글` 태그를 판별한다. 공개 본문·미디어 데이터셋을 만들지 않는다.
2. 대상 원문 URL을 공개 oEmbed endpoint로 검증하고, 허용된 글의 공식 임베드를 소식 목록에 반영한다. 홈 3개와 전체 목록은 유지하며 게시물 본문·미디어는 공식 임베드가 표시한다.
3. 저장은 표시용 원문 참조와 최소 운영 상태 중심으로 설계한다. oEmbed 내용은 게시물의 프론트엔드 표시 용도로만 사용하며 본문 추출·재구성·분석용 아카이브를 만들지 않는다. 삭제·비공개·태그 제거 시 목록과 캐시 갱신, 만료 기간, 로딩 실패의 원문 링크 대체를 설계한다.
4. 수동 입력은 기술적으로 필수 조건이 아니다. 다만 `threads_basic`으로 찾은 URL을 공개 oEmbed 목록에 자동 연결하는 전체 사용 사례가 Meta로부터 승인되었다는 뜻은 아니다. 각 endpoint의 동작과 허용 범위를 근거로 한 설계 후보이며, 기본 권한의 사용 목적과 이 연결의 적합성을 Stage 1의 남은 확인 사항으로 유지한다.
5. 이후 사용자의 “진행해줘.” 지시로 대상 6개 전체의 자동 선별·공개 oEmbed와 로컬 렌더링을 검증했다. 이 결과를 바탕으로 구현계획 보정안을 작성했다. Stage 2 진입과 공개 활성화는 각각 별도 승인 대상으로 유지한다.

- probe 기본 예시 shortcode에 이 값을 사용하고, synthetic fixture 검증에서는 `SyntheticOnly`로 분리한다.

## 4. 인증·토큰 운영

- [Get Started](https://developers.facebook.com/docs/threads/get-started): 앱 역할이 있는 Threads tester는 개발 중 인증할 수 있다. 앱 역할이 없는 다른 사용자의 데이터 접근에는 별도의 App Review·공개 조건이 있다. 본인 계정 연결 검증과 다중 사용자 서비스를 구분한다.
- [Threads 앱 사용 사례 설정](https://developers.facebook.com/docs/development/create-an-app/threads-use-case): Threads app ID/secret, tester 역할 및 앱 공개 시 필요한 개인정보처리방침·데이터 삭제 경로를 확인할 수 있다.
- [Long-Lived Access Tokens](https://developers.facebook.com/docs/threads/get-started/long-lived-tokens): short-lived 토큰은 1시간이며 유효할 때 장기 토큰으로 교환할 수 있다. 장기 토큰은 60일이고 발급/갱신 후 최소 24시간이 지났으며 만료 전이어야 갱신 가능하다. 실제 만료 기록은 응답의 수명을 사용한다.
- Stage 1의 probe는 기존 사용자 토큰으로 읽기만 한다. 토큰 교환·갱신 및 GitHub secret 저장 helper는 계획한 Stage 2 범위다.
- Meta 앱 secret은 이번 probe에 필요하지 않으며 도구가 입력받지 않는다. 토큰 갱신 및 앱 secret 처리 방식은 운영 설정 단계에서 분리한다.

## 5. 저장·수정·삭제 운영 보정안

[Meta 플랫폼 약관](https://developers.facebook.com/terms/)의 데이터 유지·삭제 항목은 갱신·삭제 요청 대응을 요구한다. 본문과 과거 snapshot을 장기 Git 이력에 쌓는 구조 대신 **Threads 원문에서 매 배포마다 현재 목록을 재생성**하는 구조로 보정한다. 현재 263개는 7페이지로 조회되므로 별도 장기 저장소 없이 실행 가능한 규모다.

- 공개 JSON v2: `schema_version`, `updated_at`, `expires_at`, `items[{platform,permalink}]`만 허용한다. 본문·태그·작성자 객체·날짜·미디어·숫자 ID는 공개하지 않고 공식 임베드가 표시한다.
- 원본·token·인증 URL·oEmbed HTML은 Git이나 지속 캐시에 저장하지 않는다. 표시용 링크 snapshot은 runner 임시 경로와 현재 Pages 산출물에만 둔다. 개발 중 실링크는 gitignore 대상 `build.noindex/`에만 둔다.
- 6시간 주기로 매번 완전 조회한다. 완전 조회에서 태그가 사라지거나 미관찰인 글은 새 목록에서 빠진다. 이는 ‘현재 표시 대상에서 제외’이며 원문의 삭제·비공개·권한 철회 이유를 확정하는 판정이 아니다.
- 페이지·계정·인증·oEmbed 중 하나라도 실패하면 새 snapshot 배포를 중단한다. 마지막 성공 사이트는 남지만, 표시 기한 48시간이 지난 뒤에는 frontend가 임베드 표시를 중단한다. 표시 기한은 서버/CDN에서 JSON 자체를 삭제하는 기능이 아니므로 명시 삭제 요청에는 재배포와 artifact 제거가 따로 필요하다.
- 본문·미디어 수정과 원문의 접근 상태는 공식 임베드가 현재 상태를 반영한다. Threads 캐시의 정확한 반영 시간을 보장하지 않는다. 상세 데이터·긴 글·동영상 재생은 공식 UI에 맡기므로 원본 추출·CDN URL 갱신 구현이 필요 없다.
- 뉴스 포함 Pages artifact 보존은 1일로 변경하는 안을 제시한다. [공식 action](https://github.com/actions/upload-pages-artifact)이 `retention-days`를 지원하며, [GitHub 문서](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/remove-workflow-artifacts)는 만료 전 artifact 삭제를 지원한다. 즉시 제거 요청 때 현재 사이트 재배포와 해당 artifact 제거를 함께 처리한다. 소식 참조는 release 증빙 artifact에 넣지 않는다.
- 기존 공개 appcast 보존·`pages-deploy` 직렬화는 유지한다. news input 조회는 잠금 안에서 수행하며 활성 상태의 조회 실패를 빈 seed로 대체하지 않는다. 이전 Git·Actions artifact를 읽어 소식을 복원하지 않는다.
- 전체 `threads_basic` URL 선별→공개 oEmbed 조합의 목적 적합성은 Meta의 별도 확인을 받은 상태가 아니다. 이는 기술적 장애와 구분하고 공개 활성화 전에 확인할 조건으로 문서화했다. 실제 게시·App Review 제출·문의 전송은 수행하지 않았다.

이 저장·보존·실패 처리 변경은 [구현계획 보정안](../plans/task_m010_555_impl.md)의 승인 대상이다. 기존 사용자 데이터·원격 branch·artifact의 삭제나 공개 배포 설정 변경은 수행하지 않았다.

## 6. 현재 산출물과 로컬 검증

- `scripts/ci/threads-news.py`: `probe`, `--check-embeds`, 로컬 검증용 `--reference-output`, `validate`, 분리된 인증/공개 client, 전체 조회·원문 대응·스키마 2 검증. 공개 oEmbed 응답의 HTML은 실행하지 않고 원문 참조만 추출한다. HTML 검증기는 범용 sanitizer가 아니며 raw HTML을 frontend에 넘기는 기능은 없다.
